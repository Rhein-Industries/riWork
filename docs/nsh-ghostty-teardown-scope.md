**Verdict: GPUI-host fallback inherits the blocker.** Its normal destruction path can synchronously enter the same `ghostty_surface_free` on the main/UI thread with a live tmux attachment and no prerequisite client detach. GPUI changes when the last terminal owner is collected; it does not introduce a detach-before-free protocol or move native destruction to a worker. This is a source-level verdict about inherited teardown exposure, **not a claim that a GPUI hang was reproduced**. The common call chain and individual paths below provide the evidence.

## Inside free: killing the PTY command is too late to be a precondition

Ghostty does attempt process cleanup **inside** the free/join operation. Its I/O loop defers backend threadExit on shutdown (`G/vendor/ghostty/src/termio/Thread.zig:264-279`, `G/vendor/ghostty/src/termio/Termio.zig:400-401`). Exec.threadExit first calls subprocess.stop; only afterward does it write the reader's quit pipe and join the reader (`G/vendor/ghostty/src/termio/Exec.zig:200-233`). The fork/exec stop calls killCommand/killPid, which repeatedly sends process-group SIGHUP, polls waitpid with WNOHANG and sleeps 10 ms while waitpid returns zero; the loop has no retry/time limit, while nonzero results or errors can end it (`G/vendor/ghostty/src/termio/Exec.zig:1124-1142`, `G/vendor/ghostty/src/termio/Exec.zig:1167-1224`). Thus the nearby comment saying stop “will not block” is not a bounded-disposal guarantee; the calling UI thread still waits for I/O completion (`G/vendor/ghostty/src/termio/Exec.zig:1120-1130`; `G/vendor/ghostty/src/Surface.zig:813-818`).

That is command/process-group cleanup, not an application-level `tmux detach-client` handshake. RiWork's local terminal command attaches an existing tmux session (`crates/riwork-desktop/src/main.rs:2441-2460`; `crates/riwork-engine/src/sessions.rs:999-1064`); the long-lived session is distinct from Ghostty's attach subprocess. The spike's external client detach unblocked exactly this destruction stage without killing its session, but no equivalent prerequisite appears in the adapter/native chain above (`S/WORKER_REPORT.md:111-120`).

## Verdict limits and verification

The two-per-pass release policy limits bursts, not the duration of one synchronous join (`crates/riwork-desktop/src/terminal_lifecycle.rs:26-34`; `G/vendor/ghostty/src/Surface.zig:813-818`). Hiding an NSView, clearing a shell claim, deferring Entity collection, or keeping GPUI as the host does not add the missing pre-free client-exit barrier; the common chain and path tables show where those operations occur. The active-tmux disposal gate therefore remains unresolved for this fallback.

**Unknown from this assignment:** whether a particular installed GPUI binary hangs, the duration/frequency of any wait, which outstanding Entity handle is last in a live frame, exact client PID/host-side remote cleanup timing, and whether the spike's sampled reader wait has the same upstream mailbox cause. The spike report itself preserves the last attribution as an inference (`S/WORKER_REPORT.md:122-134`). No code-only conclusion here establishes safe runtime disposal or every-build binary equivalence.
