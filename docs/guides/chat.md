## Harness launches and usage

The **New Tab** section of a pane's **…** actions menu launches a shell, Codex, Claude, Grok, or Muse in the selected worktree, one entry each. The agents start unrestricted, with each CLI's permission bypass flag (Codex `--dangerously-bypass-approvals-and-sandbox`, Claude `--dangerously-skip-permissions`, Grok `--always-approve`, Muse `--yolo`), while **Agent terminals run unrestricted** is on in Settings, which it is by default; turn it off and the same entries start them with the CLI's usual permissions, asking before they act. Cmd+Shift+C opens Codex; Cmd+Shift+L opens Claude; Cmd+Shift+G opens Grok; Cmd+Shift+U opens Muse, the same way. Scheduling a Grok or Muse *terminal* and Somtus activity and completion alerts for them are not yet supported. Grok has no chat; chats run Codex, Claude and Muse (see [Chats](#chat-tabs)).

Click the bottom usage readout, or open **USAGE** under **Views** in a pane's **…** actions menu, for remaining quota, reset countdowns, and update times. Codex reads its official app-server account endpoint on a worker with a timeout, refreshing every 15 minutes or on demand. Claude sends documented statusline JSON through settings passed only to that invocation; global Claude settings are unchanged. Claude quota appears after a response on supported Pro/Max accounts and versions. Context usage and estimated session cost appear separately. Missing quota windows stay unavailable; old snapshots are marked stale. Quota is shared by sessions on the same account.

Grok shows what its own CLI reports for each session, not the account allowance. Grok's **Usage limit**, **Credits left** and **Pay-as-you-go limit left** appear only in the `/usage` screen inside Grok; it has no official CLI or JSON interface for them, so Somtus does not read them and never calls Grok's private endpoints or reads its sign-in files. The USAGE tab lists every live Grok tab of the project with its model, total tokens (input, output, cached, cache writes and reasoning), turns and session cost in USD, then a combined total, and points to `/usage` for the allowance. The bottom readout for a focused Grok tab shows that session, for example `GROK $0.42 · 128k tok`; clicking it opens the USAGE tab. Somtus finds a tab's session by matching the pane's process (a Grok executable, or its direct child when the pane runs a wrapper) to an entry in `active_sessions.json` under `GROK_HOME` (default `~/.grok`). Entries whose pid has been reused by another program, or that name a process that started after they were written, are ignored, and a tab with two candidate sessions shows none. It then runs `grok usage SESSION_ID` on a worker with a 5-second timeout and bounded output, using the real Grok binary rather than Somtus's launcher. Figures are read only while the USAGE tab or the readout is on screen, at most every 30 seconds per session across all windows (a failed read after good figures is retried after 10 seconds), or immediately with **REFRESH**. A session Grok has not counted anything for yet shows as unavailable, not as $0.00. If a read fails or Grok is mid-write, the last figures stay, marked stale. Session figures include history inherited by a resume or fork. `somtus usage --shell SHELL_UUID` for a Grok shell prints the same figures. In `--json` the existing fields are unchanged (`windows` is empty and `account_label` is `unknown`, because the allowance is unknown), `session_cost_usd` is the cost, and a `session` object adds `session_id`, `primary_model`, `turns`, `model_calls`, `tokens` (`input`, `output`, `cached_read`, `cache_creation`, `reasoning`, `total`), `cost_usd`, `updated_at` and a per-model `models` list. When a session cannot be read (not running, not listed yet, ambiguous, Grok missing or slow) the command still succeeds and `session_error` says why. `somtus usage` without `--shell` reports the account of the shell it runs in (`RIWORK_SHELL_ID`): that shell's frozen Codex account, else its project's choice, else the app choice.

```sh
somtus usage --json
somtus usage --shell SHELL_UUID --json
somtus open PROJECT_NAME
somtus open /path/to/another/project
```

Project windows and independently launched app processes keep their own selected project. Projects, tasks, the shell registry, and layouts share the Somtus data directory. Older and newer builds can share it after `somtus update` leaves an older window or `somtus` on `PATH`: a build keeps the fields and shell entries it does not understand, such as a session for a harness it predates, when it rewrites `state.json` or `sessions.json`; it hides those entries instead of failing. A store schema newer than the build is still refused. Closing a window preserves its shells. There is one persistent global orchestrator and one persistent orchestrator per project.
## Chat host

Codex, Claude and Muse chats talk to the agents through their structured interfaces, not their terminals (Codex's app-server, Claude's stream-json, Muse's `serve` host over MSP). The agent processes behind them belong to the chat host, `somtus chat serve`, so a chat keeps working while app windows reload, update or quit. There is one host per Somtus data directory. It listens on `run/chat.sock` (mode 600, in a mode-700 directory, connections from other users are dropped), `run/chat.lock` keeps a second host out, and `run/chat.log` has its output. `somtus chat ensure` starts it detached if it is not running (several callers at once start one) and prints the socket. The host exits by itself after 15 minutes with no client connected and no chat starting, running or waiting for you (`chat serve --idle-seconds N` changes that); the next `ensure` starts it again.

```sh
somtus chat ensure
somtus chat new --provider codex --worktree WORKTREE_ID --mode auto-edit
somtus chat new --provider claude --project PROJECT_ID
somtus chat new --provider codex --project PROJECT_ID --model MODEL --effort high --fast --title "Fix the build"
somtus chat list --project PROJECT_ID --json
somtus chat send CHAT_ID "run the tests"
somtus chat events CHAT_ID --since 0 --wait-ms 10000 --json
somtus chat command CHAT_ID --command-json '{"command":"interrupt"}' --json
somtus chat command CHAT_ID --command-json '{"command":"switch","provider":"claude","model":"opus"}'
somtus chat models --provider claude --project PROJECT_ID --json
somtus chat suggestions CHAT_ID --json
somtus chat stop CHAT_ID
```

**Muse chats** run one `muse serve` per chat. They cover:

- **Messages and steering.** A message sent while a turn runs is steered into exactly that turn (`turn/steer` with the turn's id). One sent while the turn is starting waits for its id. One that Muse refuses because the turn just ended starts the next turn, once.
  - Muse 1.4.7 answers a steer that arrives after the turn's last model call as accepted, but under the steer's own id instead of the turn's, and drops it. Such a message is not sent again; a notice gives it back in full.
  - A typed message is never lost silently. One that Muse refuses, that is never written, or that is waiting or unconfirmed when Muse stops or dies comes back in full in a notice. One whose delivery is uncertain is never resent.
- **Attachments.** UTF-8 text files arrive as text. Static PNG and JPEG images arrive as MSP image parts (`mediaType`, `base64Data`), within the same limits as the other providers. The transcript shows the message as sent, with its snapshots, never the file contents.
  - The send is answered only once Muse has taken or refused it, so a refusal keeps the draft.
  - Attachments are refused while a turn is starting or being interrupted.
  - A reply that cannot be matched to the turn is reported as unknown rather than retried.
- **Approvals.** Each choice Muse offers has a scope (`once`, `session` or `localPersistent`). **Allow**, **Allow for this session** and **Decline** send only a one-time or session-scoped choice. Somtus never sends a choice that saves a lasting rule; when Muse offers a grant only in that form, the chat says so and offers Decline and Stop. A refreshed approval (`approval/updated`) is shown again with its new subject. A refresh that leaves no choice Somtus can send closes the prompt and says so, so an earlier step's choice is never sent against the new one.
- **Questions.** Single choice, several choices within Muse's bounds, and free text up to Muse's 500 characters. An answer outside those limits is refused before anything is sent. A question Muse settles by itself after a delay says so; showing it does not stop the countdown.
- **Modes.**
  - **Supervised**, **Auto-edit** and **Full** select Muse's `promptUnmatched`, `onRequest` and `allowAll` under the permission profile your Muse settings choose. Muse's own default profile is Auto-review, where an AI reviewer may decide eligible approvals.
  - Muse has no planning mode. **Plan** starts the conversation under Muse's **Read only** profile ("Reads files only") with `denyUnmatched`, and the chat says so. Under that profile a write by a shell command is refused.
  - Muse fixes a conversation's profile when it starts, so a Muse conversation cannot be moved into or out of Plan. Start a new Muse chat instead.
  - Muse has no fast mode. Somtus refuses it for a running chat. A new Muse chat that asks for it, for example from an automation, is made without it and says so.
- **Contributor mode.** Somtus starts every Muse with Muse's contributor mode off, whatever your Muse settings say, and turns it on only for a chat or terminal you ask it for. Muse says that with contributor mode off, your content won't be used for product improvement. Every start of a Muse chat (creation, each resume, after a restart of the chat host, back from another provider) runs `muse serve --contributor-mode off`, or `on` for a chat you turned on: an override for that process that Muse never saves, so your Muse settings stay as they are. Model discovery runs off too. Turn it on for a new chat with the **Contributor off/on** toggle the new-chat dialog shows for Muse (`chat new --contributor-on`; `--contributor-opt-out` is the explicit off), and for an existing one with the **Contributor** toggle beside the model picker (or `{"command":"configure","contributor_mode":"on"}` and `"off"`); the choice stays with the chat until you turn it off. Muse fixes the mode for a process, so an idle chat restarts `muse serve` and resumes the same conversation with its model, effort and approval mode; a stopped chat keeps the choice for its next start. The change waits while a turn runs, waits for you or Muse still starts. If Muse does not start again with it, the chat keeps its old choice and says so. Chats from before this release, opted out or not, start off. Muse terminals Somtus starts (New Tab, `shell create --harness muse`, handoffs) pass `--contributor-mode off` too, or `on` with `shell create --contributor-on` or `handoff --contributor-on`; and `muse` typed in a Somtus terminal, or run by an agent there, adds `--contributor-mode off` to a session it starts (interactive, `resume`, `exec`, `serve`) unless you pass `--contributor-mode` yourself, leaving `--help`, `--version` and Muse's other subcommands as typed (`muse help` is a prompt to Muse 1.4.7, so it starts off too). A Muse run outside Somtus, or by an absolute path to the Muse binary, follows your Muse settings. A Codex or Claude chat has no contributor mode to turn on: asked for one, it is made without it, with a notice, and it refuses on; a chat that switched away from Muse with it on keeps it for a switch back, and can turn it off.
- **Switching providers.** A chat that moves to Muse sends the conversation so far with its first message to Muse, as a leading part of that message. The transcript shows only what you typed. It is sent once: a resumed Muse conversation that has run a turn already has it.
- **Cua.ai Driver.** Somtus's Cua.ai Driver reaches the chat as an MCP server for that session only (`config.mcpServers` on `session/start` and `session/resume`, which needs Muse's `sessionMcp` capability), never through Muse's settings. A Muse without that capability runs the chat without it, and the chat says so.

`chat/muse_tests.rs` checks the driver against fixtures and, with `MUSE_LIVE_BIN` naming the Muse binary itself, against the real `muse serve --provider echo` in throwaway homes. The live tests cover:

- a private stand-in MCP server started at `session/start` and again at resume;
- the carried-over conversation, attachments, steering and interrupt;
- the Read only profile.

Approvals, questions and compaction are checked against fixtures only, because the echo provider cannot produce them.

`--mode` is how much the agent may do without asking: `supervised` (the default; ask before commands and edits), `auto-edit` (edit the workspace, ask for the rest), `full` (never ask; what unrestricted launches use) or `plan` (plan first, change nothing). Like `shell create`, `chat new` starts in the given worktree, in the project's primary worktree, or else in the active project. Chat IDs are UUIDs; commands accept a unique prefix of at least eight characters.

`chat new --json` prints the chat as `chat list --json` shows it, also when its provider did not start (its state is then `failed`, with the reason); without `--json` that is an error. `--model`, `--effort` and `--title` (at most 100, 32 and 200 characters, no control characters) take their value as it is, also with `=`, so a title may begin with `--`. `--fast` turns on the provider's fast mode for a model that has one (Codex's Fast service tier, Claude's fast mode); `{"command":"configure","fast":true}` (or `false`) changes it later, and the chat tab's toolbar shows a Fast toggle for a model that supports it. The tab's model picker lists the models the agent itself reports (a `models` event in the chat's log) with the efforts each takes, and falls back to a text field for an agent that reports none. `chat list --project` lists one project's chats.

`chat events` and `chat command` are what the phone's remote connector runs for chats (see `docs/remote-protocol.md`, "Chat extension"), and work from a terminal too. `chat events CHAT_ID --since N --wait-ms M` reads the events after `seq` N and prints one compact JSON line, `{"chat_id","events":[{"seq","event"}],"next","more"}`. Events that are already there come at once; otherwise it waits up to M milliseconds (at most 25000) for the first one and then collects for another 50 ms. `--max` (500 by default, at most 2000) and `--max-bytes` (1 MiB by default, at most 2 MiB) cut the page; `more` says it was cut, and `next` is the `--since` for the next call. An event too big for a page alone has its long strings cut. `chat command CHAT_ID --command-json JSON` sends one command to the chat (`send`, `interrupt`, `approve`, `answer`, `configure`, `compact`, `stop` or `switch`, in the JSON of the chat model) and refuses anything with a field it does not use; a refusal of the command starts with `invalid_request:`. `somtus capabilities --json` has `"chat": true` in a build that has all of this.

`{"command":"switch","provider":"codex|claude"}` (with an optional `model`, `effort` and `fast`) moves a chat to the other provider in place, as the model menu of a chat tab does (see [Chat tabs](#chat-tabs)): the same id, log and approval mode, a new agent on a thread of its own that is given the conversation so far. It is refused while a turn runs or waits, and with the provider the chat has it is an ordinary `configure`. A chat host started by an older Somtus refuses it as a command it does not know. `chat models --provider codex|claude [--project ID]` prints what a chat of that provider can be set to, read from saved chats without starting the host: the newest list a driver of the provider reported (in a chat that runs the project's Codex account, for Codex), the other model IDs chats were set to, and why the provider cannot be offered, if it cannot. `somtus capabilities --json` has `"chat_provider_switch": true` and `"chat_models": true` in a build that has them.

Each chat is a directory, `chats/CHAT_ID/`, in the Somtus data directory: `info.json` (the chat's id, project, worktree, directory, title, mode, model, effort, fast mode, the provider's thread id, the Codex account it runs under, for a chat that is an orchestrator, its `orchestrator` scope and, for one that switched provider, `carried_over`, the document of the conversation before the switch and whose it was, replaced atomically) and `events.jsonl` (everything that happened in it, one JSON object per line, appended as it happens; the line number is the event's `seq`). A client that opens a chat gets `events.jsonl` from the `seq` it last saw and then follows live events on the same connection, so a client that reconnects loses nothing; one that falls too far behind is disconnected and asks again from its last `seq`. The host starts no agent when it starts: every chat it loads is stopped, and the first message to one starts its agent again on the saved thread (Codex `thread/resume`, Claude `--resume`). A turn that a stop or a crash cut off is ended in the log (as interrupted) so no window waits for it. `chat stop` ends the agent and keeps the history; deleting a chat also removes its directory. If an agent cannot start (not installed, no Cua driver, a Codex account that is no longer available) the chat is kept as failed with the reason, and the next message tries again.

Chats are started the way terminal launches are: the same `codex` and `claude` programs (found on the login shell's `PATH`), the same Cua.ai Driver MCP wiring (`mcp_servers.cua-driver` for Codex, `--mcp-config` for Claude), the Codex account of the project (or of the app) saved with the chat so a chat keeps its Codex home, and Claude's `ANTHROPIC_API_KEY` as the chat's billing says (see **Claude chats bill** in [Settings](settings.md#settings)): removed on Subscription, so a stray key cannot switch it to API billing; on API key, the key saved in the Keychain, or with none saved the environment as it is. The agent's environment has `RIWORK_CHAT_ID`, the chat's id, as a terminal agent's has `RIWORK_SHELL_ID` (Codex is told it in its shell environment policy too, since it builds the environment of its commands from that); `somtus handoff` uses either to find the conversation that is meant when no `--from` is given. The host's `create` request takes an optional Codex account of its own (`codex_account_id`, an account id) in place of the project's; `somtus handoff` uses it, and `chat new` does not offer it.
## Chat tabs

The [chat improvement roadmap](../../docs/chat-improvement-roadmap.md) tracks the output, conversation, worker, and mobile improvements, with delivery status and acceptance checks.

A chat is one native conversation for every model, Codex's and Claude's, instead of an agent's terminal. **New chat…** in a pane's **⋯** menu, **View → New chat…**, **New chat…** in the Sessions panel and Cmd+Option+Shift+C open a **New chat** tab that asks where the chat works (the project's root or a worktree, the selected one first), its permissions (Supervised, Auto-edit, Full, which never asks before it acts, or Plan) and its model: one list with Codex's models and Claude's under their own headings, each with its provider's default, a search field, and a field for a model ID the list does not have, which is a model of the provider whose model is chosen. The model decides whether the chat is Codex's or Claude's; nothing else asks. A **First message** is optional: **Start chat** creates the chat and sends it, and a message that cannot be sent stays in the chat's message box. **Create chat** (or **Start chat**) turns the tab into the chat; **Cancel** or closing the tab drops it. **Save as default** keeps the tab's provider, model, effort, fast mode and permissions as what every New chat tab starts with (Settings → Agent sessions → **New chat defaults** shows them and **Reset** forgets them; `somtus settings set new_chat_defaults '{"provider":"claude","model":"opus","mode":"auto_edit","fast":false}'` sets them from a shell). Without saved defaults a tab starts with the provider of the chat in front, its default model and Supervised. A chat is driven through the agent's structured interface (`codex app-server`, Claude's stream-json mode) by the chat host, a background process (`somtus chat serve`) that owns the agent process and the chat's event log. A tab only follows the chat, so closing it, reloading the app or restarting the host does not end the chat: a restored layout reopens its chat tabs by id and rebuilds each transcript from the start of the log, and while the host is away a tab shows **Reconnecting…** and subscribes again from the last event it saw. A tab whose chat was deleted says so and offers **Close**.

The tab is titled by the chat, with the agent's name or, with **Icons instead of labels** on, its mark (`>_` for Codex, a spark for Claude), and a working (●), waiting (◌) or done (✓) mark in front of the title, with the same hover hint that agents in terminals get. Open chats count among the agents in the status bar and in the project and worktree rows. Messages read as a conversation in one centered reading column: your messages as blocks across it, the agent's as Markdown (headings, lists, tables, quotes, links that open in the browser, code blocks with a **copy** button; **copy** on hover takes the whole message). Drag to select text within a paragraph, a table cell or a code block, double-click a word, triple-click the whole run, and Cmd+C copies it. The agent's thinking is folded under **Thinking…**. Commands, file changes (with an expandable diff, additions and removals tinted) and other tool calls are cards that open on click; command output preserves terminal colors and has independent Earlier, Newer, and Latest controls, with up to 200 lines per page. Copy page takes the displayed text; Copy retained includes the bounded retained history. Long Markdown plans have an expandable preview and explicit Save Markdown / Save to workspace actions; todo lists remain checklists. The list follows new text until you scroll up, and **↓ latest** brings you back.

Select part of an assistant answer and choose **Reply to selection** to add a source chip above the message box. Select text in a diff and choose **Comment on selected lines** to capture the file, exact old/new line ranges and selected patch lines. Each chip has its own editable quote and comment, Remove, and Go to source. References and comments recover with the draft and attachments. Changed or missing sources are marked explicitly; Re-anchor only succeeds when the original excerpt still has one unambiguous location. Send includes readable reference text for the provider. Selections spanning different answers or files are not combined into a misleading reference.

**Review files** opens a focused review with folders, Expand/Collapse all, file and hunk navigation, and comments attached to the reported patch revision. Back to chat restores the transcript's reading position. This surface reviews the agent's reported edits; it does not claim they are a net workspace diff. Large file lists are paged, each diff preview retains up to 400 lines, and Copy patch preserves the full reported patch.

Completed Mermaid blocks offer **Diagram / Source** and enlargement in the image viewer. Rendering uses the bundled Mermaid library locally, with no network requests; streaming, malformed, oversized, or unavailable diagrams retain their source. Other completed code blocks add **Reader** for an editable scratch copy and **Save…**, alongside Copy and Wrap. Shell snippets offer **Copy & open terminal…**: choose an existing local terminal, then paste the copied snippet yourself. The reader and save actions accept snippets up to 256 KiB and never alter the conversation or message draft.

Local links offer **File actions…** with relative/full path copy, Reveal in Finder, and the system's preferred application for that file type. The actions recheck the chat's registered project scope and the current regular file before proceeding. Images offer **Save displayed image…**, **Copy image**, and **Open original** when a local file or URL exists. Save and Copy use the displayed, potentially resized preview as PNG; a local original that has changed since preview must be reopened before it can launch. Exports use a chosen destination and require confirmation before replacing an existing file.

**Find** also searches collapsed Activity, tool details, and complete plan documents, opening the selected match. Command search covers the current retained page; navigate to Earlier or Newer to search another page.

**Turns** opens a bounded list of prompt and answer previews. Previous and next controls move through the conversation without searching for a particular word; choosing a preview jumps to that exchange. Navigating to a turn pauses live following so new output preserves your reading position. **Latest** resumes following new output. Each completed turn's Activity disclosure summarizes observed work, such as **Read 8 files · Changed 3 files · Ran 2 commands**. Repeated paths count once, search hits do not count as files read, and failures stay available when the disclosure is expanded, including attempts recovered before the final answer.

**Images in a chat.** An image the agent shows by path, by `file://` URL or in a Markdown image is a card that reads the file only when you open it (a click), at most 24 MiB, decoded and shrunk like the Files preview, with **Click to view** for the whole picture. A relative path is read from the folder the chat works in. A path or URL may name an image anywhere in the chat's own project: its root, its repositories, any of its worktrees, and its project orchestrator's folder (`RIWORK_HOME/orchestrators/projects/PROJECT_UUID`). The global orchestrator's chat may show images from every registered project and project orchestrator folder, and from its own (`RIWORK_HOME/orchestrator`). Every chat also shows the images you sent it: its own attachment snapshots in `RIWORK_HOME/chats/CHAT_UUID/attachments` (stored without an extension and shown only if they hold a supported image). Nothing else is read: not another project's folders (for a project's chat), not another chat's attachments or anything else under `RIWORK_HOME/chats`, not the rest of `RIWORK_HOME`, not a folder that is merely a parent of these, and not through a symbolic link or `..` out of them; the folders come from the projects and worktrees Somtus has registered, checked against the chat's own project and orchestrator identity, and change as soon as those do (an image shown from a folder that is gone is dropped). **Open in Files preview** under an image is offered only when Files can show it, that is when it is in the chat's own worktree of the window's project; an image from another worktree is viewed in the chat. Clicked file links in a chat still open in Files only within the chat's own worktree.

The message box is a card inset from the bottom of the tab. While it is empty in a wide tab it shares one row with **+** and its controls (the model, effort and Fast choices, the mic, **Interrupt** and Send); once you type or attach something it takes the card's whole width and the controls move to a row under it, and a narrow tab gives them a row of their own. **+** offers **Files and images…** and **Paste image**; files can also be pasted or dropped on the box. A notice, a request for approval and a question from the agent are cards in the same column, above the message box. Every theme lays a chat out this way; a theme chooses only its colors, fonts and how its cards and buttons are drawn.

Desktop drafts restore text and completed attachment snapshots after closing a tab or restarting. Saved attachments appear as **Checking** while their files are verified in the background; typing remains available, and Send and preview wait for verification. Missing or changed files remain visible as **Unavailable**, with **Check again** and Remove, and their saved references survive closing the tab. A check or retry in an older window cannot replace a newer window’s saved draft. Up to eight unresolved submissions per chat are retained separately; interrupted sends reopen as **Uncertain** for review and require an explicit resend. Attachments that had not finished staging show a recovery warning and must be attached again. Storage keeps the newest 64 chats for 30 days, with up to 256 KiB of text per draft or submission; oversized new draft text is kept only for the current run. Sending waits asynchronously for the recovery snapshot to reach disk; a storage failure reports that nothing was sent and keeps the editor. A graceful reload waits for queued drafts before starting the replacement app and cancels if saving fails.

Subagents and worker shells and chats also appear in a sticky **Workers** shelf directly above the message box. It shows two compact rows, with failures and workers waiting for input first; **All** expands the bounded list, and a row opens its output and actions. Each worker appears once even after follow-up assignments. The shelf stays visible while the transcript scrolls and leaves the message draft and focus intact. Status badges come from the provider or session inventory. With a reported Codex or Claude model, a visible chat can summarize changed output through a separate background request using that model and its account/billing choice: at most one batch every 30 seconds, with bounded input and one short sentence per worker. Unchanged output makes no further model calls. These summaries do not send messages into the parent conversation or alter worker state. Output snippets remain available while a summary is pending or unavailable; Muse currently uses these snippets. Hovering a generated summary identifies it as AI-generated.

When the agent asks to run a command, change files or use a tool, a bar above the message box names it and offers what the agent allows: **Allow**, **Allow for session**, **Deny**, **Stop**. With the message box empty, ⏎ allows, ⇧⏎ allows for the session and ⎋ denies; anything typed makes ⏎ a message again. Questions from the agent show their options as buttons beside a text field. In the message box ⏎ sends, also while a turn runs (the agent steers or queues it), ⇧⏎ starts a new line, and Cmd+. stops the turn. While a turn runs, **Interrupt** stands in the send button's place until something is typed; then **Send** is back, to steer. The toolbar sets the approval mode (Supervised, Auto-edit, Full, Plan), the model (any provider's, see below; a Claude agent that has not listed its models gets a name field with opus, sonnet and haiku) and the effort, compacts the context, and shows how much of the context window is in use. A Claude chat that runs on an Anthropic API key instead of a Claude subscription shows an **API key** badge there, as soon as its agent starts: Claude's own handshake says how it signed in (its `account`, of which the chat keeps only the key's source and the plan's name, never the email or organization). Its hover hint names the key's source and, for a key from `ANTHROPIC_API_KEY`, how to go back to the subscription. A Claude chat's message box has a billing switch beside the model, **Subscription** or **API key**, saved with the chat (`claude_billing` in its info, never a key): one click switches it, and the chat host restarts Claude on the same conversation, as it does for Muse's contributor mode (refused while a turn runs or waits, or Claude still starts; a restart that fails leaves the chat as it was, and says so). New chats start from the Settings default; a chat from before the switch follows the Settings default until it is switched. It shows what the running Claude says it bills once it has said (else the chat's choice), warns when that is not what the chat chose (a Claude started before the key was saved, or an `apiKeyHelper` of Claude's own), and with no key saved it opens Settings at the key field instead of switching. When a Claude chat on its subscription hits the five-hour or weekly usage limit, the limit's banner offers **Use API key** when a key is saved, which switches the chat and, if the limited turn had produced nothing yet, sends its message again, or **Enter API key**, which opens Settings at the key field. Closing the banner dismisses that limit until its reset; the banner goes once Claude bills an API key. Claude's own cost figure is shown as an estimate, never a bill. **⋯** has **Hand off…** (see **Handoff**), **Stop chat**, which ends the agent's process but keeps the chat (a stopped chat says it resumes when you send a message; a failed one offers **Retry**), and **Delete chat**.

Typing `/` at the start of the message box, or `@` at the start of a word, opens a list just above the box at the caret: the chat's slash commands, or the files and folders of the chat's folder. the list offers Somtus's own `/memo` in every chat and the provider commands that work through it, which today is Claude's `/compact` in Claude chats (Codex and Muse read a typed `/compact` as words; their **Compact** is the toolbar's). Commands are registered in one place, `COMMANDS` in `crates/riwork-engine/src/chat/suggest.rs`, which the phone's list reads too (`somtus chat suggestions CHAT_ID --json`, the connector's `chat.suggestions`). `@` lists the folder once in the background (breadth first, at most 5,000 entries, 50,000 looked at and 2 seconds, without what `.gitignore` leaves out, `.git` or symbolic links), keeps the listing for 30 seconds for every tab of that folder, and only filters it while you type. The highlighted row has a preview beside the list (above it in a narrow tab): what it is, what sending a command does, a file's size and first lines, and what accepting puts in. ↑ and ↓ move, ⏎ or ⇥ put the row in, ⎋ closes the list until that word is typed again, and a click puts a row in. Accepting only edits the draft: a command goes in as `/compact `, a file as its path relative to the chat's folder (a folder with `/`, a path with spaces in backticks), which the agent opens from where it runs; nothing is attached, and nothing is sent until you press ⏎ or Send. A `/` or `@` inside a word (`a/b`, `me@host`) opens nothing, nor does `/` after the first word. The list stands above the box, so it never covers Send, Stop or the pickers.

Typing `&` in the message box (at its start or after a space, anywhere in the message and as often as you like; `&` inside a word or a URL is just text) lists the models of every provider, so a message to an orchestrator in a Codex or Muse chat can name a Claude model and the other way round: the chat's own list (the one its model menu shows), then what each provider's saved chats listed (as `somtus chat models` reads them), each model once and each row naming its provider. They are the most used first, whatever the provider: how many of your own chats of that provider are set to each now (chats with a first message, scheduled ones included, not workers' or orchestrators'), counted from the chats' saved metadata and kept 30 seconds; ties and models you never used keep that order. Nothing new is recorded for it, so a deleted chat no longer counts and a chat that changed model counts only for its latest. Claude's `default` entry is not offered: it is the Claude CLI's own choice, not a model, so `&default` would name nothing. The chat's current model is marked, and typing filters the list by id or name. Accepting a model (⏎, ⇥ or a click) puts its mention in the message: `&` and the model's id as its provider takes it (`&opus`, `&gpt-6.1-sol`, never the display name), and a space after it unless one follows already, as `/` and `@` do; ⌘Z takes it back. A mention is only text, for telling an orchestrator which model you would like for the work you hand it (`&opus design the API, then &gpt-6.1-sol implement it`): nothing is switched or sent, the chat keeps its own model and effort, a running turn is not touched, and the orchestrator still decides (its skill reads a mention as your preference, and says so when it uses another model). The current model is put in like any other. The preview shows the mention, the model's provider, name and description and the count. With no list saved for any provider, no `&` list opens here. The phone's list comes with `somtus chat suggestions CHAT_ID --json` (`mention_models`), with the same counts.

**Another agent for the conversation.** The model picker lists the chat's own agent's models first, which change the model in place as before, and under **Continue with another agent** the other agents (Codex, Claude, Muse), each with its default and the models its saved chats reported (as `somtus chat models` reads them, with Muse's last answered list; no agent is asked for it); the search field narrows both, and ⏎ takes the first of this agent's models, else the first other agent's row (a search that names an agent, such as `claude`, is never set as this chat's model). Choosing another agent does not change the chat under the agent that had it: a small confirmation opens above the message box with what the new agent reads (**Transcript**, or **Summary** while this chat is idle and can be asked), an optional note, and **Hand off** / **Cancel** (⎋). **Hand off** is a handoff in place (see Handoff): a new chat of that agent and model, in the same project, worktree and folder, with the name this chat's tab shows (a chat named only for its agent, such as **Codex chat**, becomes **Claude chat**) and its permission mode, starts from the handoff document and takes this tab, at the same place, with the focus in its message box; the chat you were in stays as it is, a closed chat that **Open original** in the new chat's header reopens. An error shows in the confirmation and leaves the chat as it was. The agent pill and the options menu's **Agent** entry offer the same (**Continue with Claude…**). While a turn runs or waits for you, the confirmation says so and **Hand off** waits: end or stop the turn first, so that nothing the agent still does, or asks you, goes out of sight while another agent starts on the same files. `somtus chat command … switch`, which the phone still sends, keeps going on with another provider inside the same chat (`context.md` in the chat's folder, with a **Continued with Claude (opus)** line in the transcript).

**Lineage.** A chat made from another says so, and so does the chat it came from. The new chat's header has a row such as **Continued from Claude · opus — “Fix the build” · transcript** or **Forked from “Fix the build”**, with **Open original** (the chat or terminal it came from) and, for a handoff, **Handoff document**; its first message, the handoff's instructions with the document in it, shows folded as **Handoff context · 37 KB**, and opens and copies like any message. The chat it came from gets a quiet row at the point where the conversation went on, **Handed off to Codex · gpt-5** or **Forked here → “Fix the build (fork)”**, with **Open**. These are Somtus's own records: the new chat's `origin` in its `info.json`, and in the source's `events.jsonl` a completed `tool_call` item (server `somtus`, tool `lineage`) with `presentation.lineage`, written by the chat host and never sent to a provider or put in a handoff document. A reader from before it (an older desktop, the phone) shows that item as a plain tool row and skips the `origin` field; no new event type is written, since a log reader, a snapshot page and the phone stop at an event they do not know.

**Forking.** **Fork chat** in the chat's **⋯** menu starts a new chat that goes on from the whole conversation, with the same agent, model and permission mode, titled **TITLE (fork)** after the name the chat's tab shows, and opens it beside this one; **Fork with…** chooses another model of this agent (the current one is checked) or another agent, with its default model or one of its saved models. Every message you sent and every finished answer has a **⋯** with **Fork from here** and **Fork with…**: the fork has the conversation up to and including that point (a fork at a message of yours answers it afresh). A chat at work is forked at its last finished item. The fork uses the agent's own copy of its thread when that is exactly the point: Claude forks a whole session (`--resume SESSION --fork-session` under a session id of the fork's own), so it forks an idle chat whole; Codex forks a thread through any finished turn (`thread/fork` with `lastTurnId`), so it forks at the end of a turn, and at a message of yours by forking through the turn before and sending the message again. Anything else, a fork with another agent, a Muse chat, a chat that went on with another provider, or an agent whose own fork does not start, is made from a handoff document cut at that point, which the fork reads first. Until a natively forked chat has a conversation of its own, each start forks again rather than resuming a copy the agent may not have kept; one that went on with another provider since (`switch`) has a thread of its own and never forks again. A chat host from before forking makes a plain chat of such a request; the fork sees that, removes it and starts from the document instead. A natively forked chat's own log starts empty, so a handoff, a fork with another agent or a `switch` of it reads what it inherited first, the original's conversation up to the point it was forked (following forks of forks), then its own; when the original cannot be read, the document's caveat says what is missing. The original is not changed except for its **Forked here** row.
