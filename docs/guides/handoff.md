# Handing work to another agent

[Documentation index](../README.md) · [Project overview](../../README.md)

Repository paths and commands below are relative to the checkout root.

## Handoff

`somtus handoff` passes a conversation from a shell or a chat to a new shell or chat, on another model, effort, permission mode or Codex account, in the same project, worktree and directory. The source is neither stopped nor changed; only `--context summary` gives it anything, one message and the turn that answers it.

```sh
somtus handoff --to chat --provider codex --model gpt-5 --account Work
somtus handoff --to shell --provider claude --model opus --mode plan --note "Review the parser change only"
somtus handoff --from SHELL_OR_CHAT_ID --to chat --provider claude --context summary --json
somtus handoff --from CHAT_ID --to chat --provider codex --at ITEM_ID
somtus chat fork CHAT_ID
somtus chat fork CHAT_ID --at ITEM_ID --provider claude --model opus --json
```

`--to shell|chat` and `--provider codex|claude|grok|muse` are required (a chat is Codex, Claude or Muse; Grok runs in a terminal). `--model` and `--effort` take their value as it is, also with `=`, like `chat new`. `--mode supervised|auto-edit|full|plan` is how much the new agent may do without asking: for a chat it is the chat's mode (supervised by default); for a shell, `auto-edit` and `plan` pass the CLI's own flags for a shell (Codex `--sandbox workspace-write` or `read-only` with `--ask-for-approval on-request`; Claude and Grok `--permission-mode acceptEdits` or `plan`; a Muse terminal has no such modes, so `plan` passes `--disable-write` and `auto-edit` keeps its supervised default; for a Muse chat the mode is the chat's approval mode, mapped to Muse's own `promptUnmatched`/`onRequest`/`allowAll`, with Plan starting the conversation under Muse's Read only profile), `full` is the permission bypass of the unrestricted launches, and `supervised`, like leaving `--mode` out, keeps the CLI's usual permissions. The model flag is Codex `-m`, Claude `--model`, Grok `-m`, Muse `--model`; the effort is Codex `-c model_reasoning_effort=…`, Claude `--effort`, Grok and Muse `--reasoning-effort`. A terminal target is started as **New Tab** starts it, with the same Cua.ai Driver wiring; a chat is made by the chat host.

**The source.** `--from` takes a shell's or a chat's id, or a unique prefix of at least eight characters of either (a shell's id needs no more than that here, unlike other commands). Without it the command hands off the session it runs in: a terminal's `RIWORK_SHELL_ID`, a chat agent's `RIWORK_CHAT_ID`. So an agent that is told to hand itself over only runs the command; one that has both variables (a terminal started by an agent in a chat) is asked to pass `--from`. An orchestrator's conversation is not handed off. The target is started in the source's project, worktree and directory (a plain shell's current directory); a chat without a project can only be handed to a chat, which is refused up front for a shell.

**The account.** `--account` is a Codex account's label or id, resolved against the saved accounts the way a launch resolves its selection (see Codex accounts under Settings): an id, or a label, email or workspace name in any case (`Work` for `me@example.com · Work`), or a part of a label that only one account has; a name that fits two accounts is an error that lists them, and one that no account has lists the known ones. An account that is saved but unavailable (Orca removed, its home missing) is refused by name, never swapped for another. `System default` is an account too. Without `--account` the project's own choice applies, as in a new tab. Claude, Grok and Muse have no Somtus-managed accounts, so `--account` with them is an error saying that only the system login exists.

**What the new agent reads.** The handoff is a Markdown document written to `RIWORK_HOME/handoffs/HANDOFF_ID.md` (mode 600, in a folder made mode 700; never in the repository, and kept until you delete it). Its heading names the source (agent, chat title or terminal, short id), its model when known, the project and worktree, the directory, the time, what the document holds, any caveat, and the `--note`. A document is your conversation as it was, secrets you typed or a command printed included, and the new agent's provider receives it: it is not redacted. Below the heading, user and agent messages are in full, and the rest is short: a command is its first line with the first and last six lines of its output and its exit status, edited files are listed by name, other tools are their name and a few words about what they were asked, and plans and todo lists are checklists. The agent's hidden thinking and the bulk of tool results are left out. A document is at most 200 KB: when the conversation is longer, the newest items are kept as they are, the oldest are left out under a marker that says how many, and the first request stays at the top; one message of more than 50 KB keeps its start and its end.

The new agent's first message is "You are taking over a conversation from SOURCE. Read the handoff at PATH and continue from where it left off." followed by the note. A chat whose document is under 48 KB gets the document in the message instead of the path; a terminal always gets the path, since a command line is limited. A Codex or Muse terminal receives the message as its startup prompt followed by the Cua.ai guidance a normal start carries; Claude and Grok receive it as their prompt.

**How each source is read.**
- A **chat** is its `events.jsonl`, folded with the same `Transcript` a chat tab draws, so it works while the host is not running.
- A **Codex terminal** is the rollout its pane is bound to (the binding Somtus keeps for activity, or the id of a `codex resume`), read from the newest 64 MB of it; its `item_completed` items are used, and the turns of a rollout from a version before them (a rollout can begin in one and go on in another) are read from what was sent to the model. An edit or command that was declined, or an edit that failed, is shown as such and not as a changed file.
- A **Claude terminal** is the session transcript `~/.claude/projects/FOLDER/SESSION.jsonl` (or under `CLAUDE_CONFIG_DIR`), found through the session id Claude's hooks report; a subagent's own conversation and notes the CLI writes for itself are left out.
- A **plain shell, Grok or Muse** has no conversation file, so it is the tmux scrollback (the newest 5,000 lines, as `shell history` reads them), which is the rendered screen and not a transcript. A Codex or Claude terminal whose conversation file is not known yet (Somtus learns it after the first turn) falls back to this too, and the document's caveat says so.

**`--context transcript|summary`.** `transcript` (the default) works for any source. `summary` is for a live Codex or Claude, a chat or a terminal, that is idle: Somtus sends it a message asking it to write a concise handoff summary (goal, state, decisions, open tasks, files touched, next steps) to a file under `handoffs/`, and waits up to five minutes for the file and for the end of that turn. A terminal gets the message the way a schedule does: the same bracketed paste and one Return under the shell's input lock, and only while the screen shows the agent's empty prompt; a chat gets a `send`. The document is then the heading and that summary. An agent that is working, waiting, stopped or not running is refused at once, with nothing sent; this includes the agent that runs the command itself, which is busy running it (it uses the transcript, or you run the handoff from outside). An agent that was asked but writes no file in time, ends its turn without one, or goes away is not an error: the handoff holds the transcript, the document's caveat says that the summary did not come and why, `--json` has it as `fallback`, and the text output says so. An agent that must ask before writing outside the project (a supervised chat, a sandboxed Codex) waits for your approval in its tab, within the same five minutes; in the app the dialog can be hidden meanwhile (below), and from a script you answer in the tab as the command waits.

**`--at ITEM_ID`** cuts a chat's conversation at one of its items (an id from `somtus chat events` or `chat snapshot`), that item included: the document holds the conversation up to there. A terminal is always handed off whole, and a summary is of the whole conversation, so both refuse `--at`.

**Both sides say so.** A chat that a handoff starts keeps where it came from (`origin` in its info: the source, its agent and model, the cut, the handoff id and document, transcript or summary), and when the source is a chat it gets a marker in its own log naming the new chat (see Lineage under Chat tabs). A chat host from before it refuses the marker and the handoff stands without it.

**`somtus chat fork CHAT_ID`** starts a new chat that goes on from a point of a chat's conversation (see Forking under Chat tabs): the whole of it, or with `--at ITEM_ID` up to and including that item; a chat at work is forked at its last finished item. It keeps the chat's agent, model, effort, permissions and Codex account unless `--provider`, `--model`, `--effort` or `--mode` say otherwise, and is titled `TITLE (fork)`, after the name the chat's tab shows, unless `--title` names it. The agent's own fork is used when it reproduces the point exactly (Claude `--fork-session` for an idle chat whole, Codex `thread/fork` through a finished turn), else a handoff document cut there. The text output names the fork and what it got; `--json` prints `{"id","source_id","title","provider","model","context":"native"|"transcript","at","document"}` and `fallback` when the agent's own fork was tried and did not start.

**Output.** The text output says which agent and kind were started and where the document is. `--json` prints `{"handoff_id","document","target":{"kind":"shell"|"chat","id"},"context":"transcript"|"summary"}` and `fallback` when a summary was replaced. A chat whose agent could not start is kept as failed and the command fails, naming the chat and the document so the message can be sent again. Progress ("Writing summary…") goes to stderr.

**Telling an agent to do it.** Say it the way you would to a person: "hand this over to a Codex chat with gpt-5 on my Work account". The agent runs `somtus handoff --to chat --provider codex --model gpt-5 --account Work`; a sandboxed agent has to ask you first, since the command writes under `RIWORK_HOME` and reaches Somtus's sockets. A new shell is a tab in a window that has the project open, as any shell made from the CLI is; a new chat is kept by the chat host and listed by `somtus chat list`. The embedded orchestrator skill and the `riwork-workspaces` skill mention the command.

**In the app.** **Hand off…** in a Codex, Claude, Grok or Muse tab's **…** menu (its **Tab** section) and in a chat tab's **⋯** menu opens a **Hand off** tab: **Open it as a** Shell or Chat, the **Agent**, the **Model** (a free text, with a few suggestions), the **Codex account** (the project's own, the system's, or a saved one, from the list Settings keeps) when the agent is Codex, **What it reads** (Transcript or Summary) when the source can be asked, and a **Note**. The work runs off the UI thread while the tab says what it is doing ("Writing summary…"); an error, such as a busy agent being asked for a summary, shows in the tab so the choice can be changed. Because a summary can take minutes, and the agent asked may be waiting for your approval in its own tab, you can switch away, or close the tab with **Continue in background**, and the work finishes: a notice follows its steps. When it is done a new chat takes the Hand off tab's place (a shell opens in the pane new tabs go to); if a summary did not come, a notice says the transcript was used. A project on another Mac has no hand off; a notice says so. In a chat, the model picker's **Continue with another agent** hands off in place instead: the new chat takes the chat's own tab (see Another agent for the conversation under Chat tabs), and **Fork chat** and **Fork from here** fork it (see Forking).
