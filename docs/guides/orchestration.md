# Orchestrators

[Documentation index](../README.md) · [Project overview](../../README.md)

Repository paths and commands below are relative to the checkout root.

## Orchestrator

The global orchestrator coordinates objectives and dependencies across projects. Each project's orchestrator manages its tasks, repositories, worktrees, and Codex, Claude, Muse, or Grok workers. Their skill (`riwork-orchestrator`, which both are given when they start and which **LOAD SKILL** brings up to date) routes work by model: orchestration, delegation and synthesis to Muse Wonder Full, the hardest reasoning, independent review and design to Claude Opus 5.5, and implementation, tests and long runs to Codex GPT-6.1-Sol, the fallback, unless you, Settings or a project chose otherwise; a fallback is reported, never silent. It also has the global orchestrator answer "what is going on" from Somtus's records first and then ask the project orchestrators that exist for a short brief (working, waiting, blocked, recently done, next step, needs you) through `somtus orchestrator send` and `output`, marking missing or stale answers; a brief creates no work. The skill opens with **Hard boundaries** that bind both: an orchestrator never tests in its own or any live orchestrator window (no clicks, keys, find bar, dialogs, layout, focus or draft changes), never live-tests closing, killing, nuking, deleting, updating or restarting shells, chats, the chat host, provider backends or orchestrators against real project state (opening such a dialog and cancelling counts), verifies only by reading evidence from isolated runs (otherwise it reports the result `unverified` and asks you to look), restarts or updates nothing that can interrupt sessions without your approval in the same turn, and requires every assignment and worker report to say where verification ran. Only your explicit approval in the same turn, naming the target, lifts one. They have separate persistent shells and ordinary workspace tabs; project orchestrators belong to their project and have no worktree, while the global orchestrator has neither project nor worktree ownership.

Press Cmd+Shift+O for the global orchestrator, or choose **Chat** in the menu that **G·ORCH** opens: it opens in the global window (see **Global window** below), never as a project window's tab. Click **P·ORCH** or press Cmd+Alt+O for the current project's orchestrator tab. Both are also under **New Tab** in a pane's **…** actions menu. Opening the project scope selects its existing tab in this window, or attaches its persistent session to the active pane. Project orchestrator tabs drag, split, close, and restore like shell tabs. Closing a tab detaches its terminal and preserves the session.

**Global window.** The global dashboard and the global chat share one window of their own, titled **Somtus · Global**, with a **Dashboard** and a **Chat** view switched at its top. It belongs to no project: opening it registers, selects or switches no project, and it writes nothing into a project's layout, tabs or chat requests, changes no window's project, worktree, task, folder, locks or remote selection, and claims no project's terminal. There is at most one, and every way in raises it on the view asked for: the global item of the status bar (**G·ORCH** in the colorful themes; a globe, with **Global** beside it when **Icons instead of labels** is off, in Native) opens a small menu above it with two rows (click it again, click elsewhere or press Escape to close it), **Dashboard** (Cmd+Option+G, also **View → Global Dashboard** and a pane's **…** → Views) and **Chat** (Cmd+Shift+O, also **View → Global Chat** and a pane's **…** → New Tab → Global orchestrator); asking again from any project window brings the same window forward. The shortcuts and the **View** items work from any window, the global one included; in a window that shows a project on another Mac they too open this Mac's global window (that Mac's global orchestrator is not opened from there). Each menu row says what it shows or what a click does: the dashboard's row sums up the work in a line, and the chat row names the orchestrator there is (**Open global chat**, with its agent and state), a global orchestrator that runs in a terminal (**Open terminal orchestrator**: it is opened as it is, never converted or ended), or, when there is none, what a click starts as **Orchestrator runs as** says (**Start global chat** or **Start global orchestrator**). Opening the menu, the window or its dashboard, drawing them and refreshing them start no agent, chat or chat host.

The **Chat** view shows the global orchestrator there is: its chat, the same chat with its transcript, draft and provider, permission and model controls (all kept with the chat, by its id), or, when the global orchestrator runs in a terminal, that terminal, labeled **Terminal orchestrator**, kept as it is (a chat takes over only after you end it). Showing the view connects to the chat host as any chat tab does (starting the host process if it is not running), but never starts an agent or makes a chat. When there is no global orchestrator, the view says so and offers **Start global chat** or **Start global orchestrator**; that button, the menu's Chat row, Cmd+Shift+O, **View → Global Chat** and the dashboard's chat control are the explicit requests that make one, as Settings say, when there is none. Closing the window (or Cmd+W in it) drops only the view: the chat and its agent, or the terminal's session, run on, and the window shows them again when it is opened. The window's image cards read what the global chat's may (see **Images in a chat** below); it has no Files of its own, so **Open in Files preview** and chat file links are a project window's. Cmd+Shift+N, Cmd+, and Cmd+Shift+S in the global window open a project window, Settings and Automations in the frontmost project window (else the active project's).

What the window last showed (its view, the dashboard's project filter and order, and its size) is kept in its own file, `RIWORK_HOME/global-window.json`, and opening the window again starts there; a missing or unreadable file is the dashboard. The file keeps `show_quiet` beside the filter, true exactly when the filter is **All**, so an older build still lists what it listed; a file from before the filters, which has only `show_quiet`, opens on **All** when it was true and **Active** otherwise, and a filter or order this build does not know reads as the default. An app reload (`somtus reload`, `somtus update`) restores it as itself, with its frame and view: its entry in the runtime registry says `"kind": "global"` and carries its own `global` state, names no project and no layout, and is the only one of its kind. Project windows are recorded exactly as before, and a snapshot written by an older build restores as project windows only. An older build that is handed a global window cannot open it (its `path` is the folder `RIWORK_HOME/global-window`, which never exists), so that reload fails and leaves the running app as it is rather than registering a project or opening the active project in its place; close the global window before reloading into an older build. A plain launch opens the active project's window as before, without the global window.

**Older layouts.** Builds before the global window opened the dashboard as a project window's panel tab and the global orchestrator as a project window's chat or terminal tab, saved with that project's layout. A project window now leaves those tabs out when it loads a layout (from `layouts.json` or a reload), says once that they moved (**View › Global Dashboard** or **Global Chat**), and saves its layout without them. Nothing is deleted: the chat, its history and draft, and the terminal's session stay as they are and open in the global window. Nothing new puts them into a project window: the dashboard panel, the global orchestrator's chat or terminal, and any route to them (a dashboard row, a reopened chat, a notification) go to the global window. A layout written by this build that an older build reads simply has no dashboard tab.

The **Dashboard** view shows every local project on this Mac at once, from what the global window samples every two seconds, as project windows do. Its toolbar holds the search, the figures in a line (agents working and their subagents, what needs you, live terminals and chats, tasks done of all with a progress bar and what is open, and the global chat's state with its one control), how fresh they are (**Live**; **Last read … ago** once a read is more than 30 seconds old; or why the sessions could not be read, keeping the last figures), and **Refresh**. Before the first read nothing is counted or listed, and it says what it is reading. **Projects** is a table. A row has a mark for the project's most pressing state, its name, group and how many things need you, its folder and number of worktrees; **Activity** (its agents working, waiting, done or of unknown state, then its live sessions: terminals and, once the chats were read, chats); **Tasks** (done of all beside a progress bar, then in progress and to do, on one line when the column has room, else one count to a line, never cut short); **Orchestrator** (the project orchestrator, chat or terminal, and its state); **Last active** (the latest time Somtus recorded something in it: a task changed, one of its live agents began what it is doing, or one of its chats' logs grew as far as that was read; **—** when nothing recorded a time); and **Tasks** and **Sessions** buttons that open those panels in the project's window. Filters list the **Active** projects (a live session or chat, or an open task; the default), those that need you (**Needs you**), have an agent **Working**, have tasks **In progress**, or **All**, each with its count; the order is **Priority** (what needs you, then what works, what runs, tasks in progress and open tasks), **Recent**, **Tasks**, **Sessions** or **Name**, each keeping the busiest first among equals. The search (Cmd+F; every word must appear somewhere, in any case) narrows every list: projects by name, group or folder, the attention, work and finished rows by what they say, tasks by title, project or branch, and automations by title or project. A filter that hides projects the search found says so and offers **Show all**. Beside the table, rails list **Needs you** (agents and chats waiting for an answer or an approval, chats whose agent failed within the last three days, orchestrators' failed chats always, and automations whose last run failed, was missed or is uncertain, unless paused), **Working now** with how long and how many subagents, **Finished in the last hour**, **Tasks in progress** across projects with when each changed, and **Automations**, each with its project, its next run or that it is paused, and how its last run went. The rails scroll on their own, so a long project list never pushes them out of sight. A wide window shows two rails, one for activity and one for tasks and automations; an ordinary one shows one; a compact one shows **Projects**, **Activity** or **Tasks** one at a time, chosen above them. In the colorful themes at the default text size, two rails start at about 1,450 points wide and one at about 1,100; Native at its default size draws text at 13 pt instead of 11, so everything needs 13/11 as much room: two rails from about 1,710 points (a 1,900-point window has both), one from about 1,295, and compact below that. A larger text size raises these widths alike. Columns that do not fit move into the project's own lines rather than being cut off: the orchestrator first, then the activity. The filter and the order are kept with the window's state (see below); the search is not. Searching, filtering, sorting, switching regions and refreshing change no project and start no agent, chat or chat host. Every row opens exactly what it names in that project's window: a window that shows the project is brought forward (else a window is opened on it, found by its id), and there it shows a session's tab, a chat as Sessions opens it, the project orchestrator's tab, a task selected in Tasks, the project, or Automations (an app automation's in the frontmost project window). No window changes project for it and the store's active project stays what it is; the global window stays the global window. A row of the global orchestrator switches the global window to Chat. A row whose session, chat, task or project is gone says so. The lists say when chats or automations are still being read or cannot be; nothing is shown as zero that was not counted.

New default orchestrators start the official `codex` CLI, install the embedded **riwork-orchestrator** skill in their context folder, and receive their scope, project UUID, and project root as appropriate, with their scope's delegation policy (see **Delegation** in [Settings](settings.md#settings)) and the skill's Hard boundaries in brief, which every LOAD SKILL message restates too. The startup message names the installed `SKILL.md` for Codex to read instead of carrying the skill text, which keeps the launch command far below tmux's limit of about 16 KB. Global context is `RIWORK_HOME/orchestrator`; project contexts are `RIWORK_HOME/orchestrators/projects/PROJECT_UUID`. Each waits for an objective. The skill covers global coordination, repository selection, task assignment, bounded delegation, progress inspection, and completion checks. Existing sessions show **LOAD SKILL** for a one-time upgrade that preserves their conversation, and again when their scope's delegation policy changes; it pastes the complete skill, with the policy as it resolves now, into the running Codex. Custom commands do not receive the skill automatically. Loading the skill does not schedule work.

Default project orchestrators launch Codex in unrestricted mode, with approval prompts and sandboxing disabled. This mode is saved with the session and preserved when its conversation is reloaded. Existing project orchestrators keep their startup mode; close and recreate them to use the new default. Global orchestrators retain the selected Codex account's permission and approval settings. Custom commands run as supplied. On a global orchestrator's first launch, Codex may ask you to trust its context folder; answer that prompt in the terminal before the startup skill loads.

**Terminal or chat.** An orchestrator runs as a Codex in a terminal tab, as above, or as a chat: a Codex, Claude or Muse conversation of the [chat host](chat.md#chat-host), in a chat tab, as was chosen when it was created: by the project's **Project Settings → Orchestrator** for its own orchestrator, else by **Orchestrator runs as** in Settings, whose default, Automatic, starts a Muse chat on Wonder Full or, when Muse cannot start, a Codex chat on GPT-6.1-Sol (see [Settings](settings.md#settings)). Everything that addresses an orchestrator handles both: P·ORCH, Cmd+Alt+O and the project **New Tab** entry open the project's terminal tab or its chat tab (an open tab is reused by the main-pane rules above, a new one opens where new tabs open), G·ORCH's Chat, Cmd+Shift+O and the global **New Tab** entry show the global one's terminal or chat in the global window, and the CLI, the MCP tools, schedules and the phone follow whichever exists. A scope has at most one orchestrator across both modes: creating one when the scope already has a terminal or a chat orchestrator returns that one, and the chat host itself refuses a second chat for a scope.

A chat orchestrator is an ordinary chat that the host knows by an `orchestrator` field in its `info.json` (`{"scope":"global"}` or `{"scope":"project","project_id":"…"}`; chats written before the field have none). It works in the same folder as a terminal orchestrator (`RIWORK_HOME/orchestrator`, `RIWORK_HOME/orchestrators/projects/PROJECT_UUID`) with the same **riwork-orchestrator** skill installed there, and its first message is the startup message a terminal orchestrator receives (its scope, project UUID and root, and the path of the installed `SKILL.md` to read), built by the same code. The agent's environment names its scope as a terminal orchestrator's does (`RIWORK_ORCHESTRATOR_SCOPE`, `RIWORK_PROJECT_ID`). The Codex account and the Cua.ai Driver connection are the ones every chat gets. **A project orchestrator never asks before it acts** (approval mode Full, as its terminal launches with approvals and sandbox off). **The global orchestrator is Supervised**: it asks before running commands and editing files, and a turn waits in the chat tab (and shows as waiting in `status` and the G·ORCH item) until you answer; a schedule defers meanwhile. A project orchestrator's tab is titled **P·ORCH · PROJECT** (the global one is the global window's Chat view), and G·ORCH and P·ORCH in the status bar are marked `●` while its agent works, `◌` while it waits for you and `✓` once it is done, as chat tabs are. A chat orchestrator whose skill is not the one this build ships, or whose scope's delegation policy changed since it was told, shows the same **Load skill** bar as a terminal one; it sends the whole skill and the policy to the chat as a message, once, when the chat is idle. Closing the tab (or the global window) leaves the chat; `somtus orchestrator close` ends its agent **and deletes the chat and its history**, as closing a terminal orchestrator ends its session, and the next one is created as Settings then says. A chat orchestrator whose agent cannot start, or whose startup message cannot be sent or recorded, is not kept: creation reports the reason and leaves nothing behind. Creating a scope's orchestrator takes turns across the desktop, the CLI and the MCP server, in either mode (a lock file per scope under `RIWORK_HOME/orchestrators`): a second request waits until the first one's orchestrator has started and been told what it is, and then gets that one.

**The id.** A chat orchestrator's id is its chat's id, one UUID everywhere: it is the `id` of its entry in `somtus orchestrator list --json` (and `chat_id` repeats it, for readers that look for the chat), what `somtus chat events`/`chat command` and the phone's `chat.*` methods take, and what `somtus schedule create --shell` takes.

```sh
somtus orchestrator create --json
somtus orchestrator create --project PROJECT_ID --json
somtus orchestrator list --json
somtus orchestrator status --project PROJECT_ID --json
somtus orchestrator output --project PROJECT_ID --lines 120 --json
somtus orchestrator send --project PROJECT_ID "Implement the requested project objective"
somtus orchestrator load-skill --project PROJECT_ID
```

All orchestrator operations use the global scope when `--project` is omitted. `somtus orchestrator close` ends only the global session; `somtus orchestrator close --project PROJECT_ID` ends only that project's session. Worker shell lists exclude orchestrators. MCP orchestrator status/output tools accept an optional project selector.

For a chat orchestrator the same commands mean the following. `create --json` adds `"created"` (false when the orchestrator was there already) to the entry. `list --json` and `status --json` give every entry `"mode"`: `"terminal"` or `"chat"`; a chat's entry has the usual fields (`id`, `project_id`, `worktree_id` null, `kind`, `cwd`, `command` null, `harness`, `unrestricted`, `alive`, `created_at_unix`, `orchestrator_skill_loaded`, `activity`, `last_activity_unix`) and `chat_id`, `provider` (`codex` or `claude`), `title` and `state` (`starting`, `idle`, `running`, `waiting`, `stopped` or `failed`, with `state_message` when failed). `alive` stays true for as long as the chat exists, because a message resumes a stopped or failed one, and `activity` is `working`, `waiting`, `done`, `unknown` (starting, stopped) or `exited` (failed). `send` is a chat message (a stopped chat is resumed first). `output --lines N` is the conversation as plain text, the last N lines (200 by default): your and the agent's messages whole (`user: …`, `agent: …`), one line for each command, edit, tool call, search and plan (`[command] ls -la (exit 0)`), and what the chat waits for last (`[waiting for approval] …`). `load-skill` sends the whole skill as a message, once, to an idle or stopped chat. `cwd` prints its folder. `metrics` and `attach` are for terminals and say so. Looking (`list`, `status`, `output`) never starts the chat host: while it is not running the saved chats are read, and every chat reads as stopped.
