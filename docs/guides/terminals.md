# Persistent terminals

[Documentation index](../README.md) · [Project overview](../../README.md)

Repository paths and commands below are relative to the checkout root.

## Persistent shells

The Shells tab includes **Nuke all shells** beside its session controls. It asks for confirmation before exiting the project's live shells, including detached and worker shells; orchestrator shells and chats stay open.

Somtus creates `~/Documents/riwork` at app startup if needed. Use **+ PROJECT** (a box-with-plus icon when **Icons instead of labels** is on) in Projects or Cmd+N to create a project. Enter a project name to create `~/Documents/riwork/NAME`; the folder field updates automatically. Default names cannot start with a dot. Editing the folder or using Browse selects an explicit location, where the name is optional; a typed folder must be an absolute path (`/…` or `~/…`), and the form shows the resolved folder. If creation fails, folders it made that are still empty are removed. `somtus project create --name NAME` also uses this default parent. Explicit CLI paths retain their usual meaning. Plain `project create` registers a folder it finds at that path; `--exclusive` never does: it fails with `already_exists: …` if the folder is there (a file or link counts) or a project has that root or that name (ignoring case), and a failure after it made the folder takes the folder back. The phone's `project.create` always runs it that way. Projects support a single Git repository, a folder containing several repositories, and plain folders. Creation offers **Initialize Git** checked by default when no repository is found. Uncheck it to keep a plain folder. Existing repositories are reused; a wrapper folder is never initialized around them. `project add` only registers a folder. For projects with several repositories, worktree creation requires choosing a repository with `--repo`; a new repository needs an initial commit before Git can create worktrees.

```sh
somtus shell create --worktree WORKTREE_ID
somtus shell create --worktree WORKTREE_ID --harness codex
somtus shell create --worktree WORKTREE_ID --harness claude
somtus shell create --worktree WORKTREE_ID --harness grok
somtus shell create --harness codex --unrestricted
somtus shell create --harness claude --as-settings
somtus shell list --all --json
somtus shell output SHELL_UUID --lines 100
somtus shell history SHELL_UUID --end 0 --lines 200
somtus shell cwd SHELL_UUID
somtus shell metrics SHELL_UUID
somtus shell send SHELL_UUID "pwd"
somtus shell keys SHELL_UUID -- t:'git status' k:Enter
somtus shell paste SHELL_UUID -- /absolute/path/to/screenshot.png
somtus shell attach SHELL_UUID
somtus shell attach SHELL_UUID --exec [--ignore-size] [--read-only]
```

An agent from `shell create --harness` asks before it acts unless you add `--unrestricted`, which passes the agent's permission bypass flag, so a script keeps its meaning. `--as-settings` does what the New tab menu does instead: unrestricted while **Agent terminals run unrestricted** is on in Settings, asking while it is off. The phone's `shell.create` uses it when it asks for the desktop's setting (`"as_settings": true`).

`shell attach` prints the tmux command a terminal runs to show the shell; with `--exec` it runs it instead, replacing the `somtus` process with the tmux client (`--ignore-size` keeps this display from resizing the shell's window, `--read-only` makes the client watch only). A remote desktop's terminal stream uses it (`remote/README.md`). In a terminal that says `xterm-ghostty` it announces that when the app bundle (or the caller's `TERMINFO`) has Ghostty's terminfo, otherwise `xterm-256color`.

Every shell has a UUID. `shell output` captures tmux scrollback and the current pane as text, including when the GPUI app is closed. Full screen terminal programs may show only their current rendered screen rather than a complete semantic transcript. Closing a tab or window detaches its shell; `somtus shell close UUID` ends it.

Mouse-wheel and trackpad scrolling use tmux's scrollback. Codex, Grok, and Claude Code sessions run inline on the main screen by default (see **Keep agent transcripts in scrollback** under Settings), so their whole conversation is in that scrollback and the wheel scrolls it. Scrolling up enters copy mode; scroll back to the bottom or press Escape to return to the live terminal. New sessions enable mouse reporting, and existing sessions are upgraded when reattached. A new session keeps up to 100,000 lines of scrollback; tmux applies that limit only to panes created after it is set, so sessions started by older builds keep tmux's default of 2,000 lines.

**Links in terminals.** Point at a URL or a file name in a shell, Codex, Claude, Grok, orchestrator or editor tab and a thin line in the theme's accent color underlines all of it, on every row it was wrapped over; hold ⌘ and the pointer becomes a hand, and ⌘-click opens it. Somtus finds the link in the text tmux shows for that tab, so it sees what you see: the live screen, the part of the scrollback you have scrolled to, or the screen of a full-screen program. A link the terminal wrapped over several rows is put back together, and a click needs nothing from Ghostty's own matcher, which does not know the folder the shell is in. Only the terminal under the pointer is read, at most every half second and off the UI thread, and none once the pointer has left the terminals; a click without ⌘ goes to the terminal as before. A URL (`http`, `https` or `mailto`) opens in the default browser or mail app, without the full stop or bracket of the sentence it sits in. A file name is `src/main.rs`, `./x`, `../x`, `~/x` or an absolute path, with an optional position (`:120`, `:120:5`, `:120-135`, `#L120`), inside backticks, quotes or brackets (a name with spaces needs quotes), a pytest id (`tests/test_a.py::test_b`), a name in a Python traceback (`File "a.py", line 12`), or a `file://` URL. It is looked for in the folder the tab's shell is in and then in the window's project or worktree root, and it is a link only if it exists (the `a/` and `b/` that `git diff` puts before a name are dropped when no such folder exists). A file inside the window's project or worktree is selected in Files and shown in Preview, scrolled to the line with that line marked. The Preview opens even with **Open the preview when a file is selected** off, a dot file turns on **Hidden** so that it has a row to select, and a folder is shown in Files. The Preview and Files go beside your work, never over the terminal you clicked in, and that terminal keeps the keys: with the tree on screen in another pane the Preview goes beside it, as when you choose a file there; with none, the roomiest unlocked pane that is wide (620 px) or tall (700 px) enough, the terminal's own included, is split and the panel takes the new pane (the terminal keeps 60% and its selected tab); when nothing can be split, the panel is a tab in another pane, selected there only if that pane shows no terminal, and a notice says where it waits. With a main pane (see **Main pane** above), the Preview and Files are tabs of it instead (a tab that would cover the clicked terminal waits unselected beside it). A message in Preview says when it cannot show the line (a picture, a PDF, a line past the end). **⌘⇧-click** opens a file of the project in the Vim editor tab at that line, and takes an editor tab that is already open on it to the line. Anything outside the project opens with its default app if it is a document, a picture, sound or video, data, or a source file other than a script, and a folder opens in Finder; anything else (executables, scripts, applications, installers and disk images, files with no known type) is shown in Finder, never opened by Somtus. The hyperlinks (OSC 8) that Claude Code and Codex print for Markdown links and files go where they point, whatever words they show: Somtus reads the target from tmux and opens it itself (an `http`, `https` or `mailto` address, or a `file:` target on this Mac), because Ghostty as embedded here does not open OSC 8 targets at all (words that are themselves an address win over a target on another site). A click that is not on a link goes to the terminal as before, which leaves Ghostty's own matcher free to `open` text that Somtus did not take for a link. The hand appears as the pointer moves with ⌘ held, and when ⌘ is pressed while the pointer rests over the terminal that has the keys. A tab for another Mac's shell is left to Ghostty, which opens URLs there (its tmux is not this Mac's, so files are not looked up). Somtus also tells its tmux server to pass OSC 8 hyperlinks on to the terminal (`terminal-features` `xterm*:hyperlinks`, set whenever a terminal attaches), which tmux drops otherwise, so that Ghostty receives them; a terminal that is already open picks it up the next time it attaches, for instance after **Reload**.

**Files dropped on a terminal.** Drag files or folders from Finder (a screenshot from the desktop, say) onto a shell, Codex, Claude, Grok, orchestrator or editor tab and their absolute paths are typed into it as Ghostty does it: a backslash before spaces and the other characters a shell reads specially (``\ ()[]{}<>"'`!#$&;|*?`` and tab), several paths separated by one space, nothing after the last and no Return. The text goes in as a paste (tmux `paste-buffer -p` into the tab's shell), bracketed when the program asked for bracketed paste, so Claude Code, Codex and Grok see pasted paths and attach dropped pictures (png, jpeg, gif, webp) as `[Image #1]`; other files stay paths. Claude Code and Grok take several paths in one paste. Codex attaches a paste only when it is a single picture's path, so a Codex tab gets one paste per path, with a space after each path that is not a picture. Which program is in front is read from the pane (`pane_current_command`, then the processes in the terminal's foreground, as for Codex installed by npm, which runs as `node`); an agent tab Somtus started counts as that agent until a shell is back in front. A thin outline in the theme's accent color marks the terminal under the drag; the drop selects that pane and gives its terminal the keys, and a terminal in copy mode leaves it first. A tab for another Mac's shell takes no drop, since a path on this Mac means nothing there, and text dragged from another app is not taken: the window accepts only files.

**Copied files and pictures.** ⌘V in a local terminal pastes text through Ghostty as before. When the pasteboard holds files instead (⌘C on files in Finder), Somtus pastes their paths exactly as a drop would, for shells and agents alike; Ghostty alone would paste only the file's name. A picture copied with no file and no text (a screenshot taken with ⌃⇧⌘4, or Copy Image) turns ⌘V into Ctrl+V for Claude Code, Codex and Grok, the key with which each reads a picture from the pasteboard itself and attaches it; a shell gets nothing, as in Ghostty. Ctrl+V itself always reaches the program unchanged (neither Somtus, Ghostty nor Somtus's tmux binds it), so it works as each CLI documents: Claude Code attaches a copied picture but not a copied file; Codex and Grok attach a copied picture or a copied picture file. A tab for another Mac's shell keeps Ghostty's text paste.

<a id="files-from-the-phone"></a>

**Files from the phone.** A photo or a file sent from the iPhone app to a terminal is pasted the same way. The phone uploads it over the encrypted link (see [docs/remote-protocol.md](../../docs/remote-protocol.md), "File upload extension"); the connector keeps it in `RIWORK_HOME/uploads/SHELL_UUID/` (folders mode 700, files mode 600, under a name the connector makes, never the phone's) and runs `somtus shell paste SHELL_UUID -- FILE...`, which pastes the paths exactly as a drop of those files on that terminal would, chosen by the program in front: Claude Code and Grok get the escaped paths in one paste and attach a picture, Codex one paste per path and attaches a picture, a shell gets the escaped paths. No Return is added and the paste happens once, however often the phone asks again. `shell paste` takes 1 to 16 existing files by absolute path, refuses anything else before it touches the pane (an error that starts with `invalid_request:`, `not_found:`, `input_unavailable:` or `not_sent:` pasted nothing), and `capabilities --json` says `"shell_paste": true`. A file sent to a chat lands in `RIWORK_HOME/uploads/CHAT_UUID/` and its path goes into the message on the phone. Uploads are removed after a day, when their device is revoked, and when the shell is closed or the chat deleted.

Somtus's tmux server always lives in tmux's default socket directory: an inherited `TMUX_TMPDIR` is ignored, so the app, the CLI, and a terminal that sets it all reach the same server. A project folder whose name tmux would misread (`C#Tools`, `#{…}`, or a name ending in `;`) starts its shells in that folder; if tmux still cannot start a shell in the requested folder, creation fails with an error instead of opening in your home directory. Variables that name a CLI profile (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `GROK_HOME`) and `RIWORK_CUA_DRIVER` are cleared from the server's environment when the app was started without them, so a value left by an earlier launch cannot reach a new session, and your own zsh startup files remain free to set them.

`shell keys` types like a keyboard instead: after `--` come 1 to 64 items, each `t:TEXT` (literal text of 1 to 4096 bytes without control characters, sent verbatim, trailing `;` and `\;` included) or `k:KEY` (`Enter`, `Tab`, `BTab`, `Escape`, `Backspace`, `Delete`, `Up`, `Down`, `Left`, `Right`, `Home`, `End`, `PageUp`, `PageDown` or `C-a` to `C-z`, or `Insert`, `Space`, `F1` to `F12`, and with modifiers `C-` `M-` `S-` in that order: any on the cursor and editing keys and F-keys (`C-Up`, `S-F5`), `M-` on `Enter`, `Tab`, `BTab`, `Escape`, `Backspace` and on a printable character (`M-x`, `M-.`), `C-` on `Space` and on `a`-`z` `@` `[` `\` `]` `^` `_` `?` (`C-\`, `C-M-x`)), with at most 4096 text bytes in all; `capabilities --json` says `"key_names": 2` for this second list. No Return is added. The items reach the pane in order under the same input lock as `shell send`, and a key that directly follows text is sent about 150 ms later so Codex does not read the pair as a paste; a pane in copy mode is taken out of it first, and a pane whose terminal input is disabled is refused. `shell keys --serve` is the remote connector's typing worker: it reads batches as JSON lines and types each exactly as `shell keys` would, with the same checks and error text, so the connector need not start a process per batch (`capabilities --json` says `"shell_keys_serve": true`; see [remote/README.md](../../remote/README.md)). `shell output --json` also reports `cursor` (`x`, `y`), `rows`, `cols` and `in_mode`; the last `rows` lines of its `output` are the visible screen. The phone companion uses both for direct typing. `shell output --json` also reports a `hash` of everything the answer says. `--styled` keeps colors and text attributes as SGR sequences (`ESC [ … m`, exactly as `tmux capture-pane -e` writes them) and removes every other escape and control sequence; the lines, and so the screen rule, are the plain capture's. `--if-changed HASH` (a `hash` from an earlier answer to the same question) with `--wait-ms N` (0 to 10000) keeps waiting inside that one process while the hash stays the same, capturing again when tmux reports a change in the pane (a read-only control-mode client attached to the session, which never sizes a window; about every 80 ms where tmux cannot do that), and answers `{"id":…,"unchanged":true,"hash":…}` without any output if nothing changed within the wait. The phone uses these to follow a terminal live instead of polling.

`shell history ID --end N --lines M [--styled] [--json]` reads older scrollback, which `shell output` (at most the newest lines plus the screen) does not reach: it skips the `N` scrollback lines directly above the screen (0 starts at the line just above it), then takes the `M` (1 to 1000) above those, clamped at the top of the history. `--json` answers `{"id":…,"output":…,"line_count":…,"history_size":…,"complete":…}`: `output` is the lines top to bottom joined by newlines, unaltered and with no newline after the last, `complete` is true when the page reaches the first line of the history, and an `N` at or beyond `history_size` gives an empty page (`line_count` 0). Paging upward from `--end 0` with each `line_count` added to `--end` rebuilds the whole history without gaps or overlaps. `--styled` applies the same SGR-only filter as `shell output --styled`. `shell output --json` (and its `unchanged` answer) also reports `history_size`, the number of scrollback lines above the screen, and `alternate`, true while a full-screen program such as vim or less is on the alternate screen; both are part of its `hash`, so output that scrolls lines away without changing the visible screen still counts as a change. The phone companion uses them to scroll back through the whole history (contract in [docs/remote-protocol.md](../../docs/remote-protocol.md)).

`shell send` pastes the text verbatim, whatever its length or trailing characters such as `;`, and presses Return once. Every tmux call is limited to five seconds, so an unresponsive tmux server produces an error instead of freezing the app. A Vim editor session ends when Vim quits, and Somtus then removes its entry from the Shells panel; exited agent and plain shells keep theirs.

Each project remembers its split layout and sizes, mixed panel/shell tab order, active selections, and selected worktree/task across project switches and UI restarts. Closed shell tabs stay detached; click their shell in the Shells panel to reattach them. A shell of a worktree whose folder was deleted outside Somtus (by `git worktree remove`, or the tool that made it) is ended, with its agent: once the folder has stayed gone for five minutes while the folder it was in is still there (so a drive that is not mounted is never taken for a deletion), and only while no terminal is attached to it and no tab of an open window holds it. A tab saved in the layout of a project no window shows does not keep it. An open Somtus window looks once a minute and ends it as `somtus shell close` does; shells of the project's own folder, and shells without a worktree, are never ended this way. Exited shells are skipped during restoration, and new CLI-created shells join the active pane (the main pane, if there is one) when the project next opens. An intentionally empty workspace stays empty. Layouts are saved separately in `layouts.json` under the same data directory. A tab this build cannot read, such as a panel type that only a newer Somtus has, is left out and the rest of the layout opens as saved; the tab stays in `layouts.json` and is written back with the pane that held it, so an older build cannot erase it. A project whose saved layout cannot be read at all, such as one with a split shape this build lacks, opens with a default layout and a notice; other projects are unaffected. Unreadable entries and unknown fields are written back unchanged and never replaced, so an older build cannot destroy a newer build's layouts (changes to that project's layout are not saved while it stays unreadable). A build from before the Preview panel cannot read a layout that has one and falls back to a default layout for that project, leaving the saved layout untouched. The main pane is saved as one more field of the project's layout (`main_pane`, written only when set), which every earlier build ignores: it opens the layout, and forgets the main pane the next time it saves that project. A `layouts.json` that is not valid JSON is kept as `layouts.corrupt-*.json` when layouts are next saved, and a file with a newer schema version is left alone.

The full-width bottom status bar shows the current project on the left and live sessions, CPU, resident RAM, usage, Codex account, the active shell UUID, **G·ORCH** (the global menu: the global window's dashboard and chat), **P·ORCH**, and the **LAYOUT** menu (see **Layout menu** above) on the right by default. The usage item has two modes, chosen in **Settings → Status bar**. **Current chat** (the default) reads out the quota of the focused chat's or shell's Codex account, named (and numbered **A1**, **A2** as its tab is when several accounts run in the project), or of the project's default Codex account when nothing of Codex is focused; a focused Claude or Grok session shows its own figures as before. **All accounts** shows every available Codex account side by side, the system default included, keeps an account that has not been read yet or whose last read failed in view with that said, and adds Claude's subscription once a Claude session has reported it; Grok and Muse have no allowance to show. Both use the usage reads Somtus already makes, and a click opens **Usage** for the details. The Codex account item says which account new Codex chats and shells in this project get, and whether the project, the app or the system default decides it (**DEFAULT (PROJECT)**, **(APP)**, **(SYSTEM)**). A click opens **New Codex sessions in this project**, which chooses it: Inherit app default (with the account that comes to), System default, or a saved account. It is the project's own choice that Project Settings saves, so orchestrator workers started without `--account` use it as well; running chats and shells keep their account, `--account` still chooses one, and the app default in Settings stays as it is. The menu's **Project Settings…**, or Cmd+Option+A, opens Project Settings. Click the status UUID to copy it. Configure status items in **Settings → Status bar**. The Shells panel shows worker shells with their metrics and current worktree when their working directory matches a known worktree.
