# Projects, worktrees and tasks

[Documentation index](../README.md) · [Project overview](../../README.md)

Repository paths and commands below are relative to the checkout root.

## Projects, worktrees, and tasks

Settings → **Import from Orca** offers a one-time preview and import of local
projects and worktrees through the installed Orca CLI. Somtus finds it through
`ORCA_CLI_COMMAND`, then the Orca.app bundle, then `PATH`, `/usr/local/bin`, and
`/opt/homebrew/bin`; Codex account discovery uses the same lookup. Keep Orca
running while previewing and importing. Existing paths retain their Somtus names
and grouping; the import records completion and is safe to invoke again. An
import with nothing to add and nothing skipped, such as while Orca is still
starting, records nothing, so you can import again once Orca lists its projects.
Settings then says there is nothing to import yet instead of offering a finish
button.
The current Orca CLI does not export folder names or nesting. You can also use:

```sh
somtus import orca --preview --json
somtus import orca --json
```

```sh
somtus project add /path/to/repo --name my-project
somtus project create /path/to/new-project --name my-project
somtus project create --name my-project
somtus project create /path/to/plain-folder --no-git
somtus project inspect /path/to/project --json
somtus project list
somtus project use PROJECT_ID
somtus open PROJECT_ID
somtus worktree create feature/branch --project PROJECT_ID
somtus worktree create feature/branch --project PROJECT_ID --repo /path/to/project/repo
somtus worktree list --all

somtus task add "Implement search" --project PROJECT_ID --details "Index project tasks"
somtus project tasks PROJECT_ID
somtus worktree tasks WORKTREE_ID
somtus task assign WORKTREE_ID TASK_ID TASK_ID
somtus task status TASK_ID in_progress
somtus search search
```

`somtus worktree create --base REF` chooses the start point of a new branch only; if the branch already exists it is checked out as is and `--base` is ignored (the MCP `base` argument behaves the same). Projects, Worktrees, Tasks, and Shells each have a searchable panel tab. Projects lists all projects; the other panels show the active project's items. Somtus discovers Git worktrees created outside the CLI during refresh. A removed worktree disappears from the Worktrees panel, project worktree counts, and chat and automation destination choices after a background folder check. Its record stays registered so task and shell references keep their UUIDs, and a restored folder returns to the GUI with that same UUID. The project's root stays visible when unavailable. Use `somtus worktree forget ID` after its tasks and shells are gone to remove the stale record.

Use the Projects sort selector beside the project count to choose **Last edited**, **Name**, **Date added**, or **Live sessions**. The arrow reverses the order. Projects sort within their virtual folders while the folder hierarchy stays intact; search and collapsed folders keep working. The preference is saved and shared across windows. Last edited defaults to newest first and reads the latest source-file modification time across each project's roots and registered worktrees, respecting Git ignores and excluding common build and dependency directories. Windows ask every 30 seconds, shared by all of them, and wait while a window is covered, minimized or on another Space; the next tick after it shows again catches up. Each root is scanned once when first asked about, and macOS file-change events (FSEvents, one stream for all roots) keep its date current after that: an edit to a file that counts updates the date from that one file, and a root is scanned again only when something its date cannot absorb happened (the newest file was deleted, replaced or dated earlier, a file appeared that Git may list, an ignore rule or the Git index changed, or events were lost), and as a safety net every 20 to 30 minutes, so an idle machine scans nothing. If the stream cannot be made, or a root is on a volume that does not report changes, its scan repeats every 30 seconds as before. Each root is scanned within its own limits, and a project shows the latest edit among the roots whose scan completed, so one very large or unreadable root does not hide the others. Unavailable dates sort last; commit dates, deleted files, and task activity are not used as file-edit timestamps. Each time a window's scan finishes, the app publishes the dates to `project-recency.json` in the Somtus data directory (mode 600, replaced atomically, left alone when nothing changed), so `somtus project list --json` and the phone can order projects the same way: only the app can scan, so the CLI just reads the file. A project that a scan could not date keeps its last published date, a removed project's date goes, and since a hidden window does not scan, the dates are as of the last time a window was showing.

Press **Cmd+Shift+E**, or choose **FILES** under **Views** in a pane's **…** actions menu, to browse the current worktree. The explorer follows the focused shell's worktree, including moving into another registered worktree with `cd`. Select a regular file and click **Edit in Vim**, double-click its row, press Enter in the tree, or press **Cmd+E**. Somtus opens Vim in a dedicated persistent terminal tab in that worktree; existing agent shells keep running. Vim's normal editing, `:w` save, `u` undo, and `/` search work in the tab. The editor tab restores with the project layout while its tmux session is alive. Return to Files and select the file to edit it again; a live Vim tab is reused even after saving, and whether you open the file from the project root or its primary worktree. Symlinks and files outside the worktree cannot be opened for editing from Files.

Choosing a file shows a read-only preview of it in the **PREVIEW** panel. Files and Preview are two tabs of the normal pane system, so you can split, resize, lock, drag and close each like any other panel; Files draws only the tree. The preview follows the selection of the same window's Files panel, which is scoped to that window's selected worktree. Choosing a file (a click, or the arrow keys in the tree; the first row a freshly loaded tree picks for itself does not count, and neither does a folder) when the window has no Preview tab opens one in a new pane of its own, and never hides your terminal or resizes a locked pane. If the Files pane is not locked it is split: the preview goes to its right when that pane is at least 620 px wide, otherwise below it when it is at least 700 px tall, and the tree keeps 36% of a side-by-side split and half of a stacked one. A locked Files pane (the left navigation pane is locked by default) or one too small to split is left alone, and the roomiest other unlocked pane that fits the same sizes is split instead: it keeps 60% and its selected tab, so a shell stays on screen, and the preview takes the other 40%, to its right or below it. Only when no pane can be split does the preview become a tab: selected in the roomiest unlocked pane that is not showing a terminal, or waiting unselected in the tab strip of one that is (then a locked pane, then the Files pane itself), and **Cmd+Shift+P** or the tab brings it forward. Splitting a terminal pane resizes that terminal. A Preview tab that is hidden behind another tab of its pane is brought forward when you choose a file, except when it shares a pane with Files, where it would hide the tree, or when the tab in front is a terminal, which you chose to look at there. Keyboard focus stays in the tree, so the arrow keys keep moving the selection while the preview follows. You can close the Preview tab (in a locked pane, unlock it first); **Open the preview when a file is selected** in Settings (on by default) decides whether choosing a file opens it again, and with it off a closed preview stays closed. All of this placement is for a window without a main pane (see **Main pane** below); with one, the Preview is a tab of the main pane and nothing is split for it.

The preview shows text, code, Markdown source, raster images (rotated by their EXIF orientation, shrunk to 1800 px if larger and never enlarged), or PDF pages. Moving the selection with the arrow keys previews after a short pause, and the previous preview stays up until the next one is ready. PDFs are parsed only on request: click the file, press Enter, or use **Preview PDF** in the placeholder. Drag the divider between the two panes to resize them. The file actions sit in the preview header, to the right of the file's name; in a narrow preview the name is shortened before the actions move to a line of their own, and any message about an action appears directly under the header. With **Icons instead of labels** on, they are compact icon buttons with tooltips. Text previews stop at 1 MiB and image or PDF previews at 24 MiB; unsupported or binary files show a message. A folder lists at most 5,000 entries, followed by a row counting the rest, and collapsed folders are not rescanned until expanded again. **Open Externally** uses the default application, but refuses symbolic links, executables, and applications, scripts, or installers such as `.app` and `.command` with an inline message; use **Reveal** for those. **Reveal** and **Copy Path** act on the selection. **Copy Contents** puts the selected UTF-8 text file's exact contents on the clipboard, unclipped and with its line endings intact, and stays disabled for binary files, images, PDFs and files over 1 MiB rather than copying part of one. **Refresh** updates the tree and preview, **Hidden** includes dotfiles, and **Cmd+F** filters files in directories already loaded (from the Preview pane it goes to the filter when Files is on screen). Use arrow keys in the tree and Tab to step through the controls of the pane you are in: the filter, tree and buttons in Files, the preview and file actions in Preview. **Cmd+Shift+E** and **Cmd+Shift+P** move the keys between the two panes. Left/Right on a PDF preview change pages, and **Cmd+O** opens externally. Files and Preview tabs restore with each project's layout; a layout saved before Preview existed has only Files, and the preview appears the first time you choose a file.

Each pane has a **lock** control. Locked panes keep their tabs, selected tab, and surrounding split sizes across project switches; panel contents still follow the selected project. The left navigation pane is locked by default. Unlock it to let that region use each project's saved layout. Locked shell tabs keep their original shell session and project context. A locked pane's tabs cannot be closed and the pane itself cannot be closed (see below); unlock it first. When the window or the pane area is resized, locked panes keep their width and height and unlocked panes absorb the change, except that a locked pane which is the only pane along an axis follows the window along it; if the window gets too small, locked panes shrink only as far as needed to leave the others a minimum size.

**Main pane.** When locks, a Files tree and the Preview all want room, one pane can say where things go. Choose **Main pane** in a pane's **…** menu (**Pane** section; a check mark shows it is on) to make that pane the **main pane**. A star marks its header (the word MAIN with **Icons instead of labels** off), and a click on the mark, or **Main pane** again, clears it. A layout has at most one: choosing another pane moves it. It is saved with each project's layout, so every project keeps its own, and a restart or a reload brings it back. A build from before the main pane opens that layout as usual and ignores it. Without one, nothing below applies and every placement rule is the one described elsewhere.

With a main pane, and outside focus mode (which shows a single pane, so nothing is sent where it cannot be seen), these go to it:

- **New tabs open in the main pane** and become its selected tab, wherever the menu was opened: Cmd+T, **New Tab** (shells, Codex, Claude, Grok, Muse, orchestrators), the Vim editor from Files or Cmd+Shift-click, and, for a project on another Mac, the shell made on it. A terminal that appears by itself (`somtus shell create`, the phone), and one made while the project was closed, joins it too, behind the tab shown. Splitting (Cmd+D) still makes a pane of its own.
- **Clicking a shell** in the Shells panel, a worktree in Worktrees or the project orchestrator (**P·ORCH**) opens its tab in the main pane (the global orchestrator opens in the [global window](orchestration.md#orchestrator) instead). A tab that is already open is reused, never opened twice. It is selected where it is when it is in the main pane, already on screen, or in a locked pane (a click never takes a tab out of a locked pane), or when the tab in front of it is not a terminal. If it is behind a terminal in an unlocked pane it moves into the main pane, so that the terminal stays.
- **The Preview and Files are tabs of the main pane**, not splits: for a file chosen in the tree (when **Open the preview when a file is selected** is on), Cmd+Shift+P when there is no Preview yet, and a Cmd-clicked path or folder in a terminal. The tab becomes the selected one, except where that would hide what is in use: a Preview never covers a tree that is on screen (if the tree is a tab of the main pane itself, the Preview waits in its tab strip), and a link clicked in a terminal of the main pane leaves the Preview waiting there too (a notice says so). A Preview that is already open stays on screen where it is; one hidden behind a panel is brought forward where it is, and one hidden behind a terminal, or behind the tree, moves into the main pane. A Preview or Files tab is the one thing taken out of a locked pane without being asked to, because bringing it forward there would cover the tree. Keyboard focus stays where it was: in the tree, in the terminal clicked, in the new tab.
- **Closing a pane** (**Close pane**, Cmd+Shift+W) moves its tabs, in their order, to the end of the main pane instead of closing them; the main pane keeps showing what it showed. A locked pane cannot be closed, so its tabs never move this way. Closing the main pane itself closes its tabs as it always did (their shells keep running) and leaves the window without a main pane until one is chosen; closing its last tab leaves the pane empty, where new tabs still open.
- **Gather tabs into main pane** (**Pane** section of the **…** menu once a main pane exists, **View → Gather Tabs into Main Pane**, **Cmd+Shift+M**) moves the tabs of every unlocked pane into the main pane, pane by pane in layout order, and removes the panes this empties. Shells keep running: a gather moves tabs and closes none. Locked panes are left as they are, with their tabs, their selected tab and their size; so a pane whose room would go to a locked neighbour stays, empty, and the notice says so.

A locked pane can be the main pane, but only if you choose it; nothing makes one on its own. The lock still keeps its tabs from closing (their X stays hidden), and it takes what you open, but not terminals that appear by themselves or a project's earlier shells, which nobody asked to put in a locked pane. A locked main pane stays the main pane across project switches with the rest of the locked pane; otherwise the main pane belongs to the project's own layout.

**Layout menu.** The **LAYOUT** item at the right end of the status bar (a small layout icon, with the word beside it when **Icons instead of labels** is off) opens a short menu above it; click it again, click elsewhere or press Escape to close the menu. Show, hide or move the item in **Settings → Status bar**. A status bar saved by an earlier build gets the item shown at the end of its right side, and hiding it keeps it hidden. The menu has three rows:

- **Default layout** (also **View → Default Layout** and **Cmd+Option+L**) arranges the window as the left navigation pane is meant to be used. On the left is a **locked** pane, at the width a new project's navigation pane starts with, holding exactly Projects, Files, Worktrees, Tasks and Shells, in that order. On the right is one **unlocked pane that becomes the main pane** and holds every other tab. Tabs are only moved, never closed, so shells keep running (a shell of another project that a locked pane carried here leaves the lock, and the notice says it is no longer part of this project's layout). The panes are read in layout order and the tabs of each in their own order, so the right pane lists them as the window showed them. The tab that was selected in the selected pane is still selected, in the pane it lands in, and that pane is the selected one; the other pane shows a tab that was showing in the window (the right pane the main pane's first, the left pane a navigation panel that was showing, else Projects). A navigation panel goes to the left pane wherever it was, and one that was not open is opened there. Panes that were locked are replaced like the others and their tabs placed by the same rule, so the new left pane is the only locked one. Panel tabs that are not navigation panels (Preview, Usage, Settings, Schedules, Project settings) go to the right pane if they were open, and none is opened or closed. Focus mode ends first. A window that already looks like this (a locked left pane with exactly those panels, and one unlocked main pane on the right) is left as it is, widths included, and the notice says so. The result is saved with the project's layout like any change made by hand, so each project keeps its own, and the locked pane travels across project switches like any locked pane.
- **Gather into main pane** (Cmd+Shift+M) is the gather described above. It is greyed out until a pane is the main pane.
- **Main pane: …** says what the main pane shows and how many tabs it holds (*empty* for a main pane with none), or *none* when there is no main pane. It is only a readout: when there is none, it says to choose **Main pane** in a pane's **…** menu.

Projects, Worktrees, the Shells panel, the status bar and shell tabs show what each Codex and Claude session is doing: **working** during an open turn, **done** after its completion, and **waiting** while a session is idle with no finished turn (a new one, an aborted Codex turn, or a Claude turn that went quiet, see below). **Unknown** means an exact conversation binding or complete lifecycle read is not available yet. New managed Codex sessions bind on their first completion; exact resumed sessions can be tracked immediately. Large Codex logs are read from their first record and recent tail, so a long-running conversation does not need a full replay. Claude has no log to follow: its state is the turn cursor that the hooks of its launch keep (`UserPromptSubmit`, `Stop`, `SessionStart`, `SubagentStart`, `SubagentStop`; identifiers only, never prompts or replies), so a Claude that Somtus did not launch with them (one started by an absolute path) reads **unknown**, and one launched before `SubagentStart` was added shows no subagents until it is restarted. Claude sends no hook when a turn is interrupted with Esc, so a turn that is open but has shown no sign of life for 10 minutes (neither a hook event nor a run of Claude's status line, which Claude does around each message and not on a timer) reads **waiting**, as does one paused by a Stop that lists background work such as a dev server; a single tool call that stays silent for over 10 minutes reads the same until its next message. Grok and Muse have no activity tracking and always read unknown; they are not counted in the summaries. Existing notification settings are preserved.

**Subagents** are shown with the agent that started them: "● 1 working · 2 subagents" in the status bar and project and worktree rows, "● WORKING · 2 SUBAGENTS" on the shell's row, and the kinds on hover over its tab ("Working · 2 subagents (general-purpose, Explore)"). A Claude subagent is counted from its `SubagentStart` to its `SubagentStop`, paired by `agent_id`, and its kind is the hook's `agent_type`. A Stop that ends the turn clears all of them; a Stop that lists background work (`background_tasks`) keeps the turn open and corrects the list to what it names; a new prompt or `/clear` starts without the previous ones. The `SubagentStop` with no start that Claude sends a few seconds after some replies (empty `agent_type`, carrying the finished turn's own prompt) is not a subagent and does not reopen the finished turn, in the display or for scheduled prompts. A subagent that was never heard from again, as after an interrupted turn, stops counting 30 minutes after it started. A Codex subagent is a child thread: a rollout in the same session tree whose first record names the shell's thread as its parent, counted while its own turn is open and its file was written within 30 minutes. Children are looked for in the newest three day directories of the tree at or after the parent's, at most every 4 seconds, and only while the parent is working. Subagents are counted only for a working agent, and only names are kept, never what a subagent was asked to do.

The same figures reach the CLI and the phone. `somtus shell list --json` and `somtus orchestrator list --json` add to each agent shell `activity` (`working`, `waiting`, `done`, `unknown` or `exited`), `activity_since_unix` (when the source records it), `subagents_working` and `subagent_kinds`; a plain shell has none of them, and a Grok or Muse shell is `unknown`. They add `last_activity_unix` to every live shell, a plain one too: the second tmux last saw output in its session (`#{window_activity}`, read in the `list-sessions` call that finds the live shells, so it costs no extra process). Output moves it whether an agent is working with no window attached or text was typed or sent in; attaching, detaching and the pointer do not, which is why tmux's `#{session_activity}` is not used. `somtus project list --json` adds `last_edited_unix` (from `project-recency.json`), `last_activity_unix` (the newest of the project's live shells, its own orchestrator included and the global one not) and `agents`, the project's agent shells by state (`working`, `waiting`, `done`). A project's orchestrator that runs as a chat counts as its terminal one does: its chat's log growing is activity of the project, and its state (`running`, `waiting`, `idle`) is an agent `working`, `waiting` or `done`. The phone's **Recent** project order follows `last_activity_unix`, then `last_edited_unix`. The CLI works the activity out itself, in its own process, from the same files the window reads (Codex rollouts and bindings, Claude hook cursors); it needs no window and no snapshot file, and reads a rollout longer than 1 MiB from its head and tail instead of through, so a list stays quick. The contract is in [docs/remote-protocol.md](../../docs/remote-protocol.md).

The **bell** beside each project controls macOS completion alerts. Alerts are off by default: a cyan bell means on, and a muted crossed-out bell means off. While Somtus is open, completed Codex turns and completed turns in newly launched Somtus Claude sessions send one alert per turn across all windows and processes. Only the packaged `Somtus.app` posts and claims alerts, so an unbundled development build sharing the same data never consumes them. Click the notification or **Open agent** to open that project's completed agent.

Initial **Done** states, historical completions, aborted turns, and ordinary shell exits do not alert. Existing Codex sessions with an exact conversation binding also work; start a new Claude session to load its completion hooks. macOS asks for permission when you first enable a bell, and **System Settings → Notifications** controls delivery. Native alerts require the packaged Somtus app; unbundled `cargo run` launches cannot send them.

Click a project row to switch the current window, or **↗** to open that project in another window. Cmd+Shift+N opens a new project window; `somtus open PROJECT_OR_PATH` opens one from the CLI. Each window keeps its own project. Right-click the Somtus icon in the Dock to see every open window of that app listed by project name, alphabetically, with the frontmost window checked; choosing one brings it to the front. Windows showing the same project add their branch, or a number when that is not enough. **New Window** in that menu is Cmd+Shift+N for the frontmost window. The list follows windows opening and closing, project switches and renames. `somtus project use ID` selects the default for subsequent windows.

Use **+ FOLDER** (a folder-with-plus icon when **Icons instead of labels** is on) to create virtual folders in Projects, or a folder's **+** to create a subfolder. Drag a project onto a folder to file it there. Drag a folder onto another folder to nest it, or onto **UNFILED** to move it to the top level. Dropping a project onto **UNFILED** removes its folder assignment. Folder headers expand or collapse their whole subtree; **✎** renames a folder and **×** removes it, promoting its projects and subfolders to its parent. Virtual folders organize the browser without moving files.

Click a project's **⚙** to open its **PROJECT SETTINGS** tab, where you can edit its name, select a folder by its full breadcrumb, and inspect its root and repository paths. **SAVE PROJECT**, Enter, or Cmd+S applies name and folder changes. Settings tabs restore with each project's layout. App-wide themes, Cua, and window preferences remain in **SETTINGS**.

```sh
somtus project folder create "Personal"
somtus project folder create "Tools" --parent "Personal"
somtus project update PROJECT_ID --folder "Personal / Tools"
somtus project folder move "Personal / Tools" --root
somtus project folder rename "Personal" "Side projects"
somtus project update PROJECT_ID --ungrouped
```
