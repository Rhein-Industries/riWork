# Settings

[Documentation index](../README.md) · [Project overview](../../README.md)

Repository paths and commands below are relative to the checkout root.

## Settings

Open **Somtus → Settings…**, press Cmd+, or choose **SETTINGS** under **Views** in a pane's **…** actions menu. Settings opens as a normal workspace tab: drag, split, close, and restore it like the other panel tabs. Preferences save automatically to `settings.json` under the Somtus data directory and are shared across open windows and app processes. A value this build does not recognize, for example a theme from a newer build, reads as that setting's default and stays in the file until you change that setting; an invalid Codex account selection still blocks new Codex launches instead of falling back to the system account, while plain shells keep opening.

- **Codex accounts** detects the current Codex profile and saved accounts from Orca. The current profile is `~/.codex` or the `CODEX_HOME` from your own environment, and its row shows the resolved path; an account home that Somtus exported into a session is never mistaken for it, so a shell inside an account-bound session still starts system-default sessions on your own profile. Use **REFRESH ACCOUNTS** to check again, then select an app default for new Codex sessions; a project can override it in **Project Settings**. Existing sessions and resumed conversations keep their original account. Quota is read separately for each account and follows the active Codex session's saved account.
- **Project Settings → Memo** (the last section) is the project's own Markdown notes: one free-text memo per project, at most 32 KB. It saves by itself a moment after typing pauses, when the editor loses focus and when Project Settings closes, and says so under the editor (**Saved automatically**, **Saving…**, or why not, with **Retry**); nothing longer than the limit is saved. It is kept in `state.json` under `project_memos`, beside the projects and not in them, so `somtus project list --json`, the MCP tools and the phone's project list never carry it, and no agent is ever given it. On the phone it is **Memo…** in a project's ⋯ menu. Typing `/memo` as the last word of a chat's message, then Return, sends nothing: it shows that project's memo above the message box with **Insert into composer** (adds it after your draft, still unsent) and **Edit** (opens it here); an empty memo offers Edit only, and the global chat, which has no project, says there is no project memo there. The last save wins, whether from the Mac or the phone: an editor takes a newer memo only while it has nothing unsaved. `somtus project memo show ID` prints it and `somtus project memo set ID < notes.md` replaces it.
- **Project Settings → Orchestrator** chooses how this project's orchestrator runs when it is next created: **Inherit app default** (the default, and what older projects read as; it names what Settings say now), **Automatic**, **Terminal** or **Chat** with its provider and model, as in Settings. It saves immediately as the project's `orchestrator` in `state.json` (`{"mode":"inherit"}`, `{"mode":"automatic"}`, `{"mode":"terminal"}` or `{"mode":"chat","provider":"muse","model":"muse-wonder-full-1.0"}`), which `somtus project show ID --json` and `somtus project list --json` print, and applies only to that project's orchestrator: the global orchestrator always follows Settings. A saved value this build cannot read is kept as it was, said to be unreadable, and inherits until you choose. `somtus orchestrator create --json` says who chose (`source`: `settings`, `project` or `request`).
- **Project Settings → Delegation** overrides the Settings delegation policy for this project's orchestrator, field by field: each row has **Inherit** (the default, naming Settings' value) beside its own choices. It saves immediately as the project's `delegation_policy` in `state.json`, in the shape Settings use, with only the fields chosen; a field this project does not choose follows Settings, then Somtus's default. The global orchestrator always follows Settings.
- **Project Settings → Codex Account** selects **Inherit app default**, **System default**, or an available saved Orca account. The choice saves immediately and applies to new Codex sessions and new project orchestrators. Older projects inherit the app setting. Global orchestrators always use the app setting. An explicit saved account that later becomes unavailable (for example when Orca is removed or the account is deleted) remains selected and prevents new Codex launches, including the `codex` launcher in a shell, with an error until it is restored or changed. Plain shells still open; they just start without an injected `CODEX_HOME`. Somtus reads only Orca's public account list and its own metadata cache; it never reads account credentials.
- New plain project shells start with `CODEX_HOME` set to the project's effective choice. The Somtus `codex` launcher in a plain shell resolves the current project choice each time a new Codex invocation begins; a resume or managed child keeps its original account. A custom command that runs `codex` by name goes through the same launcher and resolves the project choice too; only an absolute path to a Codex binary bypasses it and uses its own environment. Utility commands such as `codex login` skip account binding, so Somtus's launcher refuses `login`, `logout`, and other credential or configuration changes (`mcp add`, `plugin`, …) while `CODEX_HOME` is an Orca-managed account home: manage that account in Orca, or point the command at your own profile with `CODEX_HOME=~/.codex codex login`. A plain shell shows a Codex account (**A1**, status bar) only while Codex is running in it. Changing a default never changes a running process or its saved account label. When multiple live Codex account homes exist in one project, tabs show **A1**, **A2**, and so on beside the session title; the focused account uses the same number in the status bar. Numbers derive from the sorted frozen homes within each project and may change when the set of live accounts changes.
- **Remote** lists the Macs paired with this one, with their link state and a two-click **REMOVE**, and has **ADD HOST** (paste a pairing link) and **PAIR ANOTHER MAC** (make a link that lets another Mac control this one). See [Controlling another Mac](remote-access.md#controlling-another-mac). Hosts are kept by `somtus-remote` in `RIWORK_HOME/remote/hosts.json` and never in `settings.json` or the layouts.
- **Status bar** lets you show or hide the entire bar, choose visible items, move each item left or right, and change its order with the arrow buttons. The current project appears on the left by default. Worktree and agent activity are optional; **RESET DEFAULTS** restores the original arrangement. Preferences apply across windows.
- **Color palette** in Settings → **Appearance** shows named swatches and marks the selected palette. **Native** is the default. The 12 fixed palettes are **Somtus**, **Catppuccin Mocha**, **Tokyo Night**, **Gruvbox Light**, **Hermes**, **Dracula**, **Monokai**, **Nord**, **Solarized Light**, **Solarized Dark**, **One Dark**, and **Gruvbox Dark**. Their interface and terminal colors come from the shared [color-palettes.json](../../crates/riwork-core/color-palettes.json), also bundled with the iPhone app. Palettes change colors only; font, text size, controls and layout keep their own settings. Preferences are shared across desktop windows and app processes.
- **Native** follows macOS light/dark appearance with neutral surfaces. **Follow Ghostty** uses Ghostty's own configuration loader, including recursive files and custom themes, and refreshes when those files change. Selecting a palette does not edit the standalone Ghostty app's configuration. All palettes retain native controls, SF Symbols and sentence-case labels. `RIWORK_APPEARANCE=light` or `dark` pins the host appearance instead of following the system.
- **Terminals match the theme** (Native only, on by default, saved as `native_terminal_colors`) gives terminals Native's white or black background and a quiet ANSI palette whose normal colors read at 4.5:1 or better. Off keeps Ghostty's own colors.
- **Interface font** (available for every palette, saved as `interface_font`): **System (SF Pro)** for everything, or **System + monospace accents** (the default), which keeps paths, branches, shell ids, commands, shortcut keys and the status bar's counts in SF Mono (Menlo where SF Mono is missing). The system font draws every size 2 pt larger, so the default 11 pt is drawn at 13 pt, the macOS body size, and **Text size** shows the size drawn (13 pt by default, stepping by whole points); with **MATCH TERMINAL** it is Ghostty's number as it is.
- **Use Somtus terminal colors** remains available under Follow Ghostty for existing preferences and is off by default. Turn it on to keep Somtus's original terminal palette. Theme changes preserve running shells, Codex/Claude/Grok sessions, tabs, and splits; returning to Ghostty's colors reconnects only terminal display clients.
- **Text size** sets Somtus's own text (panels, tabs, menus, the status bar, Settings, and hover hints) in points, like Ghostty's `font-size`: the number is the size of the panels' list text, from 9 to 24 pt; 11 pt is the original size. **−** and **+** in the row, the arrow keys (or − / =) on the focused row, Cmd+= / Cmd+- outside a terminal, or the **View** menu step it by 1 pt, as Ghostty's own Cmd+= does; **RESET**, 0, or Cmd+0 returns to 11 pt. Bars, rows, menus, and icons grow with the text, and terminals keep their own size. It applies to all open windows at once and is saved as `ui_text_size` in `settings.json`; a value out of range is pulled into it and anything but a number reads as 11. **MATCH TERMINAL** in the same row (or M, Enter, or Space on the focused row; off by default, saved as `ui_text_matches_terminal`) uses the `font-size` in your Ghostty configuration instead and shows the same number, so the panels' list text is as large as terminal text (Ghostty's macOS default is 13 pt). It is read with Ghostty's own loader including `config-file` includes and re-read within a few seconds of an edit; a terminal you zoomed with Cmd+= is not followed. Changing the size by any means turns matching off and steps from the size shown.
- **Icons instead of labels** is off by default. Turn it on to show a small icon instead of the name on the built-in panel tabs (Projects, Worktrees, Files, Preview, Tasks, Shells, Usage, Settings, Project Settings, and Schedules) and on toolbar buttons: **+ FOLDER** and **+ PROJECT** in Projects, the create-folder button in Project Settings, and the file actions in Preview (Edit in Vim, Copy Path, Copy Contents, Reveal, Open Externally). Hover an icon for its full name and shortcut; a button that is unavailable says why. Shell, agent, orchestrator, and editor tabs keep their titles, and the focus-mode bar still shows the full name. It applies to all open windows at once and is saved as `panel_tab_icons` in `settings.json`; the key keeps that name from when the setting only covered tabs, and a build without the setting leaves it alone.
- **Open the preview when a file is selected** is on by default and saved as `open_preview_on_select` in `settings.json`. Choosing a file in Files then opens the Preview panel in a pane of its own, or brings it forward if it is hidden behind another tab that is not a terminal. Turn it off to arrange the panes yourself: a Preview tab you closed stays closed, and one you left behind another tab stays there. It applies to all open windows at once.
- **Keep agent transcripts in scrollback (inline mode)** is on by default and saved as `agent_inline_mode` in `settings.json`. A full-screen agent draws on the terminal's alternate screen, where tmux keeps no history, so the phone could only page through the app by sending it PageUp and PageDown over the network. With this on, new agent sessions draw on the main screen: Codex starts with `--no-alt-screen`, Grok with `--minimal` (Grok's own `--no-alt-screen` still redraws a fixed full-height canvas and leaves no transcript), and Claude Code with `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`, which overrides a `"tui": "fullscreen"` in your Claude settings. The conversation then becomes ordinary terminal scrollback that the desktop wheel and the phone's `shell history` can read and scroll locally. The setting applies to agent tabs, orchestrators, session reloads, and a `codex`, `grok`, or `claude` typed in a Somtus shell when it opens an interactive session; `codex exec`, `grok -p`, utility commands, and an invocation that already names its screen (`--no-alt-screen`, `--minimal`, `--fullscreen`) are left as typed. It is read when an agent starts, so a running session keeps its current mode until it is restarted. Turn it off to run the agents full screen again. Inline Codex and Grok clear their scrollback and draw the transcript again at the new width whenever the pane is resized, which includes the phone pinning or releasing the pane size.
- **Agent terminals run unrestricted** (Agent sessions) is on by default and saved as `agent_terminals_unrestricted` in `settings.json`. On, Codex, Claude and Grok from the **New Tab** menu, Cmd+Shift+C, Cmd+Shift+L and Cmd+Shift+G, and from the paired phone start without approval prompts: Codex with `--dangerously-bypass-approvals-and-sandbox`, Claude with `--dangerously-skip-permissions`, Grok with `--always-approve`. Off, the same entries start them with each CLI's usual permissions, so they ask before running commands and editing files. The menu names only the agent either way. The file is read each time an agent starts, so every window and the phone follow a change at once; a session that is already running keeps its mode until it is closed. Orchestrators keep their own rules (see [Orchestrator](orchestration.md#orchestrator)), `somtus shell create` keeps its own flags, and chats have their permission mode in the chat.
- **Show microphone buttons for dictation** (Agent sessions) is off by default and saved as `dictation_mic` in `settings.json`. It governs every dictation mic: on the Mac, every Codex and Claude chat tab then shows a mic button beside Send: click it, or press ⌃⌥D in the chat, to dictate into the message box, and again to stop (⎋ cancels); the words are recognized on this Mac by the bundled `riwork-speech` helper and never sent anywhere, and dictation never sends the message. Off, the chats show no mic, their hint line does not mention dictation, ⌃⌥D does nothing in them, and no speech helper starts or asks for the microphone or speech recognition. Switching it off during a dictation cancels it, and open chat tabs follow at once. The paired phone follows the same setting through `appearance.json` (`mic`, below) and shows or hides all of its mic buttons, in its chat composers and on its terminal key bar. The Mac's terminals have no dictation.
- **Dictation model** (Agent sessions, shown while the mic setting is on) chooses what the Mac's chats dictate with, saved as `dictation_model` in `settings.json`: **Apple Speech** (`apple`, the default; the system's on-device recognizer, as before) or a local MLX speech model run by `mlx-audio`: **Parakeet TDT 0.6B v3** (2.5 GB; fast, English and 24 other European languages), **Whisper large-v3 turbo** (1.6 GB; 99 languages), and **Nemotron 3.5 Transcribe** 4-bit EA (19.3 GB, 32 GB of memory or more) and 8-bit EA (35.1 GB, 64 GB or more). A Nemotron 4-bit copy that riTranscribe downloaded before its repository left Hugging Face is offered too while it is still in the cache. Choosing a model and downloading it are separate: **Download** fetches the model's pinned files (an exact commit and the exact files and sizes in `crates/riwork-nsh-native/speech/models.json`; never code) into the standard Hugging Face cache (`HF_HUB_CACHE`, else `~/.cache/huggingface/hub`), shared with other apps, with progress and **Cancel**; a model already there needs no download. The first local model also sets up Somtus's own speech runtime (Python 3.12 and `mlx-audio`, about 450 MB) with `uv sync --frozen` into `RIWORK_HOME/speech`; that needs [uv](https://docs.astral.sh/uv/) (`brew install uv`), and a model on this Mac without it shows **Set up**. While dictating with a local model, `riwork-speech capture` only listens (it asks for the microphone, never speech recognition) and one long-lived worker (`speech/worker.py`, its log in `RIWORK_HOME/speech/worker.log`) recognizes: it re-reads the phrase being spoken every half second (Parakeet) or second (Whisper, Nemotron), after warming a newly loaded model up so its first words come as fast as the rest, so the words in the message box settle as you talk, and settles each phrase after a pause. The worker loads models with the Hub offline, keeps the chosen one in memory between dictations, frees it after ten idle minutes, and ends with the app; audio is never written to disk or sent anywhere. Dictating with a model that is not on this Mac yet says so and points here. `somtus settings set dictation_model parakeet-v3` chooses one from the CLI. The worker's own tests run with the runtime's Python: `python -I -m unittest discover -s crates/riwork-nsh-native/speech`; `dictation::tests::a_local_model_dictates_a_recording_end_to_end` (ignored; its doc names the environment) plays a recording through the whole path.
- **Push to talk** (Agent sessions, shown while the mic setting is on), saved as `push_to_talk_key`: hold **Right ⌘** (`right_command`, the default) or **Right ⌥** (`right_option`) alone in the selected chat, or hold its mic button, and talk; let go and the last words settle and the message is sent. Only words that dictation delivered send: a hold in which nothing was heard sends nothing, not even a draft already in the box. A press shorter than a quarter of a second is a tap and does nothing, and the key used with another key (a shortcut such as ⌘C, or an Option character such as ⌥G for @ on Swiss and German keyboards) voids the hold and discards what it heard. A window that loses the keyboard mid-hold stops and keeps the words without sending. **Off** turns the key off; holding the mic button still works. ⌃⌥D and a click on the mic still dictate without sending. NSH has no key-up events, so the host's AppKit monitor reports a hold's edges to the key window as `pushToTalkDown:…`, `pushToTalkUp:…` and `pushToTalkChord:…` commands; it never consumes a key. With a local model, dictation listens as soon as the microphone is open and says the model is loading meanwhile: what is said while it loads is kept and recognized once it is loaded.
- **Claude chats bill** (Agent sessions) chooses **Subscription** or **API key** for new Claude chats; API key is the default. It is saved as the switch it grew from, `claude_chat_ignores_api_key` in `settings.json` (`true` is Subscription; `false`, absent or unreadable is API key), so builds from before, and a chat host of one still running, read the same choice. Subscription starts the chat's `claude` without `ANTHROPIC_API_KEY`, so a key exported in your shell cannot switch it from your Claude subscription to API billing. API key gives it the Anthropic API key saved below, billed to your Anthropic API account (and any API credits it has), or, with none saved, the environment it would have anyway, `ANTHROPIC_API_KEY` included, keeping every sign-in method it has, as Anthropic's terms for products that run Claude Code ask. Each chat keeps the choice it was made with (its message box switches it); a chat from before the choice follows this setting at each start. Claude terminal tabs are not affected.
- **Anthropic API key** (Agent sessions) takes a pasted key in a masked field, with **Save** and **Remove** and a line that says whether a key is saved, never the key. The key is kept only in the login Keychain, as one generic password (service `dev.riwork.anthropic-api-key`, account `claude-chats`): never in `settings.json`, a chat's info, events or logs. The chat host asks for it each time it starts a Claude chat on API key (never when the host itself starts) and gives it to that chat's `claude` as `ANTHROPIC_API_KEY`, as a key exported in your shell would be: the commands Claude runs inherit it, so what they print is the agent's output. A chat host, window or tmux server that a command inside such a chat starts drops it again. A saved key the Keychain will not give fails that start with the Keychain's reason rather than starting Claude on another sign-in; a Keychain that cannot even say whether a key is saved leaves the start as it always was. A Keychain that refuses a save or a removal says why and changes nothing. Saving a key affects every Claude chat set to API key, including the default for new chats, from its next start; Settings says so beside the field.
- **Orchestrator runs as** (Agent sessions) chooses how the global and project orchestrators are created from now on: **Automatic** (the default), **Terminal** or **Chat**. Automatic starts a Muse chat on `muse-wonder-full-1.0`, the best delegator, and when Muse cannot start (not installed, or its chat fails to start) a Codex chat on `gpt-6.1-sol`, the workhorse, and says so: the window that asked shows why, and `somtus orchestrator create` prints it as `fallback` (a **Note** in plain text). If neither starts, creation fails with each reason and nothing is left behind. Terminal is the Codex terminal orchestrators always were. Chat shows **Chat provider** (**Codex**, **Claude** or **Muse**) and **Chat model**: the provider's own default, the model Somtus's routing recommends for it (Muse `muse-wonder-full-1.0`, Claude `opus`, which Claude reports as Opus 5.5, Codex `gpt-6.1-sol`), a model saved earlier, or any ID typed into **Other model** and saved with Return; another provider starts on its own default. An explicit Chat that cannot start is an error, never replaced by another provider. They are saved as `orchestrator_mode` (`automatic`, `terminal` or `chat`), `orchestrator_chat_provider` and `orchestrator_chat_model` (null: the provider's default) in `settings.json`, and the CLI, the MCP tools, the windows and the phone read the file each time they create one, so a change applies to all of them at once. These keys are written only when you choose in these rows, so saving another setting leaves them out and a file without `orchestrator_mode` (a fresh one, or one from a build before orchestrators had modes) is Automatic, whatever the default of a later build; a saved `terminal` or `chat` from an older build is a choice and stays one until you change it. A value this build cannot read (or a model saved beside a provider it cannot read) is kept in the file as it was, Settings name it under the rows, and the default stands in for it until you choose in the row, even the value shown. A project can choose for its own orchestrator in Project Settings (below). It applies only to orchestrators created from now on: an existing orchestrator keeps its mode, provider and model until it is closed (`somtus orchestrator close`) and created again, which is also how the rule for the unrestricted mode of project orchestrators works. A custom `--command` is always a terminal. See [Orchestrator](orchestration.md#orchestrator).
- **Delegation** (Agent sessions) is the policy orchestrators are told when they start or load their skill: **Spread work** (on by default: fan independent tasks out to several worker shells at once; off, one worker at a time unless asked), **Parallel worker shells** (a soft target, 1 to 10, default 4), and the harness and model to prefer for **Design work** (default Claude `opus`) and **Workhorse work** (default Codex `gpt-6.1-sol`), as the skill's model routing does. Somtus starts no shell by it; the orchestrators act on it. It is saved as `delegation_policy` in `settings.json` (`spread_work`, `parallel_shells`, `design` and `workhorse` as `{"provider":"claude","model":"opus"}`), written only when you choose, field by field: a field never chosen follows Somtus's default, and a value this build cannot read (or a policy that is not an object) is kept as it was and named under the rows; a model id a session would refuse is never saved. A project can override any field (below). The startup message states the result in one sentence; a running orchestrator keeps what it was told until it is created again or loads its skill, and shows **Load skill** once a change applies to it.
- **Remember project window size** is on by default. New or reopened project windows restore the last normal window size, fitted to the current display's visible area, and later windows in the cascade stay on that display. Only a size you set by resizing is saved: zooming (the green button or a titlebar double-click), entering fullscreen, or the smaller size a window is clamped to on a smaller display does not overwrite it. Switching projects in an existing window keeps that window's size. Layouts without a saved size use the default size until the window is resized.

On iPhone, **Display → Color palette** offers **Native** by default, the same 12 fixed palettes offline, and an explicit **Follow desktop** choice. The choice is saved locally on the phone; changing it does not change the Mac. Native follows the phone's light/dark setting, while Follow desktop uses the selected desktop's cached colors, including Ghostty colors, and falls back to Native until available. Controls and typography stay native for every palette. iPad retains its existing desktop color synchronization.

The desktop publishes its resolved palette, terminal colors and microphone preference to `appearance.json` under the Somtus data directory (mode 600, replaced atomically, unchanged documents are not rewritten). `somtus appearance` prints a summary; `somtus appearance --json` prints the validated document. It contains `v`, `updated_at`, `dark`, the interface `palette`, optional `terminal` colors and 16 ANSI entries, and optional `native` and `mic` flags. Before the first publication, the command asks you to open Somtus. The companion reads this document through `appearance.get`; the microphone preference applies independently of the phone's chosen palette.

The embedded Ghostty adapter currently uses the light variant of a paired `light:…,dark:…` theme and does not follow macOS appearance changes. A single Ghostty theme or an explicit Somtus theme applies consistently.
