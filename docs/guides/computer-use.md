## Cua.ai setup and computer use

Somtus uses [Cua.ai's Cua Driver](https://cua.ai/cua-driver) for computer use across Codex, Claude, Grok, Muse, and the global and project orchestrators. On a machine without the driver, the app opens Settings with **SET UP CUA**. Setup downloads Cua's official stable installer over HTTPS, installs the signed `CuaDriver.app`, and prepares the shared connection. You can also run:

```sh
somtus setup
somtus cua status --json
somtus cua permissions
```

Select **GRANT MACOS ACCESS**, then enable **CuaDriver** in macOS **Privacy & Security → Accessibility** and **Screen & System Audio Recording**. These permissions belong to CuaDriver and need to be enabled once in System Settings. Approve CuaDriver's direct screen capture prompt when macOS shows it. Settings reports the grants and capture verification, and offers **CHECK AGAIN** after enabling them. Somtus launches its driver in standard permission mode. The explicit grant action restarts the shared service with Cua's permission onboarding so updated grants are read by a fresh process.

**The cua-driver skill.** Cua Driver ships an agent skill pack, a directory it names with `cua-driver skills path` (normally `~/.cua-driver/skills/cua-driver`). Setup, and only setup (`somtus setup`, `somtus cua setup`, **SET UP CUA**, or **LINK CUA SKILL** when the driver is ready but a CLI lacks the skill), asks the driver for that directory once the driver has passed Somtus's identity check. When the pack is not there, setup runs `cua-driver skills install`, Cua's own way to fetch it, which also links the agents Cua Driver itself detects and never over an existing path. Somtus then links the pack, as a symlink named `cua-driver`, into the user skill directory each CLI reads:

| CLI | Skill link | Notes |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/cua-driver`, and `$CLAUDE_CONFIG_DIR/skills/cua-driver` | Claude Code does not read `~/.agents/skills`. |
| Codex | `~/.agents/skills/cua-driver` | Codex reads it whatever `CODEX_HOME` is, so the system home and every Orca account home Somtus binds share one link. Orca's account homes are not written. |
| Grok | `~/.grok/skills/cua-driver`, and `$GROK_HOME/skills/cua-driver` | Grok also reads `~/.agents/skills` and `~/.claude/skills` and lists one skill per name. |
| Muse | `~/.config/muse/skills/cua-driver`, and `$XDG_CONFIG_HOME/muse/skills/cua-driver` | `~/.local/share/muse/skills` only caches Muse's bundled skills. Muse also reads `~/.agents/skills`. |

The second location applies when Somtus itself runs with that variable, which its sessions inherit; an app opened from the Dock has none of them. A variable that is a relative path is reported as unsupported, since each session resolves it from its own directory. A CLI with no home on this Mac is skipped: no `~/.claude`, `~/.grok` or `~/.config/muse` (Muse creates it whenever it runs), and for Codex none of the homes it is launched with. Setup creates the directories that lead to a link it makes, such as `~/.agents/skills`, never a CLI's home. It never replaces or removes a file, a directory or a link it did not make, and does not create through a `skills` path that is a file or a link to a missing directory: such a path is reported as blocked and left as it is. The links Somtus made are recorded with their target and inode in `RIWORK_HOME/cua/skill-links.json`. Only a link that is still that very link is repointed when the pack moves, by an atomic exchange that puts back anything else it finds; a link Cua Driver or anyone else made, even to the same pack, stays theirs, and counts as linked when it resolves to the pack. `somtus cua status` (and `--json`, under `skills`) reports each location with its path as `linked`, `missing`, `stale`, `blocked_by_foreign_path`, `pack_missing`, `home_absent` or `unsupported`. Status, app start, and shell, harness and chat launches only read these directories. A linked skill is found by sessions that start afterwards; a running session keeps the skills it started with. Settings shows the driver's readiness and each CLI's skill link separately. The MCP connection and Somtus's computer-use instructions are unchanged and do not depend on the skill.

Somtus runs Cua's installer with a minimal environment: `PATH`, `HOME`, `TMPDIR`, the locale, proxy and certificate settings, and Cua's telemetry variables. Tokens and API keys in your shell, such as `GH_TOKEN`, are not passed to it. After installing, and before it launches or runs the driver, Somtus checks that `/Applications/CuaDriver.app` carries Cua AI, Inc.'s Developer ID signature (bundle identifier `com.trycua.driver`, Team ID `YCK386LBJ7`) and that macOS accepts it as notarized (`codesign --verify` and `spctl --assess`). An app that fails is not launched; the error explains how to reinstall it. Somtus remembers a successful check until the app on disk changes, so normal startup does not repeat it. The driver must live inside that app; a `cua-driver` elsewhere on `PATH` is not used. An installer that times out is stopped with SIGTERM so it can release its lock, and Somtus removes a leftover lock under `RIWORK_HOME/cua/package/packages/.install.lock.d` when the process recorded in it is gone. A slow first start of the driver after boot is retried and never triggers a reinstall.

**Telemetry.** Cua's installer states that telemetry defaults to enabled for new installations, and that it collects no prompts, tool arguments, screen contents, or file paths. Somtus captures the installer's output, so you do not see that notice, and it does not change the default. To opt out, run `RIWORK_HOME/cua/bin/cua-driver telemetry disable` after setup (for the default state directory, `~/.local/share/riwork/cua/bin/cua-driver telemetry disable`), which is the command Cua's installer prints. Somtus also forwards `CUA_TELEMETRY_ENABLED` and `CUA_DRIVER_RS_TELEMETRY_ENABLED` from the environment of `somtus setup` to the installer, but the command changes the driver's own persistent setting.

New Somtus Codex, Claude, Grok, and Muse launches receive the same `cua-driver` MCP connection and computer-use instructions (a Muse terminal as an `mcpServers.cua-driver` entry passed with `-c`, its instructions riding its first message, as Codex's do; a Muse chat names the same server for its session only, see [Chat host](chat.md#chat-host)). Codex's OpenAI computer-use feature is disabled for these launches. Existing model, account, and harness permission preferences are retained. New plain shell tabs include Somtus's Codex, Claude, Grok, and Muse launchers on their `PATH`, so starting any CLI from a shell tab uses the same integration. An absolute path to a separately installed CLI bypasses those launchers. Somtus runs the CLI under the name it finds it by, so version-manager shims such as mise's and Volta's keep working, and it skips a file that is not executable. When the app is opened from the Dock or Finder its `PATH` lacks the directories that nvm, pnpm, bun, pyenv and similar tools add. If a CLI is not found on the app's own `PATH`, Somtus asks your login shell (`$SHELL`, else `/bin/zsh`) once per process, without a terminal and within three seconds, for the `PATH` a terminal would have, and gives Codex, Claude, and Grok tabs that `PATH` after the launcher directory. A shell that fails or hangs is ignored. Existing running harnesses need to be restarted to load the new connection; closing and reopening a terminal tab only reattaches its running session.

The MCP connection runs through `somtus cua mcp`, which resolves the installed driver without depending on the agent's `PATH`. It stays running as a small stdio proxy between the agent and `cua-driver mcp` instead of replacing itself with the driver, so a driver or desktop service restart (for example when the service is replaced or ends) no longer drops computer use for agents that are already running. Messages are forwarded line by line, unchanged and in order, and the driver's stderr goes to the proxy's stderr. When the driver's MCP process ends while the agent is still connected, every request it had not answered gets the JSON-RPC error `-32000` "Cua Driver restarted; retry the request" (with the request's id unchanged); the proxy then makes sure the desktop service is running through the same signature-checked start as a first launch, starts a new driver, replays the agent's `initialize` and `notifications/initialized` (the replayed answer is not passed on) and, when the driver declares that its tool list can change, sends `notifications/tools/list_changed`. Requests that arrive while the driver is down get the same error at once instead of waiting. A failed restart, including a failed handshake replay, is retried after 1, 2, 5, 10 and then every 30 seconds; a driver that stayed up for 30 seconds starts the schedule over. Restarts are also recorded in `RIWORK_HOME/cua/driver.log`. The proxy exits only when the agent closes its input, after stopping the driver. A single message over 16 MiB is a protocol error: one from the agent is dropped and answered with an error that has a null id, and one from the driver makes the proxy restart the driver and fail the requests it was serving. A driver that cannot be started at all when `somtus cua mcp` launches still fails the launch with the reason. For a custom driver installation or isolated tests, set `RIWORK_CUA_DRIVER` to its executable (an empty value is ignored). This developer override skips the signature and notarization check, since it names a different binary on purpose, and is passed to each harness's MCP server so `somtus cua mcp` uses the same driver. New tmux sessions receive it in their environment too, so a `codex`, `claude`, or `grok` typed in a plain shell tab uses the same driver. When several agents start together against a stopped desktop service, the later ones wait up to 30 seconds for the first to start it instead of failing. If the Somtus binary a launcher points to has moved or been deleted, the launcher warns and runs the next `codex`, `claude`, or `grok` on `PATH` outside Somtus's launcher directory until the app regenerates them. Setup keeps its managed launchers under `RIWORK_HOME/cua` and does not edit your global Codex, Claude, or Grok configuration or shell startup files; outside `RIWORK_HOME` it only adds the skill links described below, plus what Cua's own `cua-driver skills install` does when the pack is missing. Grok receives a session-scoped agent definition from `RIWORK_HOME/cua/grok-agent-*.md`; its model and login still come from Grok's own profile, while Somtus's agent definition replaces Grok's default agent selection for that session. Each launch refreshes the definition it uses and removes ones that no launch has used for 30 days. Before a Grok tab or a `grok` typed in a Somtus shell starts, Somtus starts Cua Driver when its desktop service is down and completes an MCP handshake. That work finishes before Grok's 30-second MCP startup limit begins. When neither `GROK_MCP_STARTUP_TIMEOUT_SECS` nor `MCP_TIMEOUT` is already set, that Grok process receives `GROK_MCP_STARTUP_TIMEOUT_SECS=120`, the same startup budget Codex is given. A value you already set is forwarded unchanged. When both are set, Grok applies `MCP_TIMEOUT` (milliseconds) over `GROK_MCP_STARTUP_TIMEOUT_SECS`. A per-server `startup_timeout_sec` in your own `config.toml` still wins, and Somtus does not edit that file or put a timeout in Grok's agent definition, which has no effect on the handshake limit. Grok still owns that limit. On 1.0.44 a headless first prompt can be sent before the session has folded this handshake into the turn, even when the server answers in well under a second, and a slow handshake is only waited on for about two seconds before that prompt proceeds. The tools are registered on the session for a later prompt. If the check fails, Grok is not started and the message names the cause, how long the check took, and `RIWORK_HOME/cua/driver.log`. Somtus's zsh tabs forward your startup files through a session directory and restore the launcher prefix after their PATH changes. Custom shells, aliases, and nested shells can override that PATH; direct Somtus harness launches always receive the connection.

**Input to Somtus's own windows is refused.** The proxy refuses, by default, the tool calls that would send input to the Somtus app you are working in, whose windows hold your orchestrator chats and terminals: any call that names a running Somtus app's pid (`pid` or `target.pid`), whatever the tool; while Somtus runs, input tools (clicks, typing, keys and hotkeys, drags, scrolls, `set_value`, menus, `bring_to_front`, `set_window_frame`, `kill_app`, replayed trajectories, and moving the real pointer) that are not aimed at one app's window by its `pid`, since desktop-scope, frontmost-app and bare element-token input could land in Somtus (agents are told to pass `pid` on every input call); and `launch_app` of Somtus itself. The agent gets a tool error that says why, the driver never sees the call, and the proxy notes it on its stderr and in `RIWORK_HOME/cua/driver.log`. Read-only tools (window state and screenshots, window and app lists, accessibility trees, health) are unaffected, and so is input to every other app. Running means registered in your own runtime registry (`~/Library/Caches/riwork/runtime`, whatever `RIWORK_RUNTIME_DIR` says), so a fixture Somtus started with its own `RIWORK_RUNTIME_DIR` and `RIWORK_HOME` can still be driven for isolated UI checks. All of Somtus's windows, terminal panes included, belong to its one process, and a tool call names no window Somtus records, so the guard covers every window of a running Somtus, not only those that show an orchestrator. To allow it on purpose, start a terminal session with `RIWORK_CUA_ALLOW_RIWORK_INPUT=1` (exactly `1`) in its environment, for example `RIWORK_CUA_ALLOW_RIWORK_INPUT=1 claude` in a Somtus shell tab: Somtus passes it on to that session's `somtus cua mcp` (harnesses filter their MCP servers' environments otherwise) and names it on the pane of each terminal it launches from that environment, and a proxy started with it says so in `driver.log`. The tmux server and the chat host, which outlive any one launch, never keep it, so chats, orchestrator chats included, are always guarded. The proxy reads it once, when it starts, so nothing an agent does later turns the guard off for a session that is already running. The guard is a safety net against accidents, not a sandbox: an agent that runs the `cua-driver` CLI directly goes around it, which is why the orchestrator skill's Hard boundaries forbid input to live orchestrator windows by any means.

Somtus also serves a local MCP connection over stdio with `somtus mcp`. Configure an MCP client to launch that command to give Codex, Claude, Grok, or Muse project, worktree, task, shell, orchestrator, and schedule tools. Many tools only read state, but others change it: they register projects and worktrees, start shells (a `command` runs as an arbitrary program), send input to shells, and edit schedules whose prompts Somtus later types into an agent. Each tool's `annotations` mark its read-only and destructive behavior accordingly; for example `riwork_worktree_list` is not read-only because refreshing writes newly found worktrees to Somtus's state. Every tool rejects arguments outside its `inputSchema` instead of ignoring them, and failed schedule calls set `isError` without `structuredContent`. The server accepts JSON-RPC batches and answers malformed input with a JSON-RPC error. It uses the same state as the CLI and GPUI app.
