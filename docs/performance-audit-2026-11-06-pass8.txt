Borrowed code-block conversion — adopted
Top-level Markdown code blocks now serialize borrowed language/title/text fields
directly into owned Value, avoiding the intermediate owned NSH CodeBlock. Other
block variants and nested code still use the typed NSH converter. The small
borrowed schema is checked against the actual NSH node serializer; optional
None versus empty strings, field order, escapes and owned returned Values match.
The current borrowed-line parser, retained document Values and owned Splice tail
remain unchanged. This does not solve whole-tail parsing or Splice cloning.

Exact-source proof covers 150 NSH field/read-back cases, 25 variant/style/nested
controls, 42 threshold cases, 8,968 UTF-8 stream prefixes and the prior 449-prefix
proof, replacements and retained outputs. Independent reviews found no blocker.
Separate allocation instrumentation preserves exact output in 64 cases. At
nominal 256 KiB, the language/title/code fixture's conversion drops from 14 to
11 requests and 541,291 to 270,944 requested bytes. Combined update+serialization
drops from 71 to 68 requests and 3,720,422 to 3,450,075 bytes. One full code-text
copy plus the two present metadata-string temporaries are eliminated. These are
allocation requests, not peak heap/RSS; omitted metadata saves fewer allocations.

The first optimized 160-condition matrix showed isolated conversion improvements
of 28–78%, but mixed combined/control times under substantial desktop load.
Original sample values were retained sorted within each variant, losing pair

duplicate canonicalization, removal then upsert, unknown-key omission, repeated

Host producer queue — threshold refinement adopted
The initial merge-every-pending-tail candidate passed deterministic ownership,
ordering, send-error and actual RuntimeWindow/frame/restore integration proofs.
Its 16-condition/seven-pair actual-host timing nevertheless rejects immediate
adoption: stable 128-capture bursts reduce producer+consumer work by 48.5%
(20 tabs) /84.5% (500 tabs), but stable two-capture bursts regress 18.2% /7.45%,
and eight-capture bursts regress 3.22% /7.37%. Edited-generation controls gain
no materialization or retained-payload reduction and have mixed times. Full
chronological producer/consumer/cleanup/DTO-drop samples are retained.

For 512 stable captures the prototype retains one rather than 512 envelopes and
four rather than 2,048 capture entries; the actual large shared layout payload
is 4.32 MB in both. Distinct edited generations retain 278.64 MB in both tested
variants. Header savings must not be portrayed as whole-layout memory savings
or a bound on all queued work. Producer synchronization also has a contention
cost, despite structural lifetime correctness. No production queue change was
accepted from these results.

A refinement retains ordinary owned snapshots for short backlog and starts tail
coalescing only at the existing 32-envelope consumer budget. The first 31 pending
snapshots have no mutable-slot allocation. All commands seal the current tail;
only equal window identity/order and pointer-identical launch/current layout
generations can merge. Geometry, focus and last valid ordinary frame history
are preserved. The receiver extracts owned messages and explicitly drains on
closure, preventing temporary producer slot references from retiring large
queued payloads on the producer thread. Sends share an ordering mutex; this is
not a literally nonblocking replacement for std mpsc.

Fresh deterministic proofs cover 31/32/33 boundaries, drain/refill, pending-count
publication and rollback, receiver extraction versus merge, command barriers and
receiver closure while a producer holds an upgraded slot. All 28 actual-host
integration parity cases pass with prescribed geometry and in-memory persistence;
these use actual RuntimeWindow, ProjectLayout, capture and inbox code, including
blocked persistence flush, global/loading/project changes and focus. For 512
stable captures the refinement retains 32 envelopes/128 capture entries. Edited
generations still retain the same large payloads. The atomic count includes
sender-in-flight/dequeued-before-extraction envelopes and excludes receiver-held
owned payloads; it is not a total memory bound.

The first 16-condition/seven-pair timing has roughly flat stable short-burst work
(-3.10% to +2.04%) and 51.0%/81.15% lower producer+consumer work for stable bursts
of 128 (20/500 tabs). One edited 20-tab/128-burst control regresses 16.03%; this
prompted one unchanged-binary repeat, with both runs preserved. The repeat reduces
that control's increase to 2.35%, but other controls remain mixed: edited 20-tab
bursts of two increase 9.61% and isolated stable 500-tab captures increase 5.01%.
Stable 128-capture gains repeat at 48.4%/81.9% work and 32.3%/60.2% full observed
cost, including measured cleanup/final DTO drops. Short stable producer deltas
are -0.056 to +0.066 us per capture in the repeat; long bursts add about 0.12 us.
These are fixture results under ordinary uncontrolled desktop activity, with
owned jobs serialized; they do not establish a universally faster queue. The
repeat took 11.141 seconds. These observations precede the command-layout
correction and final adoption measurements below.
The work metric sums producer and consumer phases within each sample before
taking medians; phase medians are not added. The full observed cost also includes
fixture/backend shutdown and final output destruction. Prebuilding edited layout
payloads, AppKit geometry sampling, real disk I/O and UI rendering are excluded.
The initial sequential timing harness and first contention proof substituted
command payload types. This changes enum/transport-slot layout, so the earlier
short send costs are a proxy, not exact production-channel costs. Snapshot
ownership, coalescing/inbox logic and RuntimeWindow materialization use the
current code. This limitation prompted a concrete harness correction.
Production-path review finds two principal producer threads: AppKit snapshots/UI
commands and the Unix listener's Wake. Capturing, materializing commands, close
admission, service processing and I/O happen outside the sender gate. The listener
has a 64-entry accepted-request queue, which bounds Wakes while service work is
blocked. The contention fixture uses finite Wake traffic; no hard mutex wait or
AppKit latency bound is claimed.

Final harnesses use the actual private command field definitions and matching
public HostCall, ReloadRequest and Bundle types from pinned cached dependencies.
The Service enum is 376 bytes in the default configuration and 744 bytes with
dev-reload, versus 72 bytes in the earlier proxy. Both candidate and baseline
have the same Service size/alignment in each configuration. This distinction is
material; the earlier evidence remains archived rather than silently relabeled.
Fresh default sequential proof and 20 contention cases in each feature
configuration pass, including final DTO/frame results, per-sender round ordering
and successful sends while the receiver is paused before materialization.

Further search investigation
A read-only follow-up identifies cancellable large tool-JSON preparation as a
separate candidate. Current cache limits bound retained normalized text, not the
full preparation/lowercase work for one item. A coarse chunked serializer with
reusable escaping scratch could observe cancellation between input scans, while
retaining canonical JSON and whole-string Unicode lowercase. Cancellation must
be distinct from serialization failure, never invoking an expensive fallback or
publishing partial cache entries. No implementation is claimed. Chunking would
not bound output reallocations, stack unwinding or whole lowercase/find latency.
The proof/profile plan and source fingerprints are in
  target/performance-audit/search-cancellation-next/plan.txt.
