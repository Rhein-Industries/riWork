# RiWork

**RiWork is in beta.**

A compact, themeable GPUI workspace with native Ghostty terminals on macOS. Tabs and split panes attach to shells in a dedicated tmux server, so shells and their output remain available when the UI closes. Projects own shells and worktrees; tasks belong to projects and can be assigned to worktrees.

## Requirements

- macOS with Xcode command line tools
- Rust 1.99.1 (selected by `rust-toolchain.toml`)
- Zig 0.16 for the Ghostty native build. `riwork update` uses the one unpacked as `toolchains/zig-0.16*` in the RiWork data directory (`~/.local/share/riwork` by default) when `ZIG` is not set; keep it out of `/tmp`, whose periodic cleanup deletes its standard library
- tmux (`brew install tmux`) for persistent shells
- Vim for editing files in persistent RiWork tabs (included with macOS)
- macOS 14 or later for Cua.ai desktop control; RiWork setup installs Cua Driver

## Rust workspace

The Rust implementation is divided into five packages:

| Package | Location | Responsibility |
| --- | --- | --- |
| `riwork-core` | `crates/riwork-core` | Stored models, paths, configuration, and persistence |
| `riwork-engine` | `crates/riwork-engine` | Sessions, chat providers, scheduling, and orchestration |
| `riwork-cli` | `crates/riwork-cli` | CLI and MCP commands, updater, and the headless `riwork-cli` executable |
| `riwork-desktop` | `crates/riwork-desktop` | GPUI windows, Ghostty terminals, native controls, and the public `riwork` executable |
| `riwork-remote` | `remote` | Encrypted relay, desktop connector, and remote client |

Core and engine have no GPUI or Ghostty dependency. The desktop calls the same CLI implementation before starting its UI, preserving the `riwork` command. The default workspace member is desktop; use `cargo build -p riwork-cli` or `cargo build -p riwork-remote` to build either companion independently. All Rust packages share the root lockfile and target directory. The Swift iOS app remains under `ios/`, and the desktop speech helper remains under `macos/speech/`.

## Build and run

```sh
ZIG=/path/to/zig-0.16/zig cargo build --release
ZIG=/path/to/zig-0.16/zig sh scripts/bundle-macos.sh release
open target/release/RiWork.app --args /path/to/project
```

The project path is optional but must be an existing directory. Without one, RiWork reopens the active project, or registers the current directory on first launch. Any other unrecognised argument, such as a misspelled command, prints an error and exits instead of opening a window. The bundle includes Ghostty terminfo and shell integration, and copies the named theme catalog from `/Applications/Ghostty.app` when installed. Set `GHOSTTY_THEMES_DIR` while bundling to use another catalog directory. Custom themes in your Ghostty configuration directory also work. For an unbundled `cargo run`, set `GHOSTTY_RESOURCES_DIR` to the bundle's `Contents/Resources/ghostty` directory. The bundler signs `RiWork.app` (ad hoc by default) under its bundle identifier `dev.riwork.shell` and verifies the signature; set `CODESIGN_IDENTITY` to a certificate name to sign with it instead. `riwork update` signs with a Developer ID Application or Apple Development identity from your keychain when `CODESIGN_IDENTITY` is not set (`CODESIGN_IDENTITY=-` keeps it ad hoc). An ad-hoc signature changes with every build, so macOS would treat each update as a new app and ask again for access to Documents, Desktop or Downloads when a terminal starts there; the replacement window would wait on that question until the reload gave up. With a certificate the answer holds across updates.

Use the release build for normal use. For development, `cargo build` and `sh scripts/bundle-macos.sh debug` create artifacts under `target/debug`; `cargo run -- /path/to/project` starts an unbundled development window.

To make the CLI available everywhere, link the built executable into a directory on your `PATH`:

```sh
ln -sfn "$PWD/target/release/riwork" "$HOME/.local/bin/riwork"
```

**Tests.** `ZIG=/path/to/zig-0.16/zig cargo test --workspace` runs the fast, deterministic tests across the Rust packages: formats and protocols, data safety, permissions and the chat, session and schedule state machines, with no real tmux server, agent process or timing. Use `cargo test -p riwork-core`, `cargo test -p riwork-engine`, or `cargo test -p riwork-cli` for focused backend work without the desktop UI dependency. Tests that drive real tmux, real child processes or wall-clock timing are marked `#[ignore = "slow: …"]`; run them before a release, on an otherwise idle machine, with `cargo test --workspace -- --include-ignored`. The phone connector can also be selected with `cargo test -p riwork-remote` (its ignored end-to-end tests need the setup in `remote/README.md`). Main is kept `cargo fmt`-clean (`cargo fmt --all --check` before committing), so formatting never arrives as a repo-wide diff that every open branch then conflicts with.

Run `riwork help` for the full command list and `riwork --version` for the installed version. Data defaults to `~/.local/share/riwork`; set `RIWORK_HOME` to use a separate store and tmux server. An empty `RIWORK_HOME` or `HOME` counts as unset. A newly created data directory is owner-only, and `state.json` and `sessions.json` are written with owner-only permissions.

## Encrypted iOS access

The standalone `riwork-remote` relay and outbound desktop connector let paired
mobile devices inspect existing projects/tasks/worktrees, read persistent shell
and orchestrator output, submit a line to an explicitly selected existing
session, start or close a terminal (a shell, Codex, Claude, Grok or Muse) in a
project or worktree, start the global or a project's orchestrator (a terminal
or a chat, as this Mac's Settings say; an orchestrator that runs as a chat is
followed and driven with the chat methods), and create a new project in the default projects folder
(the phone names it and never chooses a location). A running RiWork window adds
a tab for a terminal started this way (or by `riwork shell create`) behind its
current one, without taking focus, and lists a project made this way (or by
`riwork project create`) in its Projects panel within a couple of seconds. A phone can
also send a photo or a file to a terminal, whose program gets its path as from a drop on
the terminal, or to a chat, whose message gets its path (see **Files from the phone**
below). Each device has independent endpoint secrets and revocable access; the
relay routes encrypted frames without session content or pairing secrets.

The [iPhone and iPad app](ios/README.md) opens with an **All hosts** dashboard for
its paired desktops: work in progress, decisions waiting for you, projects and
open tasks. Each row names its host, and choosing a desktop opens that host's
dashboard. Unavailable hosts retain their last successful read with an age;
partial totals say how many hosts were read. Looking at a dashboard creates no
sessions or projects. A decision opens its original approval choices or question,
then checks the exact host, chat and current request again before sending your
explicit response. An uncertain response is never retried automatically.

**Haiku dashboard summaries** is an optional desktop setting beside the saved
Anthropic API key. It is off by default and uses separately billed API requests
to `claude-haiku-5-5` to summarize observed activity. The desktop and phone show
these summaries with their freshness; actionable decisions still come from
provider requests. Unchanged evidence is reused, requests are at least one minute
apart, and each host is limited to 120 requests per day. Missing keys or API
failures leave the underlying dashboard available. See
[dashboard decisions](docs/dashboard-decisions.md).

For a connected Clicks keyboard with the software keyboard hidden, the phone puts
project tabs at the bottom and treats physical **Tab** as a shortcut prefix:
**Tab Q** sends a normal Tab, **Tab E** sends Escape, **Tab W/A/S/D** moves with
arrows, and **Tab 1–9** switches tabs. Hold Tab for one second to see the full map.
The Standard profile and touch Tab keep their usual behavior. Choose the Clicks
profile in **Display → Keyboard** if iOS reports a generic keyboard name; see
[keyboard controls](ios/README.md#project-and-terminal-tabs).

```sh
cargo build --locked --release --manifest-path remote/Cargo.toml
export RIWORK_REMOTE_BIN="$PWD/target/release/riwork-remote"
riwork remote --help
riwork remote start --riwork /absolute/path/to/riwork
```

Build the standalone binary before bundling to include it beside the desktop
CLI. `RIWORK_HOME` is retained. Stopping the transport preserves tmux and harness
state. Mobile tabs can temporarily resize the existing tmux grid to their visible
terminal area; disconnect restores desktop sizing and keeps the same process.
Follow [pairing and test instructions](remote/README.md), the
[frozen mobile protocol](docs/remote-protocol.md), and
[TLS relay deployment](docs/remote-deployment.md). v1 supports captured terminal
text and single-line input, with persistent request deduplication and explicit
unknown-outcome errors.

Open the native iPhone/iPad project in [ios/RiWorkRemote.xcodeproj](ios/RiWorkRemote.xcodeproj).
See [iOS setup and verification](ios/README.md) for building, pairing and continuing
in the compact project and terminal-tab interface.

## Controlling another Mac

A second Mac running RiWork can open this Mac's projects and shells as real terminals, with the fidelity of a local one (colors, mouse, full-screen programs, scrollback). The shells stay on the Mac they belong to, in its own tmux; a tab on the other Mac only attaches to one, so closing the tab, closing the window or losing the connection never ends the shell. The two Macs talk through the same encrypted relay as the phone companion, and the app needs the `riwork-remote` binary next to it, as `riwork remote` does.

**Pairing.** On the Mac whose shells you want to reach (the host), open Settings → **Remote** → **PAIR ANOTHER MAC**. Name the other Mac, give the relay's `wss://…/v1/ws` URL and the relay's routes file (it starts at `RIWORK_HOME/remote/relay-routes.json`). RiWork runs `riwork-remote pair --protocol 2 --kind desktop` and shows a single-use link that expires after about ten minutes, with **COPY LINK**. Add the route `pair` appended to your relay's routes and restart the relay, exactly as for a phone. The link is a secret: it is held only while the dialog is open, is never written to disk or a log, and is shown cut short. On the other Mac, Settings → Remote → **ADD HOST**, paste the link, and optionally name the host; RiWork runs `riwork-remote hosts add --link -` and hands it the link on standard input, never on the command line. Settings lists every paired Mac with its link state; **REMOVE** (click twice) forgets one, and it must send a new link to be paired again. A paired Mac has the same authority as a phone, which includes typing into any terminal, so pair only Macs you control. Revoke one on the host with `riwork remote revoke DEVICE_UUID`.

**A paired Mac is a folder.** In the Projects panel each paired Mac appears below your own folders, named after it, with a small dot: cyan for online, gold for connecting, a hollow grey one for **Offline (or access revoked)**, which is all RiWork can tell about a sleeping Mac and one that revoked this one. Its projects are listed inside as ordinary project rows with the same figures (trees, done/all tasks, live shells), ordered and searched like the others (a Mac has no file times to sample, so **Last edited** follows the date a project was added). The folder opens and closes like the others, but it cannot be renamed, moved or removed here. The rows are read from the Mac only while the Projects panel shows the folder, and the figures a few projects at a time; a Mac that cannot be reached keeps listing what it listed last, dimmed. That list is kept in `remote-ui.json` in the RiWork data directory (mode 600), so a restart shows it before the Mac answers. **+** on the folder asks for a name and creates the project on that Mac with `project.create`, in its default projects folder. It is sent once and never retried: if no answer comes, the folder says the project may exist and asks for its list again, and trying again is up to you.

**Selecting a remote project** works like selecting a local one. It becomes the window's project, under its own layout, and the window title and status bar name it with its Mac, as in `RiWork · app (on Studio)`. Its ids are kept as `remote:{host}:{project}` wherever the window stores a project, so they can never be looked up in, or collide with, this Mac's store; nothing local is created for it, and selecting it does not change the active project that `riwork` commands use. The panels follow:

- **Worktrees**, **Tasks** and **Shells** list what the Mac reports (`worktrees.list`, `tasks.list`, `shells.list` and `orchestrators.list`) while they are on screen. Tasks are read-only, as the Mac offers no task changes. Choosing a worktree does what it does locally: it becomes the one new terminals start in, and a tab already open on one of its shells is shown, else its newest live shell is opened, else a plain shell is started in it on the Mac with `shell.create` and opened, in the pane that is selected. That shell is made once; a second click while it is being made does nothing, and nothing is ever sent again unasked. Choosing a shell opens it as a tab.
- **New Tab** (the **+** menu, Cmd+T and the Codex, Claude, Grok and Muse shortcuts) asks the Mac for a Shell, Codex, Claude, Grok or Muse in the selected worktree or the project's root with `shell.create`, then opens it. An agent is unrestricted or not as **Agent terminals run unrestricted** in this Mac's Settings says, and the request says which, so the other Mac's own setting does not decide. Like a project, it is sent once and never retried. The orchestrator entries open the Mac's own orchestrator if it has one running in a terminal; one that runs as a chat there has no terminal to attach to, and a notice says to open it on that Mac or in the iOS app. A split starts empty, as nothing is made on the other Mac unasked.
- **Files**, **Preview**, **Project settings**, **Schedules** and **Usage** have nothing behind them for another Mac's project yet, and say *Not available for a project on HOST* instead of showing this Mac's data. The status bar shows the project, the worktree, the live shells and the active tab's id; agent activity and resources show a dash, and usage and the Codex account are left out, as they are this Mac's own.

A window opens on the same remote project after a restart or a reload. If the Mac is offline then, the folder shows the kept list, dimmed, and the connection is made in the background.

**Tabs.** A remote tab is titled `⇄ HOST · …` and the host mark is drawn in magenta. Its terminal runs `riwork-remote attach --desktop ID --shell UUID`, a bridge to the host's tmux client through that host's client daemon (`riwork-remote client ensure` starts it on demand), so hiding, releasing and re-attaching a terminal work as for a local shell: the host's tmux repaints the screen. Remote tabs are saved in the remote project's layout as `remote_shell` tabs and come back with the window; a build without this feature keeps them untouched. While the daemon's link to the host is down, a **RECONNECTING · HOST** strip sits above the terminal. When the shell ends on the host, the bridge exits and the strip says **Ended on HOST** until the tab is closed; **RECONNECT** starts the bridge again in case it was only the connection that ended.

## Update and restart

```sh
riwork update                 # Build release, install it, and reload all open RiWorks
riwork update --debug         # Explicit development build
riwork restart                # Quickly restart all open windows using the installed build
riwork reload                 # Compatibility alias for restart
riwork instances --json       # Inspect running apps and their windows
riwork restart --session      # Also resume this RiWork-hosted Codex conversation with Cua
```

`restart` restores every open RiWork app and window using the latest installed build,
without rebuilding. Use `update` to build and install the current source and restore all
windows in one command. `reload` remains an alias with the same behavior; `--all` is
accepted for compatibility because both commands always include all running apps.

Reloads preserve each window's project, layout, position, and persistent shells. The old app exits only after its replacement has restored the windows. If the replacement has not confirmed within 25 seconds, the old app keeps its windows, stops the replacement it launched (SIGTERM, then SIGKILL after 3 seconds, sent to the replacement's own process group only after its pid and start time are checked) and records why in the reload report, including, when known, the terminal session the replacement was stuck attaching and the diagnostic file under `~/Library/Caches/riwork/runtime/diagnostics/` to read. A replacement that no one is left to stop ends itself 40 seconds after starting to restore, unregistering first. Stopping a replacement closes only the terminal clients attached to it; the tmux sessions and their agents keep running. Running agents stay attached to their existing tmux sessions. Apps opened before reload support was installed need one normal quit and reopen first. A running app relaunches only as its own executable or the build recorded by `riwork update`; it refuses any other path found in a reload request. A running app whose registration this build cannot read (an incompatible version) is reported as a warning instead of being silently skipped, and counts as `unreadable_registrations` in `--json` output. `reload` and `update` still reload every readable app, then exit non-zero because that process keeps running its old build; quit and reopen it, or run `riwork reload` from the build that started it.

`update` builds and packages your local source in a staging directory, including `riwork-remote` when the checkout contains its manifest, then installs the executable and app together. A companion failure preserves the previous installation. It defaults to an optimized release build, including when run from a debug CLI. Use `--source /path/to/riWork` to choose a checkout, `--debug` for a development build, or `--no-reload` to install without reopening windows. `--release` selects the default explicitly; it cannot be combined with `--debug`. The command does not fetch or change Git history. Later `open` and `reload` commands use the latest successfully installed app, including when its profile or source checkout differs from the CLI's. Build failures keep the installed app running and retain a diagnostic log.

Before anything is replaced, `update` checks the staged bundle's code signature and starts both the staged executable and the one inside the bundle with `riwork help`. A build that compiles but fails to start is rejected, and the installed build stays as it was. The build being replaced is kept next to the new one as `RiWork.app.previous` and `riwork.previous` in `target/<profile>` until the next successful update replaces them. `update` prints the `.previous` location and repeats it if the reload fails. To roll back after a bad update:

```sh
cd target/release   # or target/debug
mv RiWork.app RiWork.app.bad && mv RiWork.app.previous RiWork.app
mv riwork riwork.bad && mv riwork.previous riwork
riwork reload
```

Ctrl-C, closing the terminal, or SIGTERM stops the running cargo, rustc, or bundler process group and removes the staging directory; the installed build is untouched. Each update begins, under its lock, by removing staging directories left by interrupted runs and all but the five most recent `target/riwork-update-*.log` files. A staging directory kept after a failed install is retained for a week.

`--session` applies to the current RiWork Codex pane. It waits for the active turn to finish, then resumes the same conversation UUID through RiWork's Cua launcher. Other agents keep running. New RiWork launches bind tool commands to their own terminal even when Codex shares a backend. For an older launch without that binding, use `riwork reload --session --shell SHELL_UUID`, selecting the conversation's terminal UUID from RiWork. Use it after installing a new harness integration; reopening the app alone cannot replace the tools of an already running agent.

## Cua.ai setup and computer use

RiWork uses [Cua.ai's Cua Driver](https://cua.ai/cua-driver) for computer use across Codex, Claude, Grok, Muse, and the global and project orchestrators. On a machine without the driver, the app opens Settings with **SET UP CUA**. Setup downloads Cua's official stable installer over HTTPS, installs the signed `CuaDriver.app`, and prepares the shared connection. You can also run:

```sh
riwork setup
riwork cua status --json
riwork cua permissions
```

Select **GRANT MACOS ACCESS**, then enable **CuaDriver** in macOS **Privacy & Security → Accessibility** and **Screen & System Audio Recording**. These permissions belong to CuaDriver and need to be enabled once in System Settings. Approve CuaDriver's direct screen capture prompt when macOS shows it. Settings reports the grants and capture verification, and offers **CHECK AGAIN** after enabling them. RiWork launches its driver in standard permission mode. The explicit grant action restarts the shared service with Cua's permission onboarding so updated grants are read by a fresh process.

**The cua-driver skill.** Cua Driver ships an agent skill pack, a directory it names with `cua-driver skills path` (normally `~/.cua-driver/skills/cua-driver`). Setup, and only setup (`riwork setup`, `riwork cua setup`, **SET UP CUA**, or **LINK CUA SKILL** when the driver is ready but a CLI lacks the skill), asks the driver for that directory once the driver has passed RiWork's identity check. When the pack is not there, setup runs `cua-driver skills install`, Cua's own way to fetch it, which also links the agents Cua Driver itself detects and never over an existing path. RiWork then links the pack, as a symlink named `cua-driver`, into the user skill directory each CLI reads:

| CLI | Skill link | Notes |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/cua-driver`, and `$CLAUDE_CONFIG_DIR/skills/cua-driver` | Claude Code does not read `~/.agents/skills`. |
| Codex | `~/.agents/skills/cua-driver` | Codex reads it whatever `CODEX_HOME` is, so the system home and every Orca account home RiWork binds share one link. Orca's account homes are not written. |
| Grok | `~/.grok/skills/cua-driver`, and `$GROK_HOME/skills/cua-driver` | Grok also reads `~/.agents/skills` and `~/.claude/skills` and lists one skill per name. |
| Muse | `~/.config/muse/skills/cua-driver`, and `$XDG_CONFIG_HOME/muse/skills/cua-driver` | `~/.local/share/muse/skills` only caches Muse's bundled skills. Muse also reads `~/.agents/skills`. |

The second location applies when RiWork itself runs with that variable, which its sessions inherit; an app opened from the Dock has none of them. A variable that is a relative path is reported as unsupported, since each session resolves it from its own directory. A CLI with no home on this Mac is skipped: no `~/.claude`, `~/.grok` or `~/.config/muse` (Muse creates it whenever it runs), and for Codex none of the homes it is launched with. Setup creates the directories that lead to a link it makes, such as `~/.agents/skills`, never a CLI's home. It never replaces or removes a file, a directory or a link it did not make, and does not create through a `skills` path that is a file or a link to a missing directory: such a path is reported as blocked and left as it is. The links RiWork made are recorded with their target and inode in `RIWORK_HOME/cua/skill-links.json`. Only a link that is still that very link is repointed when the pack moves, by an atomic exchange that puts back anything else it finds; a link Cua Driver or anyone else made, even to the same pack, stays theirs, and counts as linked when it resolves to the pack. `riwork cua status` (and `--json`, under `skills`) reports each location with its path as `linked`, `missing`, `stale`, `blocked_by_foreign_path`, `pack_missing`, `home_absent` or `unsupported`. Status, app start, and shell, harness and chat launches only read these directories. A linked skill is found by sessions that start afterwards; a running session keeps the skills it started with. Settings shows the driver's readiness and each CLI's skill link separately. The MCP connection and RiWork's computer-use instructions are unchanged and do not depend on the skill.

RiWork runs Cua's installer with a minimal environment: `PATH`, `HOME`, `TMPDIR`, the locale, proxy and certificate settings, and Cua's telemetry variables. Tokens and API keys in your shell, such as `GH_TOKEN`, are not passed to it. After installing, and before it launches or runs the driver, RiWork checks that `/Applications/CuaDriver.app` carries Cua AI, Inc.'s Developer ID signature (bundle identifier `com.trycua.driver`, Team ID `YCK386LBJ7`) and that macOS accepts it as notarized (`codesign --verify` and `spctl --assess`). An app that fails is not launched; the error explains how to reinstall it. RiWork remembers a successful check until the app on disk changes, so normal startup does not repeat it. The driver must live inside that app; a `cua-driver` elsewhere on `PATH` is not used. An installer that times out is stopped with SIGTERM so it can release its lock, and RiWork removes a leftover lock under `RIWORK_HOME/cua/package/packages/.install.lock.d` when the process recorded in it is gone. A slow first start of the driver after boot is retried and never triggers a reinstall.

**Telemetry.** Cua's installer states that telemetry defaults to enabled for new installations, and that it collects no prompts, tool arguments, screen contents, or file paths. RiWork captures the installer's output, so you do not see that notice, and it does not change the default. To opt out, run `RIWORK_HOME/cua/bin/cua-driver telemetry disable` after setup (for the default state directory, `~/.local/share/riwork/cua/bin/cua-driver telemetry disable`), which is the command Cua's installer prints. RiWork also forwards `CUA_TELEMETRY_ENABLED` and `CUA_DRIVER_RS_TELEMETRY_ENABLED` from the environment of `riwork setup` to the installer, but the command changes the driver's own persistent setting.

New RiWork Codex, Claude, Grok, and Muse launches receive the same `cua-driver` MCP connection and computer-use instructions (a Muse terminal as an `mcpServers.cua-driver` entry passed with `-c`, its instructions riding its first message, as Codex's do; a Muse chat names the same server for its session only, see [Chat host](#chat-host)). Codex's OpenAI computer-use feature is disabled for these launches. Existing model, account, and harness permission preferences are retained. New plain shell tabs include RiWork's Codex, Claude, Grok, and Muse launchers on their `PATH`, so starting any CLI from a shell tab uses the same integration. An absolute path to a separately installed CLI bypasses those launchers. RiWork runs the CLI under the name it finds it by, so version-manager shims such as mise's and Volta's keep working, and it skips a file that is not executable. When the app is opened from the Dock or Finder its `PATH` lacks the directories that nvm, pnpm, bun, pyenv and similar tools add. If a CLI is not found on the app's own `PATH`, RiWork asks your login shell (`$SHELL`, else `/bin/zsh`) once per process, without a terminal and within three seconds, for the `PATH` a terminal would have, and gives Codex, Claude, and Grok tabs that `PATH` after the launcher directory. A shell that fails or hangs is ignored. Existing running harnesses need to be restarted to load the new connection; closing and reopening a terminal tab only reattaches its running session.

The MCP connection runs through `riwork cua mcp`, which resolves the installed driver without depending on the agent's `PATH`. It stays running as a small stdio proxy between the agent and `cua-driver mcp` instead of replacing itself with the driver, so a driver or desktop service restart (for example when the service is replaced or ends) no longer drops computer use for agents that are already running. Messages are forwarded line by line, unchanged and in order, and the driver's stderr goes to the proxy's stderr. When the driver's MCP process ends while the agent is still connected, every request it had not answered gets the JSON-RPC error `-32000` "Cua Driver restarted; retry the request" (with the request's id unchanged); the proxy then makes sure the desktop service is running through the same signature-checked start as a first launch, starts a new driver, replays the agent's `initialize` and `notifications/initialized` (the replayed answer is not passed on) and, when the driver declares that its tool list can change, sends `notifications/tools/list_changed`. Requests that arrive while the driver is down get the same error at once instead of waiting. A failed restart, including a failed handshake replay, is retried after 1, 2, 5, 10 and then every 30 seconds; a driver that stayed up for 30 seconds starts the schedule over. Restarts are also recorded in `RIWORK_HOME/cua/driver.log`. The proxy exits only when the agent closes its input, after stopping the driver. A single message over 16 MiB is a protocol error: one from the agent is dropped and answered with an error that has a null id, and one from the driver makes the proxy restart the driver and fail the requests it was serving. A driver that cannot be started at all when `riwork cua mcp` launches still fails the launch with the reason. For a custom driver installation or isolated tests, set `RIWORK_CUA_DRIVER` to its executable (an empty value is ignored). This developer override skips the signature and notarization check, since it names a different binary on purpose, and is passed to each harness's MCP server so `riwork cua mcp` uses the same driver. New tmux sessions receive it in their environment too, so a `codex`, `claude`, or `grok` typed in a plain shell tab uses the same driver. When several agents start together against a stopped desktop service, the later ones wait up to 30 seconds for the first to start it instead of failing. If the RiWork binary a launcher points to has moved or been deleted, the launcher warns and runs the next `codex`, `claude`, or `grok` on `PATH` outside RiWork's launcher directory until the app regenerates them. Setup keeps its managed launchers under `RIWORK_HOME/cua` and does not edit your global Codex, Claude, or Grok configuration or shell startup files; outside `RIWORK_HOME` it only adds the skill links described below, plus what Cua's own `cua-driver skills install` does when the pack is missing. Grok receives a session-scoped agent definition from `RIWORK_HOME/cua/grok-agent-*.md`; its model and login still come from Grok's own profile, while RiWork's agent definition replaces Grok's default agent selection for that session. Each launch refreshes the definition it uses and removes ones that no launch has used for 30 days. Before a Grok tab or a `grok` typed in a RiWork shell starts, RiWork starts Cua Driver when its desktop service is down and completes an MCP handshake. That work finishes before Grok's 30-second MCP startup limit begins. When neither `GROK_MCP_STARTUP_TIMEOUT_SECS` nor `MCP_TIMEOUT` is already set, that Grok process receives `GROK_MCP_STARTUP_TIMEOUT_SECS=120`, the same startup budget Codex is given. A value you already set is forwarded unchanged. When both are set, Grok applies `MCP_TIMEOUT` (milliseconds) over `GROK_MCP_STARTUP_TIMEOUT_SECS`. A per-server `startup_timeout_sec` in your own `config.toml` still wins, and RiWork does not edit that file or put a timeout in Grok's agent definition, which has no effect on the handshake limit. Grok still owns that limit. On 1.0.44 a headless first prompt can be sent before the session has folded this handshake into the turn, even when the server answers in well under a second, and a slow handshake is only waited on for about two seconds before that prompt proceeds. The tools are registered on the session for a later prompt. If the check fails, Grok is not started and the message names the cause, how long the check took, and `RIWORK_HOME/cua/driver.log`. RiWork's zsh tabs forward your startup files through a session directory and restore the launcher prefix after their PATH changes. Custom shells, aliases, and nested shells can override that PATH; direct RiWork harness launches always receive the connection.

**Input to RiWork's own windows is refused.** The proxy refuses, by default, the tool calls that would send input to the RiWork app you are working in, whose windows hold your orchestrator chats and terminals: any call that names a running RiWork app's pid (`pid` or `target.pid`), whatever the tool; while RiWork runs, input tools (clicks, typing, keys and hotkeys, drags, scrolls, `set_value`, menus, `bring_to_front`, `set_window_frame`, `kill_app`, replayed trajectories, and moving the real pointer) that are not aimed at one app's window by its `pid`, since desktop-scope, frontmost-app and bare element-token input could land in RiWork (agents are told to pass `pid` on every input call); and `launch_app` of RiWork itself. The agent gets a tool error that says why, the driver never sees the call, and the proxy notes it on its stderr and in `RIWORK_HOME/cua/driver.log`. Read-only tools (window state and screenshots, window and app lists, accessibility trees, health) are unaffected, and so is input to every other app. Running means registered in your own runtime registry (`~/Library/Caches/riwork/runtime`, whatever `RIWORK_RUNTIME_DIR` says), so a fixture RiWork started with its own `RIWORK_RUNTIME_DIR` and `RIWORK_HOME` can still be driven for isolated UI checks. All of RiWork's windows, terminal panes included, belong to its one process, and a tool call names no window RiWork records, so the guard covers every window of a running RiWork, not only those that show an orchestrator. To allow it on purpose, start a terminal session with `RIWORK_CUA_ALLOW_RIWORK_INPUT=1` (exactly `1`) in its environment, for example `RIWORK_CUA_ALLOW_RIWORK_INPUT=1 claude` in a RiWork shell tab: RiWork passes it on to that session's `riwork cua mcp` (harnesses filter their MCP servers' environments otherwise) and names it on the pane of each terminal it launches from that environment, and a proxy started with it says so in `driver.log`. The tmux server and the chat host, which outlive any one launch, never keep it, so chats, orchestrator chats included, are always guarded. The proxy reads it once, when it starts, so nothing an agent does later turns the guard off for a session that is already running. The guard is a safety net against accidents, not a sandbox: an agent that runs the `cua-driver` CLI directly goes around it, which is why the orchestrator skill's Hard boundaries forbid input to live orchestrator windows by any means.

RiWork also serves a local MCP connection over stdio with `riwork mcp`. Configure an MCP client to launch that command to give Codex, Claude, Grok, or Muse project, worktree, task, shell, orchestrator, and schedule tools. Many tools only read state, but others change it: they register projects and worktrees, start shells (a `command` runs as an arbitrary program), send input to shells, and edit schedules whose prompts RiWork later types into an agent. Each tool's `annotations` mark its read-only and destructive behavior accordingly; for example `riwork_worktree_list` is not read-only because refreshing writes newly found worktrees to RiWork's state. Every tool rejects arguments outside its `inputSchema` instead of ignoring them, and failed schedule calls set `isError` without `structuredContent`. The server accepts JSON-RPC batches and answers malformed input with a JSON-RPC error. It uses the same state as the CLI and GPUI app.

`riwork worktree create --base REF` chooses the start point of a new branch only; if the branch already exists it is checked out as is and `--base` is ignored (the MCP `base` argument behaves the same). Projects, Worktrees, Tasks, and Shells each have a searchable panel tab. Projects lists all projects; the other panels show the active project's items. RiWork discovers Git worktrees created outside the CLI during refresh. A removed worktree disappears from the Worktrees panel, project worktree counts, and chat and automation destination choices after a background folder check. Its record stays registered so task and shell references keep their UUIDs, and a restored folder returns to the GUI with that same UUID. The project's root stays visible when unavailable. Use `riwork worktree forget ID` after its tasks and shells are gone to remove the stale record.

Use the Projects sort selector beside the project count to choose **Last edited**, **Name**, **Date added**, or **Live sessions**. The arrow reverses the order. Projects sort within their virtual folders while the folder hierarchy stays intact; search and collapsed folders keep working. The preference is saved and shared across windows. Last edited defaults to newest first and reads the latest source-file modification time across each project's roots and registered worktrees, respecting Git ignores and excluding common build and dependency directories. Windows ask every 30 seconds, shared by all of them, and wait while a window is covered, minimized or on another Space; the next tick after it shows again catches up. Each root is scanned once when first asked about, and macOS file-change events (FSEvents, one stream for all roots) keep its date current after that: an edit to a file that counts updates the date from that one file, and a root is scanned again only when something its date cannot absorb happened (the newest file was deleted, replaced or dated earlier, a file appeared that Git may list, an ignore rule or the Git index changed, or events were lost), and as a safety net every 20 to 30 minutes, so an idle machine scans nothing. If the stream cannot be made, or a root is on a volume that does not report changes, its scan repeats every 30 seconds as before. Each root is scanned within its own limits, and a project shows the latest edit among the roots whose scan completed, so one very large or unreadable root does not hide the others. Unavailable dates sort last; commit dates, deleted files, and task activity are not used as file-edit timestamps. Each time a window's scan finishes, the app publishes the dates to `project-recency.json` in the RiWork data directory (mode 600, replaced atomically, left alone when nothing changed), so `riwork project list --json` and the phone can order projects the same way: only the app can scan, so the CLI just reads the file. A project that a scan could not date keeps its last published date, a removed project's date goes, and since a hidden window does not scan, the dates are as of the last time a window was showing.

Press **Cmd+Shift+E**, or choose **FILES** under **Views** in a pane's **…** actions menu, to browse the current worktree. The explorer follows the focused shell's worktree, including moving into another registered worktree with `cd`. Select a regular file and click **Edit in Vim**, double-click its row, press Enter in the tree, or press **Cmd+E**. RiWork opens Vim in a dedicated persistent terminal tab in that worktree; existing agent shells keep running. Vim's normal editing, `:w` save, `u` undo, and `/` search work in the tab. The editor tab restores with the project layout while its tmux session is alive. Return to Files and select the file to edit it again; a live Vim tab is reused even after saving, and whether you open the file from the project root or its primary worktree. Symlinks and files outside the worktree cannot be opened for editing from Files.

Choosing a file shows a read-only preview of it in the **PREVIEW** panel. Files and Preview are two tabs of the normal pane system, so you can split, resize, lock, drag and close each like any other panel; Files draws only the tree. The preview follows the selection of the same window's Files panel, which is scoped to that window's selected worktree. Choosing a file (a click, or the arrow keys in the tree; the first row a freshly loaded tree picks for itself does not count, and neither does a folder) when the window has no Preview tab opens one in a new pane of its own, and never hides your terminal or resizes a locked pane. If the Files pane is not locked it is split: the preview goes to its right when that pane is at least 620 px wide, otherwise below it when it is at least 700 px tall, and the tree keeps 36% of a side-by-side split and half of a stacked one. A locked Files pane (the left navigation pane is locked by default) or one too small to split is left alone, and the roomiest other unlocked pane that fits the same sizes is split instead: it keeps 60% and its selected tab, so a shell stays on screen, and the preview takes the other 40%, to its right or below it. Only when no pane can be split does the preview become a tab: selected in the roomiest unlocked pane that is not showing a terminal, or waiting unselected in the tab strip of one that is (then a locked pane, then the Files pane itself), and **Cmd+Shift+P** or the tab brings it forward. Splitting a terminal pane resizes that terminal. A Preview tab that is hidden behind another tab of its pane is brought forward when you choose a file, except when it shares a pane with Files, where it would hide the tree, or when the tab in front is a terminal, which you chose to look at there. Keyboard focus stays in the tree, so the arrow keys keep moving the selection while the preview follows. You can close the Preview tab (in a locked pane, unlock it first); **Open the preview when a file is selected** in Settings (on by default) decides whether choosing a file opens it again, and with it off a closed preview stays closed. All of this placement is for a window without a main pane (see **Main pane** below); with one, the Preview is a tab of the main pane and nothing is split for it.

The preview shows text, code, Markdown source, raster images (rotated by their EXIF orientation, shrunk to 1800 px if larger and never enlarged), or PDF pages. Moving the selection with the arrow keys previews after a short pause, and the previous preview stays up until the next one is ready. PDFs are parsed only on request: click the file, press Enter, or use **Preview PDF** in the placeholder. Drag the divider between the two panes to resize them. The file actions sit in the preview header, to the right of the file's name; in a narrow preview the name is shortened before the actions move to a line of their own, and any message about an action appears directly under the header. With **Icons instead of labels** on, they are compact icon buttons with tooltips. Text previews stop at 1 MiB and image or PDF previews at 24 MiB; unsupported or binary files show a message. A folder lists at most 5,000 entries, followed by a row counting the rest, and collapsed folders are not rescanned until expanded again. **Open Externally** uses the default application, but refuses symbolic links, executables, and applications, scripts, or installers such as `.app` and `.command` with an inline message; use **Reveal** for those. **Reveal** and **Copy Path** act on the selection. **Copy Contents** puts the selected UTF-8 text file's exact contents on the clipboard, unclipped and with its line endings intact, and stays disabled for binary files, images, PDFs and files over 1 MiB rather than copying part of one. **Refresh** updates the tree and preview, **Hidden** includes dotfiles, and **Cmd+F** filters files in directories already loaded (from the Preview pane it goes to the filter when Files is on screen). Use arrow keys in the tree and Tab to step through the controls of the pane you are in: the filter, tree and buttons in Files, the preview and file actions in Preview. **Cmd+Shift+E** and **Cmd+Shift+P** move the keys between the two panes. Left/Right on a PDF preview change pages, and **Cmd+O** opens externally. Files and Preview tabs restore with each project's layout; a layout saved before Preview existed has only Files, and the preview appears the first time you choose a file.

Each pane has a **lock** control. Locked panes keep their tabs, selected tab, and surrounding split sizes across project switches; panel contents still follow the selected project. The left navigation pane is locked by default. Unlock it to let that region use each project's saved layout. Locked shell tabs keep their original shell session and project context. A locked pane's tabs cannot be closed and the pane itself cannot be closed (see below); unlock it first. When the window or the pane area is resized, locked panes keep their width and height and unlocked panes absorb the change, except that a locked pane which is the only pane along an axis follows the window along it; if the window gets too small, locked panes shrink only as far as needed to leave the others a minimum size.

**Main pane.** When locks, a Files tree and the Preview all want room, one pane can say where things go. Choose **Main pane** in a pane's **…** menu (**Pane** section; a check mark shows it is on) to make that pane the **main pane**. A star marks its header (the word MAIN with **Icons instead of labels** off), and a click on the mark, or **Main pane** again, clears it. A layout has at most one: choosing another pane moves it. It is saved with each project's layout, so every project keeps its own, and a restart or a reload brings it back. A build from before the main pane opens that layout as usual and ignores it. Without one, nothing below applies and every placement rule is the one described elsewhere.

With a main pane, and outside focus mode (which shows a single pane, so nothing is sent where it cannot be seen), these go to it:

- **New tabs open in the main pane** and become its selected tab, wherever the menu was opened: Cmd+T, **New Tab** (shells, Codex, Claude, Grok, Muse, orchestrators), the Vim editor from Files or Cmd+Shift-click, and, for a project on another Mac, the shell made on it. A terminal that appears by itself (`riwork shell create`, the phone), and one made while the project was closed, joins it too, behind the tab shown. Splitting (Cmd+D) still makes a pane of its own.
- **Clicking a shell** in the Shells panel, a worktree in Worktrees or the project orchestrator (**P·ORCH**) opens its tab in the main pane (the global orchestrator opens in the [global window](#orchestrator) instead). A tab that is already open is reused, never opened twice. It is selected where it is when it is in the main pane, already on screen, or in a locked pane (a click never takes a tab out of a locked pane), or when the tab in front of it is not a terminal. If it is behind a terminal in an unlocked pane it moves into the main pane, so that the terminal stays.
- **The Preview and Files are tabs of the main pane**, not splits: for a file chosen in the tree (when **Open the preview when a file is selected** is on), Cmd+Shift+P when there is no Preview yet, and a Cmd-clicked path or folder in a terminal. The tab becomes the selected one, except where that would hide what is in use: a Preview never covers a tree that is on screen (if the tree is a tab of the main pane itself, the Preview waits in its tab strip), and a link clicked in a terminal of the main pane leaves the Preview waiting there too (a notice says so). A Preview that is already open stays on screen where it is; one hidden behind a panel is brought forward where it is, and one hidden behind a terminal, or behind the tree, moves into the main pane. A Preview or Files tab is the one thing taken out of a locked pane without being asked to, because bringing it forward there would cover the tree. Keyboard focus stays where it was: in the tree, in the terminal clicked, in the new tab.
- **Closing a pane** (**Close pane**, Cmd+Shift+W) moves its tabs, in their order, to the end of the main pane instead of closing them; the main pane keeps showing what it showed. A locked pane cannot be closed, so its tabs never move this way. Closing the main pane itself closes its tabs as it always did (their shells keep running) and leaves the window without a main pane until one is chosen; closing its last tab leaves the pane empty, where new tabs still open.
- **Gather tabs into main pane** (**Pane** section of the **…** menu once a main pane exists, **View → Gather Tabs into Main Pane**, **Cmd+Shift+M**) moves the tabs of every unlocked pane into the main pane, pane by pane in layout order, and removes the panes this empties. Shells keep running: a gather moves tabs and closes none. Locked panes are left as they are, with their tabs, their selected tab and their size; so a pane whose room would go to a locked neighbour stays, empty, and the notice says so.

A locked pane can be the main pane, but only if you choose it; nothing makes one on its own. The lock still keeps its tabs from closing (their X stays hidden), and it takes what you open, but not terminals that appear by themselves or a project's earlier shells, which nobody asked to put in a locked pane. A locked main pane stays the main pane across project switches with the rest of the locked pane; otherwise the main pane belongs to the project's own layout.

**Layout menu.** The **LAYOUT** item at the right end of the status bar (a small layout icon, with the word beside it when **Icons instead of labels** is off) opens a short menu above it; click it again, click elsewhere or press Escape to close the menu. Show, hide or move the item in **Settings → Status bar**. A status bar saved by an earlier build gets the item shown at the end of its right side, and hiding it keeps it hidden. The menu has three rows:

- **Default layout** (also **View → Default Layout** and **Cmd+Option+L**) arranges the window as the left navigation pane is meant to be used. On the left is a **locked** pane, at the width a new project's navigation pane starts with, holding exactly Projects, Files, Worktrees, Tasks and Shells, in that order. On the right is one **unlocked pane that becomes the main pane** and holds every other tab. Tabs are only moved, never closed, so shells keep running (a shell of another project that a locked pane carried here leaves the lock, and the notice says it is no longer part of this project's layout). The panes are read in layout order and the tabs of each in their own order, so the right pane lists them as the window showed them. The tab that was selected in the selected pane is still selected, in the pane it lands in, and that pane is the selected one; the other pane shows a tab that was showing in the window (the right pane the main pane's first, the left pane a navigation panel that was showing, else Projects). A navigation panel goes to the left pane wherever it was, and one that was not open is opened there. Panes that were locked are replaced like the others and their tabs placed by the same rule, so the new left pane is the only locked one. Panel tabs that are not navigation panels (Preview, Usage, Settings, Schedules, Project settings) go to the right pane if they were open, and none is opened or closed. Focus mode ends first. A window that already looks like this (a locked left pane with exactly those panels, and one unlocked main pane on the right) is left as it is, widths included, and the notice says so. The result is saved with the project's layout like any change made by hand, so each project keeps its own, and the locked pane travels across project switches like any locked pane.
- **Gather into main pane** (Cmd+Shift+M) is the gather described above. It is greyed out until a pane is the main pane.
- **Main pane: …** says what the main pane shows and how many tabs it holds (*empty* for a main pane with none), or *none* when there is no main pane. It is only a readout: when there is none, it says to choose **Main pane** in a pane's **…** menu.

Projects, Worktrees, the Shells panel, the status bar and shell tabs show what each Codex and Claude session is doing: **working** during an open turn, **done** after its completion, and **waiting** while a session is idle with no finished turn (a new one, an aborted Codex turn, or a Claude turn that went quiet, see below). **Unknown** means an exact conversation binding or complete lifecycle read is not available yet. New managed Codex sessions bind on their first completion; exact resumed sessions can be tracked immediately. Large Codex logs are read from their first record and recent tail, so a long-running conversation does not need a full replay. Claude has no log to follow: its state is the turn cursor that the hooks of its launch keep (`UserPromptSubmit`, `Stop`, `SessionStart`, `SubagentStart`, `SubagentStop`; identifiers only, never prompts or replies), so a Claude that RiWork did not launch with them (one started by an absolute path) reads **unknown**, and one launched before `SubagentStart` was added shows no subagents until it is restarted. Claude sends no hook when a turn is interrupted with Esc, so a turn that is open but has shown no sign of life for 10 minutes (neither a hook event nor a run of Claude's status line, which Claude does around each message and not on a timer) reads **waiting**, as does one paused by a Stop that lists background work such as a dev server; a single tool call that stays silent for over 10 minutes reads the same until its next message. Grok and Muse have no activity tracking and always read unknown; they are not counted in the summaries. Existing notification settings are preserved.

**Subagents** are shown with the agent that started them: "● 1 working · 2 subagents" in the status bar and project and worktree rows, "● WORKING · 2 SUBAGENTS" on the shell's row, and the kinds on hover over its tab ("Working · 2 subagents (general-purpose, Explore)"). A Claude subagent is counted from its `SubagentStart` to its `SubagentStop`, paired by `agent_id`, and its kind is the hook's `agent_type`. A Stop that ends the turn clears all of them; a Stop that lists background work (`background_tasks`) keeps the turn open and corrects the list to what it names; a new prompt or `/clear` starts without the previous ones. The `SubagentStop` with no start that Claude sends a few seconds after some replies (empty `agent_type`, carrying the finished turn's own prompt) is not a subagent and does not reopen the finished turn, in the display or for scheduled prompts. A subagent that was never heard from again, as after an interrupted turn, stops counting 30 minutes after it started. A Codex subagent is a child thread: a rollout in the same session tree whose first record names the shell's thread as its parent, counted while its own turn is open and its file was written within 30 minutes. Children are looked for in the newest three day directories of the tree at or after the parent's, at most every 4 seconds, and only while the parent is working. Subagents are counted only for a working agent, and only names are kept, never what a subagent was asked to do.

The same figures reach the CLI and the phone. `riwork shell list --json` and `riwork orchestrator list --json` add to each agent shell `activity` (`working`, `waiting`, `done`, `unknown` or `exited`), `activity_since_unix` (when the source records it), `subagents_working` and `subagent_kinds`; a plain shell has none of them, and a Grok or Muse shell is `unknown`. They add `last_activity_unix` to every live shell, a plain one too: the second tmux last saw output in its session (`#{window_activity}`, read in the `list-sessions` call that finds the live shells, so it costs no extra process). Output moves it whether an agent is working with no window attached or text was typed or sent in; attaching, detaching and the pointer do not, which is why tmux's `#{session_activity}` is not used. `riwork project list --json` adds `last_edited_unix` (from `project-recency.json`), `last_activity_unix` (the newest of the project's live shells, its own orchestrator included and the global one not) and `agents`, the project's agent shells by state (`working`, `waiting`, `done`). A project's orchestrator that runs as a chat counts as its terminal one does: its chat's log growing is activity of the project, and its state (`running`, `waiting`, `idle`) is an agent `working`, `waiting` or `done`. The phone's **Recent** project order follows `last_activity_unix`, then `last_edited_unix`. The CLI works the activity out itself, in its own process, from the same files the window reads (Codex rollouts and bindings, Claude hook cursors); it needs no window and no snapshot file, and reads a rollout longer than 1 MiB from its head and tail instead of through, so a list stays quick. The contract is in [docs/remote-protocol.md](docs/remote-protocol.md).

The **bell** beside each project controls macOS completion alerts. Alerts are off by default: a cyan bell means on, and a muted crossed-out bell means off. While RiWork is open, completed Codex turns and completed turns in newly launched RiWork Claude sessions send one alert per turn across all windows and processes. Only the packaged `RiWork.app` posts and claims alerts, so an unbundled development build sharing the same data never consumes them. Click the notification or **Open agent** to open that project's completed agent.

Initial **Done** states, historical completions, aborted turns, and ordinary shell exits do not alert. Existing Codex sessions with an exact conversation binding also work; start a new Claude session to load its completion hooks. macOS asks for permission when you first enable a bell, and **System Settings → Notifications** controls delivery. Native alerts require the packaged RiWork app; unbundled `cargo run` launches cannot send them.

Click a project row to switch the current window, or **↗** to open that project in another window. Cmd+Shift+N opens a new project window; `riwork open PROJECT_OR_PATH` opens one from the CLI. Each window keeps its own project. Right-click the RiWork icon in the Dock to see every open window of that app listed by project name, alphabetically, with the frontmost window checked; choosing one brings it to the front. Windows showing the same project add their branch, or a number when that is not enough. **New Window** in that menu is Cmd+Shift+N for the frontmost window. The list follows windows opening and closing, project switches and renames. `riwork project use ID` selects the default for subsequent windows.

Use **+ FOLDER** (a folder-with-plus icon when **Icons instead of labels** is on) to create virtual folders in Projects, or a folder's **+** to create a subfolder. Drag a project onto a folder to file it there. Drag a folder onto another folder to nest it, or onto **UNFILED** to move it to the top level. Dropping a project onto **UNFILED** removes its folder assignment. Folder headers expand or collapse their whole subtree; **✎** renames a folder and **×** removes it, promoting its projects and subfolders to its parent. Virtual folders organize the browser without moving files.

Click a project's **⚙** to open its **PROJECT SETTINGS** tab, where you can edit its name, select a folder by its full breadcrumb, and inspect its root and repository paths. **SAVE PROJECT**, Enter, or Cmd+S applies name and folder changes. Settings tabs restore with each project's layout. App-wide themes, Cua, and window preferences remain in **SETTINGS**.

## App preview tabs

Choose **App preview…** in a pane's **+** menu or **View → App preview…**, enter the app's launch command and working folder, and choose **Run**. **Hidden GPUI** runs a separate process with no native window or Dock icon, streams compressed frames into the tab, and forwards pointer, scroll, keyboard, and committed text input. Add the development adapter described in [riwork-gpui-preview](crates/riwork-gpui-preview/README.md) to your GPUI app. To try the included example in this checkout, use `cargo run -p riwork-gpui-preview --example counter` as the command and this checkout as the working folder.

Tabs save their command, folder, and mode, and restore stopped. **Restart** rebuilds/reruns the command; **Stop** and closing a tab stop its launched process group. Rendering pauses when the tab or RiWork window is inactive. Logs are available below the preview. The GPUI adapter currently uses the real Metal renderer through GPUI's development headless platform; native dialogs, clipboard, accessibility, and native IME composition inside the child are not supplied by that platform.

**Cua window** is an optional mode for an unmodified local app, using RiWork's guarded Cua.ai Driver for capture and input. It targets a window of the process launched by this tab. This mode requires a normal, non-minimized app window; it does not make arbitrary applications windowless or remove their Dock icons. Missing driver or macOS permissions are reported with the RiWork Cua setup instructions.

**iOS Simulator** builds an Xcode scheme, creates a dedicated simulator, installs and launches the app, and streams its framebuffer with touch input into the tab without opening Simulator.app. Choose the working folder and scheme; project, iPhone model, and installed iOS version can be selected or detected automatically. Stop and closing the tab shut down and delete only its owned simulator. The native adapter has been verified with Xcode 26.0.1 on iOS 18.1 and 26.0; it currently supports one finger, scrolling, Home, and US keyboard text. See the [native adapter and real-device proof](tools/ios-preview-bridge/README.md) for compatibility and input limits.

Coding shells can create and reuse these tabs, wait for a first frame, read build logs, send touch input, capture a fresh frame, and close them through `riwork preview` or the `riwork_preview_*` MCP tools. For example: `riwork preview open --ios --scheme MyApp --wait --json`. Commands target an exact preview ID and work while its window is inactive. See [preview CLI and MCP controls](docs/preview-control.md).

## Persistent shells

The Shells tab includes **Nuke all shells** beside its session controls. It asks for confirmation before exiting the project's live shells, including detached and worker shells; orchestrator shells and chats stay open.

RiWork creates `~/Documents/riwork` at app startup if needed. Use **+ PROJECT** (a box-with-plus icon when **Icons instead of labels** is on) in Projects or Cmd+N to create a project. Enter a project name to create `~/Documents/riwork/NAME`; the folder field updates automatically. Default names cannot start with a dot. Editing the folder or using Browse selects an explicit location, where the name is optional; a typed folder must be an absolute path (`/…` or `~/…`), and the form shows the resolved folder. If creation fails, folders it made that are still empty are removed. `riwork project create --name NAME` also uses this default parent. Explicit CLI paths retain their usual meaning. Plain `project create` registers a folder it finds at that path; `--exclusive` never does: it fails with `already_exists: …` if the folder is there (a file or link counts) or a project has that root or that name (ignoring case), and a failure after it made the folder takes the folder back. The phone's `project.create` always runs it that way. Projects support a single Git repository, a folder containing several repositories, and plain folders. Creation offers **Initialize Git** checked by default when no repository is found. Uncheck it to keep a plain folder. Existing repositories are reused; a wrapper folder is never initialized around them. `project add` only registers a folder. For projects with several repositories, worktree creation requires choosing a repository with `--repo`; a new repository needs an initial commit before Git can create worktrees.

```sh
riwork shell create --worktree WORKTREE_ID
riwork shell create --worktree WORKTREE_ID --harness codex
riwork shell create --worktree WORKTREE_ID --harness claude
riwork shell create --worktree WORKTREE_ID --harness grok
riwork shell create --harness codex --unrestricted
riwork shell create --harness claude --as-settings
riwork shell list --all --json
riwork shell output SHELL_UUID --lines 100
riwork shell history SHELL_UUID --end 0 --lines 200
riwork shell cwd SHELL_UUID
riwork shell metrics SHELL_UUID
riwork shell send SHELL_UUID "pwd"
riwork shell keys SHELL_UUID -- t:'git status' k:Enter
riwork shell paste SHELL_UUID -- /absolute/path/to/screenshot.png
riwork shell attach SHELL_UUID
riwork shell attach SHELL_UUID --exec [--ignore-size] [--read-only]
```

An agent from `shell create --harness` asks before it acts unless you add `--unrestricted`, which passes the agent's permission bypass flag, so a script keeps its meaning. `--as-settings` does what the New tab menu does instead: unrestricted while **Agent terminals run unrestricted** is on in Settings, asking while it is off. The phone's `shell.create` uses it when it asks for the desktop's setting (`"as_settings": true`).

`shell attach` prints the tmux command a terminal runs to show the shell; with `--exec` it runs it instead, replacing the `riwork` process with the tmux client (`--ignore-size` keeps this display from resizing the shell's window, `--read-only` makes the client watch only). A remote desktop's terminal stream uses it (`remote/README.md`). In a terminal that says `xterm-ghostty` it announces that when the app bundle (or the caller's `TERMINFO`) has Ghostty's terminfo, otherwise `xterm-256color`.

Every shell has a UUID. `shell output` captures tmux scrollback and the current pane as text, including when the GPUI app is closed. Full screen terminal programs may show only their current rendered screen rather than a complete semantic transcript. Closing a tab or window detaches its shell; `riwork shell close UUID` ends it.

Mouse-wheel and trackpad scrolling use tmux's scrollback. Codex, Grok, and Claude Code sessions run inline on the main screen by default (see **Keep agent transcripts in scrollback** under Settings), so their whole conversation is in that scrollback and the wheel scrolls it. Scrolling up enters copy mode; scroll back to the bottom or press Escape to return to the live terminal. New sessions enable mouse reporting, and existing sessions are upgraded when reattached. A new session keeps up to 100,000 lines of scrollback; tmux applies that limit only to panes created after it is set, so sessions started by older builds keep tmux's default of 2,000 lines.

**Links in terminals.** Point at a URL or a file name in a shell, Codex, Claude, Grok, orchestrator or editor tab and a thin line in the theme's accent color underlines all of it, on every row it was wrapped over; hold ⌘ and the pointer becomes a hand, and ⌘-click opens it. RiWork finds the link in the text tmux shows for that tab, so it sees what you see: the live screen, the part of the scrollback you have scrolled to, or the screen of a full-screen program. A link the terminal wrapped over several rows is put back together, and a click needs nothing from Ghostty's own matcher, which does not know the folder the shell is in. Only the terminal under the pointer is read, at most every half second and off the UI thread, and none once the pointer has left the terminals; a click without ⌘ goes to the terminal as before. A URL (`http`, `https` or `mailto`) opens in the default browser or mail app, without the full stop or bracket of the sentence it sits in. A file name is `src/main.rs`, `./x`, `../x`, `~/x` or an absolute path, with an optional position (`:120`, `:120:5`, `:120-135`, `#L120`), inside backticks, quotes or brackets (a name with spaces needs quotes), a pytest id (`tests/test_a.py::test_b`), a name in a Python traceback (`File "a.py", line 12`), or a `file://` URL. It is looked for in the folder the tab's shell is in and then in the window's project or worktree root, and it is a link only if it exists (the `a/` and `b/` that `git diff` puts before a name are dropped when no such folder exists). A file inside the window's project or worktree is selected in Files and shown in Preview, scrolled to the line with that line marked. The Preview opens even with **Open the preview when a file is selected** off, a dot file turns on **Hidden** so that it has a row to select, and a folder is shown in Files. The Preview and Files go beside your work, never over the terminal you clicked in, and that terminal keeps the keys: with the tree on screen in another pane the Preview goes beside it, as when you choose a file there; with none, the roomiest unlocked pane that is wide (620 px) or tall (700 px) enough, the terminal's own included, is split and the panel takes the new pane (the terminal keeps 60% and its selected tab); when nothing can be split, the panel is a tab in another pane, selected there only if that pane shows no terminal, and a notice says where it waits. With a main pane (see **Main pane** above), the Preview and Files are tabs of it instead (a tab that would cover the clicked terminal waits unselected beside it). A message in Preview says when it cannot show the line (a picture, a PDF, a line past the end). **⌘⇧-click** opens a file of the project in the Vim editor tab at that line, and takes an editor tab that is already open on it to the line. Anything outside the project opens with its default app if it is a document, a picture, sound or video, data, or a source file other than a script, and a folder opens in Finder; anything else (executables, scripts, applications, installers and disk images, files with no known type) is shown in Finder, never opened by RiWork. The hyperlinks (OSC 8) that Claude Code and Codex print for Markdown links and files go where they point, whatever words they show: RiWork reads the target from tmux and opens it itself (an `http`, `https` or `mailto` address, or a `file:` target on this Mac), because Ghostty as embedded here does not open OSC 8 targets at all (words that are themselves an address win over a target on another site). A click that is not on a link goes to the terminal as before, which leaves Ghostty's own matcher free to `open` text that RiWork did not take for a link. The hand appears as the pointer moves with ⌘ held, and when ⌘ is pressed while the pointer rests over the terminal that has the keys. A tab for another Mac's shell is left to Ghostty, which opens URLs there (its tmux is not this Mac's, so files are not looked up). RiWork also tells its tmux server to pass OSC 8 hyperlinks on to the terminal (`terminal-features` `xterm*:hyperlinks`, set whenever a terminal attaches), which tmux drops otherwise, so that Ghostty receives them; a terminal that is already open picks it up the next time it attaches, for instance after **Reload**.

**Files dropped on a terminal.** Drag files or folders from Finder (a screenshot from the desktop, say) onto a shell, Codex, Claude, Grok, orchestrator or editor tab and their absolute paths are typed into it as Ghostty does it: a backslash before spaces and the other characters a shell reads specially (``\ ()[]{}<>"'`!#$&;|*?`` and tab), several paths separated by one space, nothing after the last and no Return. The text goes in as a paste (tmux `paste-buffer -p` into the tab's shell), bracketed when the program asked for bracketed paste, so Claude Code, Codex and Grok see pasted paths and attach dropped pictures (png, jpeg, gif, webp) as `[Image #1]`; other files stay paths. Claude Code and Grok take several paths in one paste. Codex attaches a paste only when it is a single picture's path, so a Codex tab gets one paste per path, with a space after each path that is not a picture. Which program is in front is read from the pane (`pane_current_command`, then the processes in the terminal's foreground, as for Codex installed by npm, which runs as `node`); an agent tab RiWork started counts as that agent until a shell is back in front. A thin outline in the theme's accent color marks the terminal under the drag; the drop selects that pane and gives its terminal the keys, and a terminal in copy mode leaves it first. A tab for another Mac's shell takes no drop, since a path on this Mac means nothing there, and text dragged from another app is not taken: the window accepts only files.

**Copied files and pictures.** ⌘V in a local terminal pastes text through Ghostty as before. When the pasteboard holds files instead (⌘C on files in Finder), RiWork pastes their paths exactly as a drop would, for shells and agents alike; Ghostty alone would paste only the file's name. A picture copied with no file and no text (a screenshot taken with ⌃⇧⌘4, or Copy Image) turns ⌘V into Ctrl+V for Claude Code, Codex and Grok, the key with which each reads a picture from the pasteboard itself and attaches it; a shell gets nothing, as in Ghostty. Ctrl+V itself always reaches the program unchanged (neither RiWork, Ghostty nor RiWork's tmux binds it), so it works as each CLI documents: Claude Code attaches a copied picture but not a copied file; Codex and Grok attach a copied picture or a copied picture file. A tab for another Mac's shell keeps Ghostty's text paste.

**Files from the phone.** A photo or a file sent from the iPhone app to a terminal is pasted the same way. The phone uploads it over the encrypted link (see [docs/remote-protocol.md](docs/remote-protocol.md), "File upload extension"); the connector keeps it in `RIWORK_HOME/uploads/SHELL_UUID/` (folders mode 700, files mode 600, under a name the connector makes, never the phone's) and runs `riwork shell paste SHELL_UUID -- FILE...`, which pastes the paths exactly as a drop of those files on that terminal would, chosen by the program in front: Claude Code and Grok get the escaped paths in one paste and attach a picture, Codex one paste per path and attaches a picture, a shell gets the escaped paths. No Return is added and the paste happens once, however often the phone asks again. `shell paste` takes 1 to 16 existing files by absolute path, refuses anything else before it touches the pane (an error that starts with `invalid_request:`, `not_found:`, `input_unavailable:` or `not_sent:` pasted nothing), and `capabilities --json` says `"shell_paste": true`. A file sent to a chat lands in `RIWORK_HOME/uploads/CHAT_UUID/` and its path goes into the message on the phone. Uploads are removed after a day, when their device is revoked, and when the shell is closed or the chat deleted.

RiWork's tmux server always lives in tmux's default socket directory: an inherited `TMUX_TMPDIR` is ignored, so the app, the CLI, and a terminal that sets it all reach the same server. A project folder whose name tmux would misread (`C#Tools`, `#{…}`, or a name ending in `;`) starts its shells in that folder; if tmux still cannot start a shell in the requested folder, creation fails with an error instead of opening in your home directory. Variables that name a CLI profile (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `GROK_HOME`) and `RIWORK_CUA_DRIVER` are cleared from the server's environment when the app was started without them, so a value left by an earlier launch cannot reach a new session, and your own zsh startup files remain free to set them.

`shell keys` types like a keyboard instead: after `--` come 1 to 64 items, each `t:TEXT` (literal text of 1 to 4096 bytes without control characters, sent verbatim, trailing `;` and `\;` included) or `k:KEY` (`Enter`, `Tab`, `BTab`, `Escape`, `Backspace`, `Delete`, `Up`, `Down`, `Left`, `Right`, `Home`, `End`, `PageUp`, `PageDown` or `C-a` to `C-z`), with at most 4096 text bytes in all. No Return is added. The items reach the pane in order under the same input lock as `shell send`, and a key that directly follows text is sent about 150 ms later so Codex does not read the pair as a paste; a pane in copy mode is taken out of it first, and a pane whose terminal input is disabled is refused. `shell output --json` also reports `cursor` (`x`, `y`), `rows`, `cols` and `in_mode`; the last `rows` lines of its `output` are the visible screen. The phone companion uses both for direct typing. `shell output --json` also reports a `hash` of everything the answer says. `--styled` keeps colors and text attributes as SGR sequences (`ESC [ … m`, exactly as `tmux capture-pane -e` writes them) and removes every other escape and control sequence; the lines, and so the screen rule, are the plain capture's. `--if-changed HASH` (a `hash` from an earlier answer to the same question) with `--wait-ms N` (0 to 10000) keeps waiting inside that one process while the hash stays the same, capturing again when tmux reports a change in the pane (a read-only control-mode client attached to the session, which never sizes a window; about every 80 ms where tmux cannot do that), and answers `{"id":…,"unchanged":true,"hash":…}` without any output if nothing changed within the wait. The phone uses these to follow a terminal live instead of polling.

`shell history ID --end N --lines M [--styled] [--json]` reads older scrollback, which `shell output` (at most the newest lines plus the screen) does not reach: it skips the `N` scrollback lines directly above the screen (0 starts at the line just above it), then takes the `M` (1 to 1000) above those, clamped at the top of the history. `--json` answers `{"id":…,"output":…,"line_count":…,"history_size":…,"complete":…}`: `output` is the lines top to bottom joined by newlines, unaltered and with no newline after the last, `complete` is true when the page reaches the first line of the history, and an `N` at or beyond `history_size` gives an empty page (`line_count` 0). Paging upward from `--end 0` with each `line_count` added to `--end` rebuilds the whole history without gaps or overlaps. `--styled` applies the same SGR-only filter as `shell output --styled`. `shell output --json` (and its `unchanged` answer) also reports `history_size`, the number of scrollback lines above the screen, and `alternate`, true while a full-screen program such as vim or less is on the alternate screen; both are part of its `hash`, so output that scrolls lines away without changing the visible screen still counts as a change. The phone companion uses them to scroll back through the whole history (contract in [docs/remote-protocol.md](docs/remote-protocol.md)).

`shell send` pastes the text verbatim, whatever its length or trailing characters such as `;`, and presses Return once. Every tmux call is limited to five seconds, so an unresponsive tmux server produces an error instead of freezing the app. A Vim editor session ends when Vim quits, and RiWork then removes its entry from the Shells panel; exited agent and plain shells keep theirs.

Each project remembers its split layout and sizes, mixed panel/shell tab order, active selections, and selected worktree/task across project switches and UI restarts. Closed shell tabs stay detached; click their shell in the Shells panel to reattach them. A shell of a worktree whose folder was deleted outside RiWork (by `git worktree remove`, or the tool that made it) is ended, with its agent: once the folder has stayed gone for five minutes while the folder it was in is still there (so a drive that is not mounted is never taken for a deletion), and only while no terminal is attached to it and no tab of an open window holds it. A tab saved in the layout of a project no window shows does not keep it. An open RiWork window looks once a minute and ends it as `riwork shell close` does; shells of the project's own folder, and shells without a worktree, are never ended this way. Exited shells are skipped during restoration, and new CLI-created shells join the active pane (the main pane, if there is one) when the project next opens. An intentionally empty workspace stays empty. Layouts are saved separately in `layouts.json` under the same data directory. A tab this build cannot read, such as a panel type that only a newer RiWork has, is left out and the rest of the layout opens as saved; the tab stays in `layouts.json` and is written back with the pane that held it, so an older build cannot erase it. A project whose saved layout cannot be read at all, such as one with a split shape this build lacks, opens with a default layout and a notice; other projects are unaffected. Unreadable entries and unknown fields are written back unchanged and never replaced, so an older build cannot destroy a newer build's layouts (changes to that project's layout are not saved while it stays unreadable). A build from before the Preview panel cannot read a layout that has one and falls back to a default layout for that project, leaving the saved layout untouched. The main pane is saved as one more field of the project's layout (`main_pane`, written only when set), which every earlier build ignores: it opens the layout, and forgets the main pane the next time it saves that project. A `layouts.json` that is not valid JSON is kept as `layouts.corrupt-*.json` when layouts are next saved, and a file with a newer schema version is left alone.

The full-width bottom status bar shows the current project on the left and live sessions, CPU, resident RAM, usage, Codex account, the active shell UUID, **G·ORCH** (the global menu: the global window's dashboard and chat), **P·ORCH**, and the **LAYOUT** menu (see **Layout menu** above) on the right by default. The usage item has two modes, chosen in **Settings → Status bar**. **Current chat** (the default) reads out the quota of the focused chat's or shell's Codex account, named (and numbered **A1**, **A2** as its tab is when several accounts run in the project), or of the project's default Codex account when nothing of Codex is focused; a focused Claude or Grok session shows its own figures as before. **All accounts** shows every available Codex account side by side, the system default included, keeps an account that has not been read yet or whose last read failed in view with that said, and adds Claude's subscription once a Claude session has reported it; Grok and Muse have no allowance to show. Both use the usage reads RiWork already makes, and a click opens **Usage** for the details. The Codex account item says which account new Codex chats and shells in this project get, and whether the project, the app or the system default decides it (**DEFAULT (PROJECT)**, **(APP)**, **(SYSTEM)**). A click opens **New Codex sessions in this project**, which chooses it: Inherit app default (with the account that comes to), System default, or a saved account. It is the project's own choice that Project Settings saves, so orchestrator workers started without `--account` use it as well; running chats and shells keep their account, `--account` still chooses one, and the app default in Settings stays as it is. The menu's **Project Settings…**, or Cmd+Option+A, opens Project Settings. Click the status UUID to copy it. Configure status items in **Settings → Status bar**. The Shells panel shows worker shells with their metrics and current worktree when their working directory matches a known worktree.

## Harness launches and usage

The **New Tab** section of a pane's **…** actions menu launches a shell, Codex, Claude, Grok, or Muse in the selected worktree, one entry each. The agents start unrestricted, with each CLI's permission bypass flag (Codex `--dangerously-bypass-approvals-and-sandbox`, Claude `--dangerously-skip-permissions`, Grok `--always-approve`, Muse `--yolo`), while **Agent terminals run unrestricted** is on in Settings, which it is by default; turn it off and the same entries start them with the CLI's usual permissions, asking before they act. Cmd+Shift+C opens Codex; Cmd+Shift+L opens Claude; Cmd+Shift+G opens Grok; Cmd+Shift+U opens Muse, the same way. Scheduling a Grok or Muse *terminal* and RiWork activity and completion alerts for them are not yet supported. Grok has no chat; chats run Codex, Claude and Muse (see [Chats](#chats)).

Click the bottom usage readout, or open **USAGE** under **Views** in a pane's **…** actions menu, for remaining quota, reset countdowns, and update times. Codex reads its official app-server account endpoint on a worker with a timeout, refreshing every 15 minutes or on demand. Claude sends documented statusline JSON through settings passed only to that invocation; global Claude settings are unchanged. Claude quota appears after a response on supported Pro/Max accounts and versions. Context usage and estimated session cost appear separately. Missing quota windows stay unavailable; old snapshots are marked stale. Quota is shared by sessions on the same account.

Grok shows what its own CLI reports for each session, not the account allowance. Grok's **Usage limit**, **Credits left** and **Pay-as-you-go limit left** appear only in the `/usage` screen inside Grok; it has no official CLI or JSON interface for them, so RiWork does not read them and never calls Grok's private endpoints or reads its sign-in files. The USAGE tab lists every live Grok tab of the project with its model, total tokens (input, output, cached, cache writes and reasoning), turns and session cost in USD, then a combined total, and points to `/usage` for the allowance. The bottom readout for a focused Grok tab shows that session, for example `GROK $0.42 · 128k tok`; clicking it opens the USAGE tab. RiWork finds a tab's session by matching the pane's process (a Grok executable, or its direct child when the pane runs a wrapper) to an entry in `active_sessions.json` under `GROK_HOME` (default `~/.grok`). Entries whose pid has been reused by another program, or that name a process that started after they were written, are ignored, and a tab with two candidate sessions shows none. It then runs `grok usage SESSION_ID` on a worker with a 5-second timeout and bounded output, using the real Grok binary rather than RiWork's launcher. Figures are read only while the USAGE tab or the readout is on screen, at most every 30 seconds per session across all windows (a failed read after good figures is retried after 10 seconds), or immediately with **REFRESH**. A session Grok has not counted anything for yet shows as unavailable, not as $0.00. If a read fails or Grok is mid-write, the last figures stay, marked stale. Session figures include history inherited by a resume or fork. `riwork usage --shell SHELL_UUID` for a Grok shell prints the same figures. In `--json` the existing fields are unchanged (`windows` is empty and `account_label` is `unknown`, because the allowance is unknown), `session_cost_usd` is the cost, and a `session` object adds `session_id`, `primary_model`, `turns`, `model_calls`, `tokens` (`input`, `output`, `cached_read`, `cache_creation`, `reasoning`, `total`), `cost_usd`, `updated_at` and a per-model `models` list. When a session cannot be read (not running, not listed yet, ambiguous, Grok missing or slow) the command still succeeds and `session_error` says why. `riwork usage` without `--shell` reports the account of the shell it runs in (`RIWORK_SHELL_ID`): that shell's frozen Codex account, else its project's choice, else the app choice.

```sh
riwork usage --json
riwork usage --shell SHELL_UUID --json
riwork open PROJECT_NAME
riwork open /path/to/another/project
```

Project windows and independently launched app processes keep their own selected project. Projects, tasks, the shell registry, and layouts share the RiWork data directory. Older and newer builds can share it after `riwork update` leaves an older window or `riwork` on `PATH`: a build keeps the fields and shell entries it does not understand, such as a session for a harness it predates, when it rewrites `state.json` or `sessions.json`; it hides those entries instead of failing. A store schema newer than the build is still refused. Closing a window preserves its shells. There is one persistent global orchestrator and one persistent orchestrator per project.

## Chat host

Codex, Claude and Muse chats talk to the agents through their structured interfaces, not their terminals (Codex's app-server, Claude's stream-json, Muse's `serve` host over MSP). The agent processes behind them belong to the chat host, `riwork chat serve`, so a chat keeps working while app windows reload, update or quit. There is one host per RiWork data directory. It listens on `run/chat.sock` (mode 600, in a mode-700 directory, connections from other users are dropped), `run/chat.lock` keeps a second host out, and `run/chat.log` has its output. `riwork chat ensure` starts it detached if it is not running (several callers at once start one) and prints the socket. The host exits by itself after 15 minutes with no client connected and no chat starting, running or waiting for you (`chat serve --idle-seconds N` changes that); the next `ensure` starts it again.

```sh
riwork chat ensure
riwork chat new --provider codex --worktree WORKTREE_ID --mode auto-edit
riwork chat new --provider claude --project PROJECT_ID
riwork chat new --provider codex --project PROJECT_ID --model MODEL --effort high --fast --title "Fix the build"
riwork chat list --project PROJECT_ID --json
riwork chat send CHAT_ID "run the tests"
riwork chat events CHAT_ID --since 0 --wait-ms 10000 --json
riwork chat command CHAT_ID --command-json '{"command":"interrupt"}' --json
riwork chat command CHAT_ID --command-json '{"command":"switch","provider":"claude","model":"opus"}'
riwork chat models --provider claude --project PROJECT_ID --json
riwork chat suggestions CHAT_ID --json
riwork chat stop CHAT_ID
```

**Muse chats** run one `muse serve` per chat. They cover:

- **Messages and steering.** A message sent while a turn runs is steered into exactly that turn (`turn/steer` with the turn's id). One sent while the turn is starting waits for its id. One that Muse refuses because the turn just ended starts the next turn, once.
  - Muse 1.4.7 answers a steer that arrives after the turn's last model call as accepted, but under the steer's own id instead of the turn's, and drops it. Such a message is not sent again; a notice gives it back in full.
  - A typed message is never lost silently. One that Muse refuses, that is never written, or that is waiting or unconfirmed when Muse stops or dies comes back in full in a notice. One whose delivery is uncertain is never resent.
- **Attachments.** UTF-8 text files arrive as text. Static PNG and JPEG images arrive as MSP image parts (`mediaType`, `base64Data`), within the same limits as the other providers. The transcript shows the message as sent, with its snapshots, never the file contents.
  - The send is answered only once Muse has taken or refused it, so a refusal keeps the draft.
  - Attachments are refused while a turn is starting or being interrupted.
  - A reply that cannot be matched to the turn is reported as unknown rather than retried.
- **Approvals.** Each choice Muse offers has a scope (`once`, `session` or `localPersistent`). **Allow**, **Allow for this session** and **Decline** send only a one-time or session-scoped choice. RiWork never sends a choice that saves a lasting rule; when Muse offers a grant only in that form, the chat says so and offers Decline and Stop. A refreshed approval (`approval/updated`) is shown again with its new subject. A refresh that leaves no choice RiWork can send closes the prompt and says so, so an earlier step's choice is never sent against the new one.
- **Questions.** Single choice, several choices within Muse's bounds, and free text up to Muse's 500 characters. An answer outside those limits is refused before anything is sent. A question Muse settles by itself after a delay says so; showing it does not stop the countdown.
- **Modes.**
  - **Supervised**, **Auto-edit** and **Full** select Muse's `promptUnmatched`, `onRequest` and `allowAll` under the permission profile your Muse settings choose. Muse's own default profile is Auto-review, where an AI reviewer may decide eligible approvals.
  - Muse has no planning mode. **Plan** starts the conversation under Muse's **Read only** profile ("Reads files only") with `denyUnmatched`, and the chat says so. Under that profile a write by a shell command is refused.
  - Muse fixes a conversation's profile when it starts, so a Muse conversation cannot be moved into or out of Plan. Start a new Muse chat instead.
  - Muse has no fast mode. RiWork refuses it for a running chat. A new Muse chat that asks for it, for example from an automation, is made without it and says so.
- **Contributor mode.** RiWork starts every Muse with Muse's contributor mode off, whatever your Muse settings say, and turns it on only for a chat or terminal you ask it for. Muse says that with contributor mode off, your content won't be used for product improvement. Every start of a Muse chat (creation, each resume, after a restart of the chat host, back from another provider) runs `muse serve --contributor-mode off`, or `on` for a chat you turned on: an override for that process that Muse never saves, so your Muse settings stay as they are. Model discovery runs off too. Turn it on for a new chat with the **Contributor off/on** toggle the new-chat dialog shows for Muse (`chat new --contributor-on`; `--contributor-opt-out` is the explicit off), and for an existing one with the **Contributor** toggle beside the model picker (or `{"command":"configure","contributor_mode":"on"}` and `"off"`); the choice stays with the chat until you turn it off. Muse fixes the mode for a process, so an idle chat restarts `muse serve` and resumes the same conversation with its model, effort and approval mode; a stopped chat keeps the choice for its next start. The change waits while a turn runs, waits for you or Muse still starts. If Muse does not start again with it, the chat keeps its old choice and says so. Chats from before this release, opted out or not, start off. Muse terminals RiWork starts (New Tab, `shell create --harness muse`, handoffs) pass `--contributor-mode off` too, or `on` with `shell create --contributor-on` or `handoff --contributor-on`; and `muse` typed in a RiWork terminal, or run by an agent there, adds `--contributor-mode off` to a session it starts (interactive, `resume`, `exec`, `serve`) unless you pass `--contributor-mode` yourself, leaving `--help`, `--version` and Muse's other subcommands as typed (`muse help` is a prompt to Muse 1.4.7, so it starts off too). A Muse run outside RiWork, or by an absolute path to the Muse binary, follows your Muse settings. A Codex or Claude chat has no contributor mode to turn on: asked for one, it is made without it, with a notice, and it refuses on; a chat that switched away from Muse with it on keeps it for a switch back, and can turn it off.
- **Switching providers.** A chat that moves to Muse sends the conversation so far with its first message to Muse, as a leading part of that message. The transcript shows only what you typed. It is sent once: a resumed Muse conversation that has run a turn already has it.
- **Cua.ai Driver.** RiWork's Cua.ai Driver reaches the chat as an MCP server for that session only (`config.mcpServers` on `session/start` and `session/resume`, which needs Muse's `sessionMcp` capability), never through Muse's settings. A Muse without that capability runs the chat without it, and the chat says so.

`chat/muse_tests.rs` checks the driver against fixtures and, with `MUSE_LIVE_BIN` naming the Muse binary itself, against the real `muse serve --provider echo` in throwaway homes. The live tests cover:

- a private stand-in MCP server started at `session/start` and again at resume;
- the carried-over conversation, attachments, steering and interrupt;
- the Read only profile.

Approvals, questions and compaction are checked against fixtures only, because the echo provider cannot produce them.

`--mode` is how much the agent may do without asking: `supervised` (the default; ask before commands and edits), `auto-edit` (edit the workspace, ask for the rest), `full` (never ask; what unrestricted launches use) or `plan` (plan first, change nothing). Like `shell create`, `chat new` starts in the given worktree, in the project's primary worktree, or else in the active project. Chat IDs are UUIDs; commands accept a unique prefix of at least eight characters.

`chat new --json` prints the chat as `chat list --json` shows it, also when its provider did not start (its state is then `failed`, with the reason); without `--json` that is an error. `--model`, `--effort` and `--title` (at most 100, 32 and 200 characters, no control characters) take their value as it is, also with `=`, so a title may begin with `--`. `--fast` turns on the provider's fast mode for a model that has one (Codex's Fast service tier, Claude's fast mode); `{"command":"configure","fast":true}` (or `false`) changes it later, and the chat tab's toolbar shows a Fast toggle for a model that supports it. The tab's model picker lists the models the agent itself reports (a `models` event in the chat's log) with the efforts each takes, and falls back to a text field for an agent that reports none. `chat list --project` lists one project's chats.

`chat events` and `chat command` are what the phone's remote connector runs for chats (see `docs/remote-protocol.md`, "Chat extension"), and work from a terminal too. `chat events CHAT_ID --since N --wait-ms M` reads the events after `seq` N and prints one compact JSON line, `{"chat_id","events":[{"seq","event"}],"next","more"}`. Events that are already there come at once; otherwise it waits up to M milliseconds (at most 25000) for the first one and then collects for another 50 ms. `--max` (500 by default, at most 2000) and `--max-bytes` (1 MiB by default, at most 2 MiB) cut the page; `more` says it was cut, and `next` is the `--since` for the next call. An event too big for a page alone has its long strings cut. `chat command CHAT_ID --command-json JSON` sends one command to the chat (`send`, `interrupt`, `approve`, `answer`, `configure`, `compact`, `stop` or `switch`, in the JSON of the chat model) and refuses anything with a field it does not use; a refusal of the command starts with `invalid_request:`. `riwork capabilities --json` has `"chat": true` in a build that has all of this.

`{"command":"switch","provider":"codex|claude"}` (with an optional `model`, `effort` and `fast`) moves a chat to the other provider in place, as the model menu of a chat tab does (see [Chat tabs](#chat-tabs)): the same id, log and approval mode, a new agent on a thread of its own that is given the conversation so far. It is refused while a turn runs or waits, and with the provider the chat has it is an ordinary `configure`. A chat host started by an older RiWork refuses it as a command it does not know. `chat models --provider codex|claude [--project ID]` prints what a chat of that provider can be set to, read from saved chats without starting the host: the newest list a driver of the provider reported (in a chat that runs the project's Codex account, for Codex), the other model IDs chats were set to, and why the provider cannot be offered, if it cannot. `riwork capabilities --json` has `"chat_provider_switch": true` and `"chat_models": true` in a build that has them.

Each chat is a directory, `chats/CHAT_ID/`, in the RiWork data directory: `info.json` (the chat's id, project, worktree, directory, title, mode, model, effort, fast mode, the provider's thread id, the Codex account it runs under, for a chat that is an orchestrator, its `orchestrator` scope and, for one that switched provider, `carried_over`, the document of the conversation before the switch and whose it was, replaced atomically) and `events.jsonl` (everything that happened in it, one JSON object per line, appended as it happens; the line number is the event's `seq`). A client that opens a chat gets `events.jsonl` from the `seq` it last saw and then follows live events on the same connection, so a client that reconnects loses nothing; one that falls too far behind is disconnected and asks again from its last `seq`. The host starts no agent when it starts: every chat it loads is stopped, and the first message to one starts its agent again on the saved thread (Codex `thread/resume`, Claude `--resume`). A turn that a stop or a crash cut off is ended in the log (as interrupted) so no window waits for it. `chat stop` ends the agent and keeps the history; deleting a chat also removes its directory. If an agent cannot start (not installed, no Cua driver, a Codex account that is no longer available) the chat is kept as failed with the reason, and the next message tries again.

Chats are started the way terminal launches are: the same `codex` and `claude` programs (found on the login shell's `PATH`), the same Cua.ai Driver MCP wiring (`mcp_servers.cua-driver` for Codex, `--mcp-config` for Claude), the Codex account of the project (or of the app) saved with the chat so a chat keeps its Codex home, and Claude's `ANTHROPIC_API_KEY` as the chat's billing says (see **Claude chats bill** in [Settings](#settings)): removed on Subscription, so a stray key cannot switch it to API billing; on API key, the key saved in the Keychain, or with none saved the environment as it is. The agent's environment has `RIWORK_CHAT_ID`, the chat's id, as a terminal agent's has `RIWORK_SHELL_ID` (Codex is told it in its shell environment policy too, since it builds the environment of its commands from that); `riwork handoff` uses either to find the conversation that is meant when no `--from` is given. The host's `create` request takes an optional Codex account of its own (`codex_account_id`, an account id) in place of the project's; `riwork handoff` uses it, and `chat new` does not offer it.

## Orchestrator

The global orchestrator coordinates objectives and dependencies across projects. Each project's orchestrator manages its tasks, repositories, worktrees, and Codex, Claude, Muse, or Grok workers. Their skill (`riwork-orchestrator`, which both are given when they start and which **LOAD SKILL** brings up to date) routes work by model: orchestration, delegation and synthesis to Muse Wonder Full, the hardest reasoning, independent review and design to Claude Opus 5.5, and implementation, tests and long runs to Codex GPT-6.1-Sol, the fallback, unless you, Settings or a project chose otherwise; a fallback is reported, never silent. It also has the global orchestrator answer "what is going on" from RiWork's records first and then ask the project orchestrators that exist for a short brief (working, waiting, blocked, recently done, next step, needs you) through `riwork orchestrator send` and `output`, marking missing or stale answers; a brief creates no work. The skill opens with **Hard boundaries** that bind both: an orchestrator never tests in its own or any live orchestrator window (no clicks, keys, find bar, dialogs, layout, focus or draft changes), never live-tests closing, killing, nuking, deleting, updating or restarting shells, chats, the chat host, provider backends or orchestrators against real project state (opening such a dialog and cancelling counts), verifies only by reading evidence from isolated runs (otherwise it reports the result `unverified` and asks you to look), restarts or updates nothing that can interrupt sessions without your approval in the same turn, and requires every assignment and worker report to say where verification ran. Only your explicit approval in the same turn, naming the target, lifts one. They have separate persistent shells and ordinary workspace tabs; project orchestrators belong to their project and have no worktree, while the global orchestrator has neither project nor worktree ownership.

Press Cmd+Shift+O for the global orchestrator, or choose **Chat** in the menu that **G·ORCH** opens: it opens in the global window (see **Global window** below), never as a project window's tab. Click **P·ORCH** or press Cmd+Alt+O for the current project's orchestrator tab. Both are also under **New Tab** in a pane's **…** actions menu. Opening the project scope selects its existing tab in this window, or attaches its persistent session to the active pane. Project orchestrator tabs drag, split, close, and restore like shell tabs. Closing a tab detaches its terminal and preserves the session.

**Global window.** The global dashboard and the global chat share one window of their own, titled **RiWork · Global**, with a **Dashboard** and a **Chat** view switched at its top. It belongs to no project: opening it registers, selects or switches no project, and it writes nothing into a project's layout, tabs or chat requests, changes no window's project, worktree, task, folder, locks or remote selection, and claims no project's terminal. There is at most one, and every way in raises it on the view asked for: the global item of the status bar (**G·ORCH** in the colorful themes; a globe, with **Global** beside it when **Icons instead of labels** is off, in Native) opens a small menu above it with two rows (click it again, click elsewhere or press Escape to close it), **Dashboard** (Cmd+Option+G, also **View → Global Dashboard** and a pane's **…** → Views) and **Chat** (Cmd+Shift+O, also **View → Global Chat** and a pane's **…** → New Tab → Global orchestrator); asking again from any project window brings the same window forward. The shortcuts and the **View** items work from any window, the global one included; in a window that shows a project on another Mac they too open this Mac's global window (that Mac's global orchestrator is not opened from there). Each menu row says what it shows or what a click does: the dashboard's row sums up the work in a line, and the chat row names the orchestrator there is (**Open global chat**, with its agent and state), a global orchestrator that runs in a terminal (**Open terminal orchestrator**: it is opened as it is, never converted or ended), or, when there is none, what a click starts as **Orchestrator runs as** says (**Start global chat** or **Start global orchestrator**). Opening the menu, the window or its dashboard, drawing them and refreshing them start no agent, chat or chat host.

The **Chat** view shows the global orchestrator there is: its chat, the same chat with its transcript, draft and provider, permission and model controls (all kept with the chat, by its id), or, when the global orchestrator runs in a terminal, that terminal, labeled **Terminal orchestrator**, kept as it is (a chat takes over only after you end it). Showing the view connects to the chat host as any chat tab does (starting the host process if it is not running), but never starts an agent or makes a chat. When there is no global orchestrator, the view says so and offers **Start global chat** or **Start global orchestrator**; that button, the menu's Chat row, Cmd+Shift+O, **View → Global Chat** and the dashboard's chat control are the explicit requests that make one, as Settings say, when there is none. Closing the window (or Cmd+W in it) drops only the view: the chat and its agent, or the terminal's session, run on, and the window shows them again when it is opened. The window's image cards read what the global chat's may (see **Images in a chat** below); it has no Files of its own, so **Open in Files preview** and chat file links are a project window's. Cmd+Shift+N, Cmd+, and Cmd+Shift+S in the global window open a project window, Settings and Automations in the frontmost project window (else the active project's).

What the window last showed (its view, the dashboard's project filter and order, and its size) is kept in its own file, `RIWORK_HOME/global-window.json`, and opening the window again starts there; a missing or unreadable file is the dashboard. The file keeps `show_quiet` beside the filter, true exactly when the filter is **All**, so an older build still lists what it listed; a file from before the filters, which has only `show_quiet`, opens on **All** when it was true and **Active** otherwise, and a filter or order this build does not know reads as the default. An app reload (`riwork reload`, `riwork update`) restores it as itself, with its frame and view: its entry in the runtime registry says `"kind": "global"` and carries its own `global` state, names no project and no layout, and is the only one of its kind. Project windows are recorded exactly as before, and a snapshot written by an older build restores as project windows only. An older build that is handed a global window cannot open it (its `path` is the folder `RIWORK_HOME/global-window`, which never exists), so that reload fails and leaves the running app as it is rather than registering a project or opening the active project in its place; close the global window before reloading into an older build. A plain launch opens the active project's window as before, without the global window.

**Older layouts.** Builds before the global window opened the dashboard as a project window's panel tab and the global orchestrator as a project window's chat or terminal tab, saved with that project's layout. A project window now leaves those tabs out when it loads a layout (from `layouts.json` or a reload), says once that they moved (**View › Global Dashboard** or **Global Chat**), and saves its layout without them. Nothing is deleted: the chat, its history and draft, and the terminal's session stay as they are and open in the global window. Nothing new puts them into a project window: the dashboard panel, the global orchestrator's chat or terminal, and any route to them (a dashboard row, a reopened chat, a notification) go to the global window. A layout written by this build that an older build reads simply has no dashboard tab.

The **Dashboard** view shows every local project on this Mac at once, from what the global window samples every two seconds, as project windows do. Its toolbar holds the search, the figures in a line (agents working and their subagents, what needs you, live terminals and chats, tasks done of all with a progress bar and what is open, and the global chat's state with its one control), how fresh they are (**Live**; **Last read … ago** once a read is more than 30 seconds old; or why the sessions could not be read, keeping the last figures), and **Refresh**. Before the first read nothing is counted or listed, and it says what it is reading. **Projects** is a table. A row has a mark for the project's most pressing state, its name, group and how many things need you, its folder and number of worktrees; **Activity** (its agents working, waiting, done or of unknown state, then its live sessions: terminals and, once the chats were read, chats); **Tasks** (done of all beside a progress bar, then in progress and to do, on one line when the column has room, else one count to a line, never cut short); **Orchestrator** (the project orchestrator, chat or terminal, and its state); **Last active** (the latest time RiWork recorded something in it: a task changed, one of its live agents began what it is doing, or one of its chats' logs grew as far as that was read; **—** when nothing recorded a time); and **Tasks** and **Sessions** buttons that open those panels in the project's window. Filters list the **Active** projects (a live session or chat, or an open task; the default), those that need you (**Needs you**), have an agent **Working**, have tasks **In progress**, or **All**, each with its count; the order is **Priority** (what needs you, then what works, what runs, tasks in progress and open tasks), **Recent**, **Tasks**, **Sessions** or **Name**, each keeping the busiest first among equals. The search (Cmd+F; every word must appear somewhere, in any case) narrows every list: projects by name, group or folder, the attention, work and finished rows by what they say, tasks by title, project or branch, and automations by title or project. A filter that hides projects the search found says so and offers **Show all**. Beside the table, rails list **Needs you** (agents and chats waiting for an answer or an approval, chats whose agent failed within the last three days, orchestrators' failed chats always, and automations whose last run failed, was missed or is uncertain, unless paused), **Working now** with how long and how many subagents, **Finished in the last hour**, **Tasks in progress** across projects with when each changed, and **Automations**, each with its project, its next run or that it is paused, and how its last run went. The rails scroll on their own, so a long project list never pushes them out of sight. A wide window shows two rails, one for activity and one for tasks and automations; an ordinary one shows one; a compact one shows **Projects**, **Activity** or **Tasks** one at a time, chosen above them. In the colorful themes at the default text size, two rails start at about 1,450 points wide and one at about 1,100; Native at its default size draws text at 13 pt instead of 11, so everything needs 13/11 as much room: two rails from about 1,710 points (a 1,900-point window has both), one from about 1,295, and compact below that. A larger text size raises these widths alike. Columns that do not fit move into the project's own lines rather than being cut off: the orchestrator first, then the activity. The filter and the order are kept with the window's state (see below); the search is not. Searching, filtering, sorting, switching regions and refreshing change no project and start no agent, chat or chat host. Every row opens exactly what it names in that project's window: a window that shows the project is brought forward (else a window is opened on it, found by its id), and there it shows a session's tab, a chat as Sessions opens it, the project orchestrator's tab, a task selected in Tasks, the project, or Automations (an app automation's in the frontmost project window). No window changes project for it and the store's active project stays what it is; the global window stays the global window. A row of the global orchestrator switches the global window to Chat. A row whose session, chat, task or project is gone says so. The lists say when chats or automations are still being read or cannot be; nothing is shown as zero that was not counted.

New default orchestrators start the official `codex` CLI, install the embedded **riwork-orchestrator** skill in their context folder, and receive their scope, project UUID, and project root as appropriate, with their scope's delegation policy (see **Delegation** in [Settings](#settings)) and the skill's Hard boundaries in brief, which every LOAD SKILL message restates too. The startup message names the installed `SKILL.md` for Codex to read instead of carrying the skill text, which keeps the launch command far below tmux's limit of about 16 KB. Global context is `RIWORK_HOME/orchestrator`; project contexts are `RIWORK_HOME/orchestrators/projects/PROJECT_UUID`. Each waits for an objective. The skill covers global coordination, repository selection, task assignment, bounded delegation, progress inspection, and completion checks. Existing sessions show **LOAD SKILL** for a one-time upgrade that preserves their conversation, and again when their scope's delegation policy changes; it pastes the complete skill, with the policy as it resolves now, into the running Codex. Custom commands do not receive the skill automatically. Loading the skill does not schedule work.

Default project orchestrators launch Codex in unrestricted mode, with approval prompts and sandboxing disabled. This mode is saved with the session and preserved when its conversation is reloaded. Existing project orchestrators keep their startup mode; close and recreate them to use the new default. Global orchestrators retain the selected Codex account's permission and approval settings. Custom commands run as supplied. On a global orchestrator's first launch, Codex may ask you to trust its context folder; answer that prompt in the terminal before the startup skill loads.

**Terminal or chat.** An orchestrator runs as a Codex in a terminal tab, as above, or as a chat: a Codex, Claude or Muse conversation of the [chat host](#chat-host), in a chat tab, as was chosen when it was created: by the project's **Project Settings → Orchestrator** for its own orchestrator, else by **Orchestrator runs as** in Settings, whose default, Automatic, starts a Muse chat on Wonder Full or, when Muse cannot start, a Codex chat on GPT-6.1-Sol (see [Settings](#settings)). Everything that addresses an orchestrator handles both: P·ORCH, Cmd+Alt+O and the project **New Tab** entry open the project's terminal tab or its chat tab (an open tab is reused by the main-pane rules above, a new one opens where new tabs open), G·ORCH's Chat, Cmd+Shift+O and the global **New Tab** entry show the global one's terminal or chat in the global window, and the CLI, the MCP tools, schedules and the phone follow whichever exists. A scope has at most one orchestrator across both modes: creating one when the scope already has a terminal or a chat orchestrator returns that one, and the chat host itself refuses a second chat for a scope.

A chat orchestrator is an ordinary chat that the host knows by an `orchestrator` field in its `info.json` (`{"scope":"global"}` or `{"scope":"project","project_id":"…"}`; chats written before the field have none). It works in the same folder as a terminal orchestrator (`RIWORK_HOME/orchestrator`, `RIWORK_HOME/orchestrators/projects/PROJECT_UUID`) with the same **riwork-orchestrator** skill installed there, and its first message is the startup message a terminal orchestrator receives (its scope, project UUID and root, and the path of the installed `SKILL.md` to read), built by the same code. The agent's environment names its scope as a terminal orchestrator's does (`RIWORK_ORCHESTRATOR_SCOPE`, `RIWORK_PROJECT_ID`). The Codex account and the Cua.ai Driver connection are the ones every chat gets. **A project orchestrator never asks before it acts** (approval mode Full, as its terminal launches with approvals and sandbox off). **The global orchestrator is Supervised**: it asks before running commands and editing files, and a turn waits in the chat tab (and shows as waiting in `status` and the G·ORCH item) until you answer; a schedule defers meanwhile. A project orchestrator's tab is titled **P·ORCH · PROJECT** (the global one is the global window's Chat view), and G·ORCH and P·ORCH in the status bar are marked `●` while its agent works, `◌` while it waits for you and `✓` once it is done, as chat tabs are. A chat orchestrator whose skill is not the one this build ships, or whose scope's delegation policy changed since it was told, shows the same **Load skill** bar as a terminal one; it sends the whole skill and the policy to the chat as a message, once, when the chat is idle. Closing the tab (or the global window) leaves the chat; `riwork orchestrator close` ends its agent **and deletes the chat and its history**, as closing a terminal orchestrator ends its session, and the next one is created as Settings then says. A chat orchestrator whose agent cannot start, or whose startup message cannot be sent or recorded, is not kept: creation reports the reason and leaves nothing behind. Creating a scope's orchestrator takes turns across the desktop, the CLI and the MCP server, in either mode (a lock file per scope under `RIWORK_HOME/orchestrators`): a second request waits until the first one's orchestrator has started and been told what it is, and then gets that one.

**The id.** A chat orchestrator's id is its chat's id, one UUID everywhere: it is the `id` of its entry in `riwork orchestrator list --json` (and `chat_id` repeats it, for readers that look for the chat), what `riwork chat events`/`chat command` and the phone's `chat.*` methods take, and what `riwork schedule create --shell` takes.

```sh
riwork orchestrator create --json
riwork orchestrator create --project PROJECT_ID --json
riwork orchestrator list --json
riwork orchestrator status --project PROJECT_ID --json
riwork orchestrator output --project PROJECT_ID --lines 120 --json
riwork orchestrator send --project PROJECT_ID "Implement the requested project objective"
riwork orchestrator load-skill --project PROJECT_ID
```

All orchestrator operations use the global scope when `--project` is omitted. `riwork orchestrator close` ends only the global session; `riwork orchestrator close --project PROJECT_ID` ends only that project's session. Worker shell lists exclude orchestrators. MCP orchestrator status/output tools accept an optional project selector.

For a chat orchestrator the same commands mean the following. `create --json` adds `"created"` (false when the orchestrator was there already) to the entry. `list --json` and `status --json` give every entry `"mode"`: `"terminal"` or `"chat"`; a chat's entry has the usual fields (`id`, `project_id`, `worktree_id` null, `kind`, `cwd`, `command` null, `harness`, `unrestricted`, `alive`, `created_at_unix`, `orchestrator_skill_loaded`, `activity`, `last_activity_unix`) and `chat_id`, `provider` (`codex` or `claude`), `title` and `state` (`starting`, `idle`, `running`, `waiting`, `stopped` or `failed`, with `state_message` when failed). `alive` stays true for as long as the chat exists, because a message resumes a stopped or failed one, and `activity` is `working`, `waiting`, `done`, `unknown` (starting, stopped) or `exited` (failed). `send` is a chat message (a stopped chat is resumed first). `output --lines N` is the conversation as plain text, the last N lines (200 by default): your and the agent's messages whole (`user: …`, `agent: …`), one line for each command, edit, tool call, search and plan (`[command] ls -la (exit 0)`), and what the chat waits for last (`[waiting for approval] …`). `load-skill` sends the whole skill as a message, once, to an idle or stopped chat. `cwd` prints its folder. `metrics` and `attach` are for terminals and say so. Looking (`list`, `status`, `output`) never starts the chat host: while it is not running the saved chats are read, and every chat reads as stopped.

## Chat tabs

The [chat improvement roadmap](docs/chat-improvement-roadmap.md) tracks the output, conversation, worker, and mobile improvements, with delivery status and acceptance checks.

A chat is one native conversation for every model, Codex's and Claude's, instead of an agent's terminal. **New chat…** under **New Tab** in a pane's **…** actions menu, **View → New chat…**, **New chat…** in the Sessions panel and Cmd+Option+Shift+C open a dialog that asks where the chat works (the project's root or a worktree, the selected one first), its permissions (Supervised, Auto-edit, Full, which never asks before it acts, or Plan) and its model: one list with Codex's models and Claude's under their own headings, each with its provider's default, a search field, and a field for a model ID the list does not have, which is a model of the provider whose model is chosen. The model decides whether the chat is Codex's or Claude's; nothing else asks. **Create chat** opens it in the main pane. A chat is driven through the agent's structured interface (`codex app-server`, Claude's stream-json mode) by the chat host, a background process (`riwork chat serve`) that owns the agent process and the chat's event log. A tab only follows the chat, so closing it, reloading the app or restarting the host does not end the chat: a restored layout reopens its chat tabs by id and rebuilds each transcript from the start of the log, and while the host is away a tab shows **Reconnecting…** and subscribes again from the last event it saw. A tab whose chat was deleted says so and offers **Close**.

The tab is titled by the chat, with the agent's name or, with **Icons instead of labels** on, its mark (`>_` for Codex, a spark for Claude), and a working (●), waiting (◌) or done (✓) mark in front of the title, with the same hover hint that agents in terminals get. Open chats count among the agents in the status bar and in the project and worktree rows. Messages read as a conversation in one centered reading column: your messages as blocks across it, the agent's as Markdown (headings, lists, tables, quotes, links that open in the browser, code blocks with a **copy** button; **copy** on hover takes the whole message). Drag to select text within a paragraph, a table cell or a code block, double-click a word, triple-click the whole run, and Cmd+C copies it. The agent's thinking is folded under **Thinking…**. Commands, file changes (with an expandable diff, additions and removals tinted) and other tool calls are cards that open on click; command output preserves terminal colors and has independent Earlier, Newer, and Latest controls, with up to 200 lines per page. Copy page takes the displayed text; Copy retained includes the bounded retained history. Long Markdown plans have an expandable preview and explicit Save Markdown / Save to workspace actions; todo lists remain checklists. The list follows new text until you scroll up, and **↓ latest** brings you back.

Select part of an assistant answer and choose **Reply to selection** to add a source chip above the message box. Select text in a diff and choose **Comment on selected lines** to capture the file, exact old/new line ranges and selected patch lines. Each chip has its own editable quote and comment, Remove, and Go to source. References and comments recover with the draft and attachments. Changed or missing sources are marked explicitly; Re-anchor only succeeds when the original excerpt still has one unambiguous location. Send includes readable reference text for the provider. Selections spanning different answers or files are not combined into a misleading reference.

**Review files** opens a focused review with folders, Expand/Collapse all, file and hunk navigation, and comments attached to the reported patch revision. Back to chat restores the transcript's reading position. This surface reviews the agent's reported edits; it does not claim they are a net workspace diff. Large file lists are paged, each diff preview retains up to 400 lines, and Copy patch preserves the full reported patch.

Completed Mermaid blocks offer **Diagram / Source** and enlargement in the image viewer. Rendering uses the bundled Mermaid library locally, with no network requests; streaming, malformed, oversized, or unavailable diagrams retain their source. Other completed code blocks add **Reader** for an editable scratch copy and **Save…**, alongside Copy and Wrap. Shell snippets offer **Copy & open terminal…**: choose an existing local terminal, then paste the copied snippet yourself. The reader and save actions accept snippets up to 256 KiB and never alter the conversation or message draft.

Local links offer **File actions…** with relative/full path copy, Reveal in Finder, and the system's preferred application for that file type. The actions recheck the chat's registered project scope and the current regular file before proceeding. Images offer **Save displayed image…**, **Copy image**, and **Open original** when a local file or URL exists. Save and Copy use the displayed, potentially resized preview as PNG; a local original that has changed since preview must be reopened before it can launch. Exports use a chosen destination and require confirmation before replacing an existing file.

**Find** also searches collapsed Activity, tool details, and complete plan documents, opening the selected match. Command search covers the current retained page; navigate to Earlier or Newer to search another page.

**Turns** opens a bounded list of prompt and answer previews. Previous and next controls move through the conversation without searching for a particular word; choosing a preview jumps to that exchange. Navigating to a turn pauses live following so new output preserves your reading position. **Latest** resumes following new output. Each completed turn's Activity disclosure summarizes observed work, such as **Read 8 files · Changed 3 files · Ran 2 commands**. Repeated paths count once, search hits do not count as files read, and failures stay available when the disclosure is expanded, including attempts recovered before the final answer.

**Images in a chat.** An image the agent shows by path, by `file://` URL or in a Markdown image is a card that reads the file only when you open it (a click), at most 24 MiB, decoded and shrunk like the Files preview, with **Click to view** for the whole picture. A relative path is read from the folder the chat works in. A path or URL may name an image anywhere in the chat's own project: its root, its repositories, any of its worktrees, and its project orchestrator's folder (`RIWORK_HOME/orchestrators/projects/PROJECT_UUID`). The global orchestrator's chat may show images from every registered project and project orchestrator folder, and from its own (`RIWORK_HOME/orchestrator`). Every chat also shows the images you sent it: its own attachment snapshots in `RIWORK_HOME/chats/CHAT_UUID/attachments` (stored without an extension and shown only if they hold a supported image). Nothing else is read: not another project's folders (for a project's chat), not another chat's attachments or anything else under `RIWORK_HOME/chats`, not the rest of `RIWORK_HOME`, not a folder that is merely a parent of these, and not through a symbolic link or `..` out of them; the folders come from the projects and worktrees RiWork has registered, checked against the chat's own project and orchestrator identity, and change as soon as those do (an image shown from a folder that is gone is dropped). **Open in Files preview** under an image is offered only when Files can show it, that is when it is in the chat's own worktree of the window's project; an image from another worktree is viewed in the chat. Clicked file links in a chat still open in Files only within the chat's own worktree.

The message box is a card inset from the bottom of the tab. While it is empty in a wide tab it shares one row with **+** and its controls (the model, effort and Fast choices, the mic, **Interrupt** and Send); once you type or attach something it takes the card's whole width and the controls move to a row under it, and a narrow tab gives them a row of their own. **+** offers **Files and images…** and **Paste image**; files can also be pasted or dropped on the box. A notice, a request for approval and a question from the agent are cards in the same column, above the message box. Every theme lays a chat out this way; a theme chooses only its colors, fonts and how its cards and buttons are drawn.

Desktop drafts restore text and completed attachment snapshots after closing a tab or restarting. Saved attachments appear as **Checking** while their files are verified in the background; typing remains available, and Send and preview wait for verification. Missing or changed files remain visible as **Unavailable**, with **Check again** and Remove, and their saved references survive closing the tab. A check or retry in an older window cannot replace a newer window’s saved draft. Up to eight unresolved submissions per chat are retained separately; interrupted sends reopen as **Uncertain** for review and require an explicit resend. Attachments that had not finished staging show a recovery warning and must be attached again. Storage keeps the newest 64 chats for 30 days, with up to 256 KiB of text per draft or submission; oversized new draft text is kept only for the current run. Sending waits asynchronously for the recovery snapshot to reach disk; a storage failure reports that nothing was sent and keeps the editor. A graceful reload waits for queued drafts before starting the replacement app and cancels if saving fails.

Subagents and worker shells and chats also appear in a sticky **Workers** shelf directly above the message box. It shows two compact rows, with failures and workers waiting for input first; **All** expands the bounded list, and a row opens its output and actions. Each worker appears once even after follow-up assignments. The shelf stays visible while the transcript scrolls and leaves the message draft and focus intact. Status badges come from the provider or session inventory. With a reported Codex or Claude model, a visible chat can summarize changed output through a separate background request using that model and its account/billing choice: at most one batch every 30 seconds, with bounded input and one short sentence per worker. Unchanged output makes no further model calls. These summaries do not send messages into the parent conversation or alter worker state. Output snippets remain available while a summary is pending or unavailable; Muse currently uses these snippets. Hovering a generated summary identifies it as AI-generated.

When the agent asks to run a command, change files or use a tool, a bar above the message box names it and offers what the agent allows: **Allow**, **Allow for session**, **Deny**, **Stop**. With the message box empty, ⏎ allows, ⇧⏎ allows for the session and ⎋ denies; anything typed makes ⏎ a message again. Questions from the agent show their options as buttons beside a text field. In the message box ⏎ sends, also while a turn runs (the agent steers or queues it), ⇧⏎ starts a new line, and Cmd+. stops the turn. While a turn runs, **Interrupt** stands in the send button's place until something is typed; then **Send** is back, to steer. The toolbar sets the approval mode (Supervised, Auto-edit, Full, Plan), the model (any provider's, see below; a Claude agent that has not listed its models gets a name field with opus, sonnet and haiku) and the effort, compacts the context, and shows how much of the context window is in use. A Claude chat that runs on an Anthropic API key instead of a Claude subscription shows an **API key** badge there, as soon as its agent starts: Claude's own handshake says how it signed in (its `account`, of which the chat keeps only the key's source and the plan's name, never the email or organization). Its hover hint names the key's source and, for a key from `ANTHROPIC_API_KEY`, how to go back to the subscription. A Claude chat's message box has a billing switch beside the model, **Subscription** or **API key**, saved with the chat (`claude_billing` in its info, never a key): one click switches it, and the chat host restarts Claude on the same conversation, as it does for Muse's contributor mode (refused while a turn runs or waits, or Claude still starts; a restart that fails leaves the chat as it was, and says so). New chats start from the Settings default; a chat from before the switch follows the Settings default until it is switched. It shows what the running Claude says it bills once it has said (else the chat's choice), warns when that is not what the chat chose (a Claude started before the key was saved, or an `apiKeyHelper` of Claude's own), and with no key saved it opens Settings at the key field instead of switching. When a Claude chat on its subscription hits the five-hour or weekly usage limit, the limit's banner offers **Use API key** when a key is saved, which switches the chat and, if the limited turn had produced nothing yet, sends its message again, or **Enter API key**, which opens Settings at the key field. Closing the banner dismisses that limit until its reset; the banner goes once Claude bills an API key. Claude's own cost figure is shown as an estimate, never a bill. **⋯** has **Hand off…** (see **Handoff**), **Stop chat**, which ends the agent's process but keeps the chat (a stopped chat says it resumes when you send a message; a failed one offers **Retry**), and **Delete chat**.

Typing `/` at the start of the message box, or `@` at the start of a word, opens a list just above the box at the caret: the chat's slash commands, or the files and folders of the chat's folder. the list offers RiWork's own `/memo` in every chat and the provider commands that work through it, which today is Claude's `/compact` in Claude chats (Codex and Muse read a typed `/compact` as words; their **Compact** is the toolbar's). Commands are registered in one place, `COMMANDS` in `crates/riwork-engine/src/chat/suggest.rs`, which the phone's list reads too (`riwork chat suggestions CHAT_ID --json`, the connector's `chat.suggestions`). `@` lists the folder once in the background (breadth first, at most 5,000 entries, 50,000 looked at and 2 seconds, without what `.gitignore` leaves out, `.git` or symbolic links), keeps the listing for 30 seconds for every tab of that folder, and only filters it while you type. The highlighted row has a preview beside the list (above it in a narrow tab): what it is, what sending a command does, a file's size and first lines, and what accepting puts in. ↑ and ↓ move, ⏎ or ⇥ put the row in, ⎋ closes the list until that word is typed again, and a click puts a row in. Accepting only edits the draft: a command goes in as `/compact `, a file as its path relative to the chat's folder (a folder with `/`, a path with spaces in backticks), which the agent opens from where it runs; nothing is attached, and nothing is sent until you press ⏎ or Send. A `/` or `@` inside a word (`a/b`, `me@host`) opens nothing, nor does `/` after the first word. The list stands above the box, so it never covers Send, Stop or the pickers.

Typing `&` in the message box (at its start or after a space, anywhere in the message and as often as you like; `&` inside a word or a URL is just text) lists the models of every provider, so a message to an orchestrator in a Codex or Muse chat can name a Claude model and the other way round: the chat's own list (the one its model menu shows), then what each provider's saved chats listed (as `riwork chat models` reads them), each model once and each row naming its provider. They are the most used first, whatever the provider: how many of your own chats of that provider are set to each now (chats with a first message, scheduled ones included, not workers' or orchestrators'), counted from the chats' saved metadata and kept 30 seconds; ties and models you never used keep that order. Nothing new is recorded for it, so a deleted chat no longer counts and a chat that changed model counts only for its latest. Claude's `default` entry is not offered: it is the Claude CLI's own choice, not a model, so `&default` would name nothing. The chat's current model is marked, and typing filters the list by id or name. Accepting a model (⏎, ⇥ or a click) puts its mention in the message: `&` and the model's id as its provider takes it (`&opus`, `&gpt-6.1-sol`, never the display name), and a space after it unless one follows already, as `/` and `@` do; ⌘Z takes it back. A mention is only text, for telling an orchestrator which model you would like for the work you hand it (`&opus design the API, then &gpt-6.1-sol implement it`): nothing is switched or sent, the chat keeps its own model and effort, a running turn is not touched, and the orchestrator still decides (its skill reads a mention as your preference, and says so when it uses another model). The current model is put in like any other. The preview shows the mention, the model's provider, name and description and the count. With no list saved for any provider, no `&` list opens here. The phone's list comes with `riwork chat suggestions CHAT_ID --json` (`mention_models`), with the same counts.

**Either provider in one chat.** The model menu lists the chat's own provider's models first and then the other provider's: its default, and the models that saved chats of it reported. Choosing one of those goes on with that provider in the same chat and tab. The chat host stops the agent, writes the conversation so far down from the chat's own log, as a handoff document would (`context.md` in the chat's folder), and starts the other agent on a thread of its own with that conversation in its instructions (appended to Claude's system prompt, Codex's developer instructions), at every start and resume from then on. The transcript stays whole, with a line that says **Continued with Claude (opus), which has the conversation so far.**, the tab's mark follows the provider (and so does a title the chat was given by default, such as **Codex chat**), and the approval mode stays; the model is the one chosen, the effort is that model's default, Fast is off, and a chat moved to Codex runs under the project's Codex account. The rows wait while a turn runs or waits for you (**Finish or interrupt the turn first**). The new agent has the conversation as a document, not as its own history, so it knows what was said and done but not what a command printed that the document leaves out. **New chat…** at the end of the menu opens the dialog for another chat; the conversation you are in stays as it is.

## Handoff

`riwork handoff` passes a conversation from a shell or a chat to a new shell or chat, on another model, effort, permission mode or Codex account, in the same project, worktree and directory. The source is neither stopped nor changed; only `--context summary` gives it anything, one message and the turn that answers it.

```sh
riwork handoff --to chat --provider codex --model gpt-5 --account Work
riwork handoff --to shell --provider claude --model opus --mode plan --note "Review the parser change only"
riwork handoff --from SHELL_OR_CHAT_ID --to chat --provider claude --context summary --json
```

`--to shell|chat` and `--provider codex|claude|grok|muse` are required (a chat is Codex, Claude or Muse; Grok runs in a terminal). `--model` and `--effort` take their value as it is, also with `=`, like `chat new`. `--mode supervised|auto-edit|full|plan` is how much the new agent may do without asking: for a chat it is the chat's mode (supervised by default); for a shell, `auto-edit` and `plan` pass the CLI's own flags for a shell (Codex `--sandbox workspace-write` or `read-only` with `--ask-for-approval on-request`; Claude and Grok `--permission-mode acceptEdits` or `plan`; a Muse terminal has no such modes, so `plan` passes `--disable-write` and `auto-edit` keeps its supervised default; for a Muse chat the mode is the chat's approval mode, mapped to Muse's own `promptUnmatched`/`onRequest`/`allowAll`, with Plan starting the conversation under Muse's Read only profile), `full` is the permission bypass of the unrestricted launches, and `supervised`, like leaving `--mode` out, keeps the CLI's usual permissions. The model flag is Codex `-m`, Claude `--model`, Grok `-m`, Muse `--model`; the effort is Codex `-c model_reasoning_effort=…`, Claude `--effort`, Grok and Muse `--reasoning-effort`. A terminal target is started as **New Tab** starts it, with the same Cua.ai Driver wiring; a chat is made by the chat host.

**The source.** `--from` takes a shell's or a chat's id, or a unique prefix of at least eight characters of either (a shell's id needs no more than that here, unlike other commands). Without it the command hands off the session it runs in: a terminal's `RIWORK_SHELL_ID`, a chat agent's `RIWORK_CHAT_ID`. So an agent that is told to hand itself over only runs the command; one that has both variables (a terminal started by an agent in a chat) is asked to pass `--from`. An orchestrator's conversation is not handed off. The target is started in the source's project, worktree and directory (a plain shell's current directory); a chat without a project can only be handed to a chat, which is refused up front for a shell.

**The account.** `--account` is a Codex account's label or id, resolved against the saved accounts the way a launch resolves its selection (see Codex accounts under Settings): an id, or a label, email or workspace name in any case (`Work` for `me@example.com · Work`), or a part of a label that only one account has; a name that fits two accounts is an error that lists them, and one that no account has lists the known ones. An account that is saved but unavailable (Orca removed, its home missing) is refused by name, never swapped for another. `System default` is an account too. Without `--account` the project's own choice applies, as in a new tab. Claude, Grok and Muse have no RiWork-managed accounts, so `--account` with them is an error saying that only the system login exists.

**What the new agent reads.** The handoff is a Markdown document written to `RIWORK_HOME/handoffs/HANDOFF_ID.md` (mode 600, in a folder made mode 700; never in the repository, and kept until you delete it). Its heading names the source (agent, chat title or terminal, short id), its model when known, the project and worktree, the directory, the time, what the document holds, any caveat, and the `--note`. A document is your conversation as it was, secrets you typed or a command printed included, and the new agent's provider receives it: it is not redacted. Below the heading, user and agent messages are in full, and the rest is short: a command is its first line with the first and last six lines of its output and its exit status, edited files are listed by name, other tools are their name and a few words about what they were asked, and plans and todo lists are checklists. The agent's hidden thinking and the bulk of tool results are left out. A document is at most 200 KB: when the conversation is longer, the newest items are kept as they are, the oldest are left out under a marker that says how many, and the first request stays at the top; one message of more than 50 KB keeps its start and its end.

The new agent's first message is "You are taking over a conversation from SOURCE. Read the handoff at PATH and continue from where it left off." followed by the note. A chat whose document is under 48 KB gets the document in the message instead of the path; a terminal always gets the path, since a command line is limited. A Codex or Muse terminal receives the message as its startup prompt followed by the Cua.ai guidance a normal start carries; Claude and Grok receive it as their prompt.

**How each source is read.**
- A **chat** is its `events.jsonl`, folded with the same `Transcript` a chat tab draws, so it works while the host is not running.
- A **Codex terminal** is the rollout its pane is bound to (the binding RiWork keeps for activity, or the id of a `codex resume`), read from the newest 64 MB of it; its `item_completed` items are used, and the turns of a rollout from a version before them (a rollout can begin in one and go on in another) are read from what was sent to the model. An edit or command that was declined, or an edit that failed, is shown as such and not as a changed file.
- A **Claude terminal** is the session transcript `~/.claude/projects/FOLDER/SESSION.jsonl` (or under `CLAUDE_CONFIG_DIR`), found through the session id Claude's hooks report; a subagent's own conversation and notes the CLI writes for itself are left out.
- A **plain shell, Grok or Muse** has no conversation file, so it is the tmux scrollback (the newest 5,000 lines, as `shell history` reads them), which is the rendered screen and not a transcript. A Codex or Claude terminal whose conversation file is not known yet (RiWork learns it after the first turn) falls back to this too, and the document's caveat says so.

**`--context transcript|summary`.** `transcript` (the default) works for any source. `summary` is for a live Codex or Claude, a chat or a terminal, that is idle: RiWork sends it a message asking it to write a concise handoff summary (goal, state, decisions, open tasks, files touched, next steps) to a file under `handoffs/`, and waits up to five minutes for the file and for the end of that turn. A terminal gets the message the way a schedule does: the same bracketed paste and one Return under the shell's input lock, and only while the screen shows the agent's empty prompt; a chat gets a `send`. The document is then the heading and that summary. An agent that is working, waiting, stopped or not running is refused at once, with nothing sent; this includes the agent that runs the command itself, which is busy running it (it uses the transcript, or you run the handoff from outside). An agent that was asked but writes no file in time, ends its turn without one, or goes away is not an error: the handoff holds the transcript, the document's caveat says that the summary did not come and why, `--json` has it as `fallback`, and the text output says so. An agent that must ask before writing outside the project (a supervised chat, a sandboxed Codex) waits for your approval in its tab, within the same five minutes; in the app the dialog can be hidden meanwhile (below), and from a script you answer in the tab as the command waits.

**Output.** The text output says which agent and kind were started and where the document is. `--json` prints `{"handoff_id","document","target":{"kind":"shell"|"chat","id"},"context":"transcript"|"summary"}` and `fallback` when a summary was replaced. A chat whose agent could not start is kept as failed and the command fails, naming the chat and the document so the message can be sent again. Progress ("Writing summary…") goes to stderr.

**Telling an agent to do it.** Say it the way you would to a person: "hand this over to a Codex chat with gpt-5 on my Work account". The agent runs `riwork handoff --to chat --provider codex --model gpt-5 --account Work`; a sandboxed agent has to ask you first, since the command writes under `RIWORK_HOME` and reaches RiWork's sockets. A new shell is a tab in a window that has the project open, as any shell made from the CLI is; a new chat is kept by the chat host and listed by `riwork chat list`. The embedded orchestrator skill and the `riwork-workspaces` skill mention the command.

**In the app.** **Hand off…** in a Codex, Claude, Grok or Muse tab's **…** menu (its **Tab** section) and in a chat tab's **⋯** menu opens a small dialog: **Open it as a** Shell or Chat, the **Agent**, the **Model** (a free text, with a few suggestions), the **Codex account** (the project's own, the system's, or a saved one, from the list Settings keeps) when the agent is Codex, **What it reads** (Transcript or Summary) when the source can be asked, and a **Note**. Tab or the arrow keys move between the lines, Left and Right or Space change a choice, Return hands off and Esc closes. The work runs off the UI thread while the dialog says what it is doing ("Writing summary…"); an error, such as a busy agent being asked for a summary, shows in the dialog so the choice can be changed. Because a summary can take minutes, and the agent asked may be waiting for your approval in its own tab, Esc (or **Hide**) while it works puts the dialog away and lets the work finish: a notice follows its steps, only one hand off runs at a time, and the window is free. When it is done the new tab opens in the pane new tabs go to (the main pane, if there is one); if a summary did not come, a notice says the transcript was used. A project on another Mac has no hand off; a notice says so.

## Settings

Open **RiWork → Settings…**, press Cmd+, or choose **SETTINGS** under **Views** in a pane's **…** actions menu. Settings opens as a normal workspace tab: drag, split, close, and restore it like the other panel tabs. Preferences save automatically to `settings.json` under the RiWork data directory and are shared across open windows and app processes. A value this build does not recognize, for example a theme from a newer build, reads as that setting's default and stays in the file until you change that setting; an invalid Codex account selection still blocks new Codex launches instead of falling back to the system account, while plain shells keep opening.

- **Codex accounts** detects the current Codex profile and saved accounts from Orca. The current profile is `~/.codex` or the `CODEX_HOME` from your own environment, and its row shows the resolved path; an account home that RiWork exported into a session is never mistaken for it, so a shell inside an account-bound session still starts system-default sessions on your own profile. Use **REFRESH ACCOUNTS** to check again, then select an app default for new Codex sessions; a project can override it in **Project Settings**. Existing sessions and resumed conversations keep their original account. Quota is read separately for each account and follows the active Codex session's saved account.
- **Project Settings → Memo** (the last section) is the project's own Markdown notes: one free-text memo per project, at most 32 KB. It saves by itself a moment after typing pauses, when the editor loses focus and when Project Settings closes, and says so under the editor (**Saved automatically**, **Saving…**, or why not, with **Retry**); nothing longer than the limit is saved. It is kept in `state.json` under `project_memos`, beside the projects and not in them, so `riwork project list --json`, the MCP tools and the phone's project list never carry it, and no agent is ever given it. On the phone it is **Memo…** in a project's ⋯ menu. Typing `/memo` as the last word of a chat's message, then Return, sends nothing: it shows that project's memo above the message box with **Insert into composer** (adds it after your draft, still unsent) and **Edit** (opens it here); an empty memo offers Edit only, and the global chat, which has no project, says there is no project memo there. The last save wins, whether from the Mac or the phone: an editor takes a newer memo only while it has nothing unsaved. `riwork project memo show ID` prints it and `riwork project memo set ID < notes.md` replaces it.
- **Project Settings → Orchestrator** chooses how this project's orchestrator runs when it is next created: **Inherit app default** (the default, and what older projects read as; it names what Settings say now), **Automatic**, **Terminal** or **Chat** with its provider and model, as in Settings. It saves immediately as the project's `orchestrator` in `state.json` (`{"mode":"inherit"}`, `{"mode":"automatic"}`, `{"mode":"terminal"}` or `{"mode":"chat","provider":"muse","model":"muse-wonder-full-1.0"}`), which `riwork project show ID --json` and `riwork project list --json` print, and applies only to that project's orchestrator: the global orchestrator always follows Settings. A saved value this build cannot read is kept as it was, said to be unreadable, and inherits until you choose. `riwork orchestrator create --json` says who chose (`source`: `settings`, `project` or `request`).
- **Project Settings → Delegation** overrides the Settings delegation policy for this project's orchestrator, field by field: each row has **Inherit** (the default, naming Settings' value) beside its own choices. It saves immediately as the project's `delegation_policy` in `state.json`, in the shape Settings use, with only the fields chosen; a field this project does not choose follows Settings, then RiWork's default. The global orchestrator always follows Settings.
- **Project Settings → Codex Account** selects **Inherit app default**, **System default**, or an available saved Orca account. The choice saves immediately and applies to new Codex sessions and new project orchestrators. Older projects inherit the app setting. Global orchestrators always use the app setting. An explicit saved account that later becomes unavailable (for example when Orca is removed or the account is deleted) remains selected and prevents new Codex launches, including the `codex` launcher in a shell, with an error until it is restored or changed. Plain shells still open; they just start without an injected `CODEX_HOME`. RiWork reads only Orca's public account list and its own metadata cache; it never reads account credentials.
- New plain project shells start with `CODEX_HOME` set to the project's effective choice. The RiWork `codex` launcher in a plain shell resolves the current project choice each time a new Codex invocation begins; a resume or managed child keeps its original account. A custom command that runs `codex` by name goes through the same launcher and resolves the project choice too; only an absolute path to a Codex binary bypasses it and uses its own environment. Utility commands such as `codex login` skip account binding, so RiWork's launcher refuses `login`, `logout`, and other credential or configuration changes (`mcp add`, `plugin`, …) while `CODEX_HOME` is an Orca-managed account home: manage that account in Orca, or point the command at your own profile with `CODEX_HOME=~/.codex codex login`. A plain shell shows a Codex account (**A1**, status bar) only while Codex is running in it. Changing a default never changes a running process or its saved account label. When multiple live Codex account homes exist in one project, tabs show **A1**, **A2**, and so on beside the session title; the focused account uses the same number in the status bar. Numbers derive from the sorted frozen homes within each project and may change when the set of live accounts changes.
- **Remote** lists the Macs paired with this one, with their link state and a two-click **REMOVE**, and has **ADD HOST** (paste a pairing link) and **PAIR ANOTHER MAC** (make a link that lets another Mac control this one). See [Controlling another Mac](#controlling-another-mac). Hosts are kept by `riwork-remote` in `RIWORK_HOME/remote/hosts.json` and never in `settings.json` or the layouts.
- **Status bar** lets you show or hide the entire bar, choose visible items, move each item left or right, and change its order with the arrow buttons. The current project appears on the left by default. Worktree and agent activity are optional; **RESET DEFAULTS** restores the original arrangement. Preferences apply across windows.
- **Theme** defaults to **Follow Ghostty**: panels, tabs, menus, and terminals share your Ghostty palette. RiWork uses Ghostty's own configuration loader, including recursive files and custom themes. It checks those files every couple of seconds and re-reads the configuration only when one changed, so palette edits appear within a few seconds. **Native**, **RiWork**, **Catppuccin Mocha**, **Tokyo Night**, **Gruvbox Light**, and **Hermes** apply matching workspace and terminal colors while retaining your other Ghostty preferences. **Hermes** sets the interface in the system font, with SF Mono for code, and draws its chats' message box and cards as flat panels with small corners and a filled send button. Preferences are shared across windows and app processes. Selecting a RiWork theme does not edit the standalone Ghostty app's configuration.
- **Native** is black on white, and white on black while macOS is in dark mode; it follows the system appearance as it switches. Everything is greys except one signal color, a deep orange (macOS's orange in dark mode), kept for what must stand out: agents at work, errors, and warnings. Selection and keyboard focus are black or white, and a pane's selected tab is a full-height, square cell in the content's background instead of an underlined cell; the window's traffic lights sit on the bar without the filled island behind them. Native draws its interface in the system font (SF Pro) with SF Symbols for its icons, writes its labels in sentence case, and uses macOS-style controls: capsule buttons, switches instead of ON/OFF boxes, segmented choices, soft rounded cards in Settings, and inset rounded rows whose selection is a fill. Codex and Claude chat tabs follow it too: messages in the system font, your own as grey blocks, tool calls as rounded cards with chevrons, the toolbar's choices as pop-up capsules, its menus like the pane menu, and a round send button in the message box's card; code, diffs and command output stay in SF Mono (Menlo where it is missing) whatever **Interface font** says. The colorful themes keep Menlo, capital labels and RiWork's square, outlined controls. `RIWORK_APPEARANCE=light` or `dark` in RiWork's environment pins the appearance instead of following the system.
- **Terminals match the theme** (Native only, on by default, saved as `native_terminal_colors`) gives terminals Native's white or black background and a quiet ANSI palette whose normal colors read at 4.5:1 or better. Off keeps Ghostty's own colors.
- **Interface font** (Native only, saved as `interface_font`): **System (SF Pro)** for everything, or **System + monospace accents** (the default), which keeps paths, branches, shell ids, commands, shortcut keys and the status bar's counts in SF Mono (Menlo where SF Mono is missing). The system font draws every size 2 pt larger, so the default 11 pt is drawn at 13 pt, the macOS body size, and **Text size** shows the size drawn (13 pt by default, stepping by whole points); with **MATCH TERMINAL** it is Ghostty's number as it is.
- **Use RiWork terminal colors** remains available under Follow Ghostty for existing preferences and is off by default. Turn it on to keep RiWork's original terminal palette. Theme changes preserve running shells, Codex/Claude/Grok sessions, tabs, and splits; returning to Ghostty's colors reconnects only terminal display clients.
- **Text size** sets RiWork's own text (panels, tabs, menus, the status bar, Settings, and hover hints) in points, like Ghostty's `font-size`: the number is the size of the panels' list text, from 9 to 24 pt; 11 pt is the original size. **−** and **+** in the row, the arrow keys (or − / =) on the focused row, Cmd+= / Cmd+- outside a terminal, or the **View** menu step it by 1 pt, as Ghostty's own Cmd+= does; **RESET**, 0, or Cmd+0 returns to 11 pt. Bars, rows, menus, and icons grow with the text, and terminals keep their own size. It applies to all open windows at once and is saved as `ui_text_size` in `settings.json`; a value out of range is pulled into it and anything but a number reads as 11. **MATCH TERMINAL** in the same row (or M, Enter, or Space on the focused row; off by default, saved as `ui_text_matches_terminal`) uses the `font-size` in your Ghostty configuration instead and shows the same number, so the panels' list text is as large as terminal text (Ghostty's macOS default is 13 pt). It is read with Ghostty's own loader including `config-file` includes and re-read within a few seconds of an edit; a terminal you zoomed with Cmd+= is not followed. Changing the size by any means turns matching off and steps from the size shown.
- **Icons instead of labels** is off by default. Turn it on to show a small icon instead of the name on the built-in panel tabs (Projects, Worktrees, Files, Preview, Tasks, Shells, Usage, Settings, Project Settings, and Schedules) and on toolbar buttons: **+ FOLDER** and **+ PROJECT** in Projects, the create-folder button in Project Settings, and the file actions in Preview (Edit in Vim, Copy Path, Copy Contents, Reveal, Open Externally). Hover an icon for its full name and shortcut; a button that is unavailable says why. Shell, agent, orchestrator, and editor tabs keep their titles, and the focus-mode bar still shows the full name. It applies to all open windows at once and is saved as `panel_tab_icons` in `settings.json`; the key keeps that name from when the setting only covered tabs, and a build without the setting leaves it alone.
- **Open the preview when a file is selected** is on by default and saved as `open_preview_on_select` in `settings.json`. Choosing a file in Files then opens the Preview panel in a pane of its own, or brings it forward if it is hidden behind another tab that is not a terminal. Turn it off to arrange the panes yourself: a Preview tab you closed stays closed, and one you left behind another tab stays there. It applies to all open windows at once.
- **Keep agent transcripts in scrollback (inline mode)** is on by default and saved as `agent_inline_mode` in `settings.json`. A full-screen agent draws on the terminal's alternate screen, where tmux keeps no history, so the phone could only page through the app by sending it PageUp and PageDown over the network. With this on, new agent sessions draw on the main screen: Codex starts with `--no-alt-screen`, Grok with `--minimal` (Grok's own `--no-alt-screen` still redraws a fixed full-height canvas and leaves no transcript), and Claude Code with `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`, which overrides a `"tui": "fullscreen"` in your Claude settings. The conversation then becomes ordinary terminal scrollback that the desktop wheel and the phone's `shell history` can read and scroll locally. The setting applies to agent tabs, orchestrators, session reloads, and a `codex`, `grok`, or `claude` typed in a RiWork shell when it opens an interactive session; `codex exec`, `grok -p`, utility commands, and an invocation that already names its screen (`--no-alt-screen`, `--minimal`, `--fullscreen`) are left as typed. It is read when an agent starts, so a running session keeps its current mode until it is restarted. Turn it off to run the agents full screen again. Inline Codex and Grok clear their scrollback and draw the transcript again at the new width whenever the pane is resized, which includes the phone pinning or releasing the pane size.
- **Agent terminals run unrestricted** (Agent sessions) is on by default and saved as `agent_terminals_unrestricted` in `settings.json`. On, Codex, Claude and Grok from the **New Tab** menu, Cmd+Shift+C, Cmd+Shift+L and Cmd+Shift+G, and from the paired phone start without approval prompts: Codex with `--dangerously-bypass-approvals-and-sandbox`, Claude with `--dangerously-skip-permissions`, Grok with `--always-approve`. Off, the same entries start them with each CLI's usual permissions, so they ask before running commands and editing files. The menu names only the agent either way. The file is read each time an agent starts, so every window and the phone follow a change at once; a session that is already running keeps its mode until it is closed. Orchestrators keep their own rules (see [Orchestrator](#orchestrator)), `riwork shell create` keeps its own flags, and chats have their permission mode in the chat.
- **Show microphone buttons for dictation** (Agent sessions) is off by default and saved as `dictation_mic` in `settings.json`. It governs every dictation mic: on the Mac, every Codex and Claude chat tab then shows a mic button beside Send: click it, or press ⌃⌥D in the chat, to dictate into the message box, and again to stop (⎋ cancels); the words are recognized on this Mac by the bundled `riwork-speech` helper and never sent anywhere, and dictation never sends the message. Off, the chats show no mic, their hint line does not mention dictation, ⌃⌥D does nothing in them, and no speech helper starts or asks for the microphone or speech recognition. Switching it off during a dictation cancels it, and open chat tabs follow at once. The paired phone follows the same setting through `appearance.json` (`mic`, below) and shows or hides all of its mic buttons, in its chat composers and on its terminal key bar. The Mac's terminals have no dictation.
- **Claude chats bill** (Agent sessions) chooses **Subscription** or **API key** for new Claude chats; API key is the default. It is saved as the switch it grew from, `claude_chat_ignores_api_key` in `settings.json` (`true` is Subscription; `false`, absent or unreadable is API key), so builds from before, and a chat host of one still running, read the same choice. Subscription starts the chat's `claude` without `ANTHROPIC_API_KEY`, so a key exported in your shell cannot switch it from your Claude subscription to API billing. API key gives it the Anthropic API key saved below, billed to your Anthropic API account (and any API credits it has), or, with none saved, the environment it would have anyway, `ANTHROPIC_API_KEY` included, keeping every sign-in method it has, as Anthropic's terms for products that run Claude Code ask. Each chat keeps the choice it was made with (its message box switches it); a chat from before the choice follows this setting at each start. Claude terminal tabs are not affected.
- **Anthropic API key** (Agent sessions) takes a pasted key in a masked field, with **Save** and **Remove** and a line that says whether a key is saved, never the key. The key is kept only in the login Keychain, as one generic password (service `dev.riwork.anthropic-api-key`, account `claude-chats`): never in `settings.json`, a chat's info, events or logs. The chat host asks for it each time it starts a Claude chat on API key (never when the host itself starts) and gives it to that chat's `claude` as `ANTHROPIC_API_KEY`, as a key exported in your shell would be: the commands Claude runs inherit it, so what they print is the agent's output. A chat host, window or tmux server that a command inside such a chat starts drops it again. A saved key the Keychain will not give fails that start with the Keychain's reason rather than starting Claude on another sign-in; a Keychain that cannot even say whether a key is saved leaves the start as it always was. A Keychain that refuses a save or a removal says why and changes nothing. Saving a key affects every Claude chat set to API key, including the default for new chats, from its next start; Settings says so beside the field.
- **Orchestrator runs as** (Agent sessions) chooses how the global and project orchestrators are created from now on: **Automatic** (the default), **Terminal** or **Chat**. Automatic starts a Muse chat on `muse-wonder-full-1.0`, the best delegator, and when Muse cannot start (not installed, or its chat fails to start) a Codex chat on `gpt-6.1-sol`, the workhorse, and says so: the window that asked shows why, and `riwork orchestrator create` prints it as `fallback` (a **Note** in plain text). If neither starts, creation fails with each reason and nothing is left behind. Terminal is the Codex terminal orchestrators always were. Chat shows **Chat provider** (**Codex**, **Claude** or **Muse**) and **Chat model**: the provider's own default, the model RiWork's routing recommends for it (Muse `muse-wonder-full-1.0`, Claude `opus`, which Claude reports as Opus 5.5, Codex `gpt-6.1-sol`), a model saved earlier, or any ID typed into **Other model** and saved with Return; another provider starts on its own default. An explicit Chat that cannot start is an error, never replaced by another provider. They are saved as `orchestrator_mode` (`automatic`, `terminal` or `chat`), `orchestrator_chat_provider` and `orchestrator_chat_model` (null: the provider's default) in `settings.json`, and the CLI, the MCP tools, the windows and the phone read the file each time they create one, so a change applies to all of them at once. These keys are written only when you choose in these rows, so saving another setting leaves them out and a file without `orchestrator_mode` (a fresh one, or one from a build before orchestrators had modes) is Automatic, whatever the default of a later build; a saved `terminal` or `chat` from an older build is a choice and stays one until you change it. A value this build cannot read (or a model saved beside a provider it cannot read) is kept in the file as it was, Settings name it under the rows, and the default stands in for it until you choose in the row, even the value shown. A project can choose for its own orchestrator in Project Settings (below). It applies only to orchestrators created from now on: an existing orchestrator keeps its mode, provider and model until it is closed (`riwork orchestrator close`) and created again, which is also how the rule for the unrestricted mode of project orchestrators works. A custom `--command` is always a terminal. See [Orchestrator](#orchestrator).
- **Delegation** (Agent sessions) is the policy orchestrators are told when they start or load their skill: **Spread work** (on by default: fan independent tasks out to several worker shells at once; off, one worker at a time unless asked), **Parallel worker shells** (a soft target, 1 to 10, default 4), and the harness and model to prefer for **Design work** (default Claude `opus`) and **Workhorse work** (default Codex `gpt-6.1-sol`), as the skill's model routing does. RiWork starts no shell by it; the orchestrators act on it. It is saved as `delegation_policy` in `settings.json` (`spread_work`, `parallel_shells`, `design` and `workhorse` as `{"provider":"claude","model":"opus"}`), written only when you choose, field by field: a field never chosen follows RiWork's default, and a value this build cannot read (or a policy that is not an object) is kept as it was and named under the rows; a model id a session would refuse is never saved. A project can override any field (below). The startup message states the result in one sentence; a running orchestrator keeps what it was told until it is created again or loads its skill, and shows **Load skill** once a change applies to it.
- **Remember project window size** is on by default. New or reopened project windows restore the last normal window size, fitted to the current display's visible area, and later windows in the cascade stay on that display. Only a size you set by resizing is saved: zooming (the green button or a titlebar double-click), entering fullscreen, or the smaller size a window is clamped to on a smaller display does not overwrite it. Switching projects in an existing window keeps that window's size. Layouts without a saved size use the default size until the window is resized.

The phone companion shows the same colors. Whenever the app starts, and whenever the resolved palette or the terminal colors change (a theme choice, macOS switching between light and dark under Native, an edit to your Ghostty configuration, **Use RiWork terminal colors**, or **Terminals match the theme**), the app writes them to `appearance.json` under the RiWork data directory (mode 600, replaced atomically, and left alone when nothing changed). `riwork appearance` prints a short summary and `riwork appearance --json` the file's validated contents: `v`, `updated_at`, `dark` (the palette background's relative luminance is below 0.5), `palette` (`bg`, `panel`, `panel_active`, `divider`, `cyan`, `magenta`, `gold`, `text`, `muted`) and `terminal` (`background`, `foreground` and the 16 ANSI colors as shown, omitted when unknown), all colors lowercase `#rrggbb`, then `"native": true` while Native is the theme and `"mic": true` while **Show microphone buttons for dictation** is on (each left out otherwise, so the file is what it was before them; switching either is published even when no color changes, and the summary's first line names them, as in `Appearance: dark, Native, mic`). Until the app has published, it exits with an error asking you to open RiWork. The phone reads it through the remote `appearance.get` method.

The embedded Ghostty adapter currently uses the light variant of a paired `light:…,dark:…` theme and does not follow macOS appearance changes. A single Ghostty theme or an explicit RiWork theme applies consistently.

## Scheduled prompts

Open **SCHEDULES** from the pane **+ / ▤** menu, **RiWork → Schedules**, or **Cmd+Shift+S**. App schedules target the existing global orchestrator, project schedules target their existing project orchestrator (in a terminal or as a chat), and workspace schedules target an explicitly selected worker in a worktree. The compact native panel supports quick future first-run choices with local timezone previews, optional exact date/time entry, one-time or elapsed-time recurring prompts, edit/pause/delete, and visible next/last outcomes.

Scheduling runs while RiWork is open. A schedule on an orchestrator that runs as a chat is delivered through the chat host: the prompt is sent as a chat message when the chat is idle or stopped, and deferred while it is working or waiting for you. Busy or blocked targets defer for up to five minutes; older occurrences are skipped. There is no overdue replay or automatic retry of uncertain delivery. Targets remain pinned across windows and restart; failed or uncertain schedules pause for review. See [timing, lifecycle, persistence, and verification](docs/scheduling.md).

Agents can configure these schedules with `riwork schedule list|show|create|update|pause|resume|delete` or the discoverable `riwork_schedule_*` tools in `riwork mcp`. Run `riwork schedule help` for UUID, scope, revision, and time requirements; [CLI and MCP examples](docs/scheduling.md#cli-and-mcp-agent-configuration) cover all three scopes.
